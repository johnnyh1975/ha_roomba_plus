# Roomba+ 4.6.0b1

**The first beta of 4.6.0.** It needs *Include pre-releases* for Roomba+ in
the Marketplace (*Show beta versions* in HACS before Home Assistant 2026.11)
and is built on **roombapy-prime 0.9.1**, unchanged from 4.5.4.

4.6.0 has two themes:

- **Prime robots get what Classic robots already had**, wherever the robot
  reports the data.
- **Missions become visible to automations and scripts**: when one
  starts, how it ended, which rooms it missed, what it used, and what a
  clean would take before it starts.

Everything new is additive. Existing entities, bus events and their fields
stay as they were.

None of this has run on a robot yet. Please report back:

- **Prime robots** (@utkjmitch, @Baby-scarf, @ecovictor75): start a clean
  from Home Assistant now and then. If the robot does not start,
  `event.<robot>_command` should show *Command not delivered*. If you
  download the diagnostics afterwards, `command_watches` shows how long
  each start took to arrive. Those times decide how long Roomba+ waits on
  Prime: 60 s for now, which is an estimate.
- **A 600** (@tankdeer): run, restart Home Assistant. The maintenance
  figures **and** *Total time* should stay where the run left them.
- **A start held back by a blocking sensor** (@ar2000ar): it should show
  on `event.<robot>_command` as *Start held back*.
- **Anyone with rooms mapped to Home Assistant areas**: the area sensors
  and `roomba_plus.plan_clean`, described below.

## Prime robots: what Classic already had

Each Prime platform used to stop before the part it shared with Classic,
so Prime lacked entities whose data it has. Now the shared entities are
created on Prime too, **each once the robot reports its field**:

- **Mission sensors**: start, elapsed time, id, recharge and expiry.
- **Lifetime figures**: average mission time, lifetime completion rate.
- **Dock counters and dock firmware.**
- **History sensors**: missions and completion rate over 30 days, last
  mission area, last error (code, time, room), the last mission
  summary, and the presence sensors.
- **Binary sensors**: mission active, mid-mission recharge, firmware
  updated, maintenance due, start blocked, demand clean blocked.
- **Other entities**: the stuck event (from the robot's `stuck` phase), a
  floor plan of each stored map (disabled by default), the raw state, and
  room progress for missions started in the app or by a schedule (the
  rooms visited, from the mission timeline).
- **A mission archive** of up to 800 missions, included in the backup.
  The mission path view reads it.

What Prime still lacks and why is listed per section in
[FEATURES.md](../docs/FEATURES.md#which-generation-section-by-section-460).

## A command the robot ignores

Sometimes a robot takes a start command without starting. The broker
confirms delivery, the robot stays on the dock, and nothing in Home
Assistant said so: Roomba+ wrote a warning to the log on Classic only,
and on Prime said nothing at all.

**Both generations, every start Roomba+ sends.** This covers:

- the actions and the start command (`vacuum.start`,
  `vacuum.clean_area`, `send_command` with `start`, `clean_room`,
  `clean_zone`, `run_favorite`, `smart_start`);
- the automatic starts: the blocking-sensor release,
  `auto_clean_dirty_rooms` and demand cleaning;
- the zone and favourite buttons and *Repeat last mission*.

When the robot has not started 20 s (Classic) or 60 s (Prime) after the
command:

- **`roomba_plus_command_not_delivered`** fires, shown as *Command not
  delivered* on the new `event.<robot>_command`.
- **The command is sent once more**, but only when the robot is idle and
  reports no reason for refusing. The option *Send an ignored command once
  more* turns this off.
- **A Prime cloud document frozen on `run`** while the battery charges is
  reported as its own type, `state_frozen`. Sending again does not help
  there; a robot restart does.

A start that does arrive late is recorded for five minutes in the
diagnostics, with how long it took.

## Mission started, mission result, missed rooms

- **`roomba_plus_mission_started`** and `event.<robot>_mission_started`:
  who started the mission, `whole_home` or `rooms`, which rooms, their
  Home Assistant areas, and the mission number. On Prime, who and where
  come from the last command, and only when it is less than five minutes
  old: a schedule start sends no command.
- **`roomba_plus_mission_result`** and `event.<robot>_mission_result`:
  `completed`, `completed_with_skips`, `cancelled`, `stuck_abandoned` or
  `error`, with the rooms that were skipped and the rooms asked for but
  not reached. On Prime, the rooms asked for come from the history's
  command and the cleaned ones from its timeline.
- **`roomba_plus.retry_missed_rooms`** cleans what the latest mission (or
  the one you name) skipped or did not reach.
- **`roomba_plus_room_completed`** carries the room's `area_id` and
  `area_name`.
- **`roomba_plus_start_blocked`** and **`_start_timeout`** carry the
  robot (`entry_id`, `name`) and show on `event.<robot>_command`. Until
  now an automation could not tell which robot was held back.

## Where the running mission is

`sensor.<robot>_current_room` and `sensor.<robot>_estimated_end_time`,
on both generations, beside mission progress. Until now these were
attributes only.

The room sensor lists each room of the run as `pending`, `operating`,
`skipped` or `completed`, the terms Matter uses, and names the room's
Home Assistant area.

## Answers for scripts and Assist

There are four new response actions (`response_variable:` in a script).
They read what Roomba+ already holds and ask nothing of the cloud:

- **`get_rooms`**: the rooms and zones, with map, area, time estimate and
  how good that estimate is.
- **`get_missions`**: the newest stored missions, by `limit` and `days`.
- **`get_mission`**: one mission in full, with the battery it used and,
  per room, whether its time was learned.
- **`plan_clean`**: what a clean of the rooms given would take if started
  now, without starting it. With `end_by` the answer says whether it
  `fits` ("only start if it is done by 5 pm"). Travel and recharges are
  not part of the room estimates; `past_error` says how far recent
  missions' estimates were off. A room without an estimate leaves the
  total empty, instead of giving a total that leaves the room out.

## What a mission taught, and how good an estimate is

- **Why a room taught nothing**: for each room of a mission, `get_mission`
  says whether its time went into the learned estimates and, if not, why:
  passage, not finished, too short, too long, skipped, or the mission's own
  stuck, error, cancel or pause. The learning goes through the same rule,
  so the answer is what was learned.
- **The quality of an estimate**: runs, spread and a rating (`high`,
  `medium`, `low`, `none`). The spread counts the runs from this version
  on. Nothing stored is migrated.
- **Each mission now records what it was estimated to take**, on both
  generations, so the estimates can be measured against the time taken.

## Battery per mission

The last mission summary shows the battery at start and end, the use, and
the use per m². A mission that recharged on the way has no figure, because
its end level says nothing about what it used.

The summary has had `battery_start_pct` and `battery_end_pct` since 3.1.0,
and they were always empty: no mission record ever carried them. They are
filled now.

## When each area was last vacuumed and mopped

`sensor.<robot>_<area>_last_vacuumed` and `_last_mopped` are off by
default, one pair per Home Assistant area the robot's rooms map to. **The
value covers the whole household**: the newest mission of that kind by any
Roomba+ robot. A kitchen the Roomba vacuums and the Braava mops shows both
times. Prime missions now record their cleaning mode so they can be told
apart.

## Smaller additions

- **Send home after a pause** (Configure → Settings): a robot left paused
  this many minutes goes back to its base. Off by default.
- **Debug capture**: `roomba_plus.debug_capture_start`, `_stop` and `_get`
  record a redacted debug log in memory, without editing
  `configuration.yaml` or restarting.
- **Blueprints arrive with the integration** under
  `blueprints/automation/roomba_plus/`. An existing file is never
  overwritten, a blueprint you deleted does not come back, and one you
  imported through its link is not added a second time.
- **Prime cloud streams**: four diagnostic sensors, off by default, show
  when the state, timeline, live map and refusal streams last delivered a
  message. The diagnostics carry the same.

## Counters survive a restart (@tankdeer)

A 600 does not send its lifetime counters again when Home Assistant
reconnects; it sends them with its next mission. *Total time*, the
mission counts, the average duration and the other lifetime counters read
*Unknown* after every restart until then. They now show their value from
before the restart until the robot reports again. Live values such as
battery, phase and signal are not kept.

4.5.4 kept the hour meter for the maintenance figures, but only when the
reading arrived beside a mission status message. The robot sends it as a
message of its own and is then quiet on the dock for most of an hour. The
diagnostics from Thursday show the reading from a scheduled run was never
stored. The reading is now kept from that message itself.

## Fixed along the way

- **Device triggers that could never fire are no longer offered.** On
  Prime this covers `bin_full`, `health_score_drop` and the map retrain
  triggers; anywhere, `start_blocked`, `maintenance_due` and
  `firmware_updated` where the robot lacks their entity. **`start_blocked`
  fires on Classic now**; it looked for the Prime entity and never fired.
  Automations that already use one keep working; they did not fire before
  either.
- **Prime: the mission's initiator held the whole command**, including the
  robot and map ids, in the last mission summary, the REST history and the
  diagnostics. It is the word again, and stored missions are repaired at
  the next history sync.

## Under the hood

- `services.async_send_watched()` wraps every start; `command_watch` reads
  Classic's local state and Prime's `ro-currentstate.cleanMissionStatus`.
- `PrimeMissionArchive` (`prime_mission_archive.py`): 800 records, in the
  backup, removed with the entry.
- New modules: `mission_started.py`, `mission_queries.py`,
  `estimate_quality.py`, `mission_battery.py`, `sensor_areas.py`,
  `pause_timeout.py`, `blueprint_install.py`, `debug_capture.py`.
- `area_resolver.async_area_for_room()`: one room-to-area rule for the
  device tracker, the events and the sensors.
- `room_times._timeline_rooms()` / `room_learning()` / `visit_learning()`:
  the learned figures and their reasons from one rule. `room_spread()`
  and three additive sums beside each mean.
- `RoombaSensor` is a `RestoreSensor`; `_KEPT_ACROSS_RESTARTS` names the
  lifetime counters that use it.
- `scripts/check_blueprint_copies.py` keeps the shipped blueprints identical
  to `blueprints/automation/`.
