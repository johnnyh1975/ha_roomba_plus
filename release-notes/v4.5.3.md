# Roomba+ 4.5.3

**Commands reach a Prime robot that iRobot moved to another part of its
cloud, a 600-series Roomba added through the account is set up as the
Classic robot it is, Wi-Fi health reads the right way round, a picked
cleaning mode holds, and the problem zone names only a room it knows.**

---

## Commands to a Prime robot on another deployment (roombapy-prime 0.8.3)

iRobot runs its cloud in several deployments, each with its own MQTT
topic prefix. Roomba+ sent every robot's commands under the prefix the
account's login named. A robot iRobot had moved to another deployment
took none of them: the cloud acknowledged the command, the robot stayed
on the dock, and state and battery kept arriving as if nothing were
wrong. @ecovictor75's Combo 105 had been moved this way; sent under its
own deployment's prefix, the same start started a mission at once.
@leonel11fcp reports the same picture on another Combo 105.

roombapy-prime 0.8.3 takes each robot's prefix from the robot's own
deployment, as the iRobot app does. Diagnostics show whether they match:
`topic_prefix_matches_robot_deployment` (`true`, `false`, or `null` when
the login names no deployment).

## A 600-series Roomba is a Classic robot (roombapy-prime 0.8.3)

A Roomba 694 (@tankdeer) and a 600-series robot with SKU `R671020`
(@egold555) were not in the table that tells Classic from Prime. Added
through the iRobot account, they were set up as Prime robots, cloud
only, and their state never changed. The 600 series is Classic now, and
the account flow sets such a robot up on the local connection.

**Already set up?** Delete the entry and add the robot again, from the
account or by its IP address. A 600 keeps no map, so there is no room
cleaning on it; start, stop, dock, battery, bin and errors work.

## Wi-Fi health read the histogram the wrong way round (@albertompinto)

iRobot's mission history reports the Wi-Fi signal as five shares: the
time at four bars, three, two, one and none, in that order. Roomba+ read
the first share as the weakest since 2.2.0. A robot with a strong signal
therefore showed a very low *Wi-Fi health*: @albertompinto's Combo j9+,
at -54 dBm on average, showed 3.5 % instead of 96 %, and a robot with a
weak signal showed a high one. The cloud's own start and end bars, which
come with each mission, confirm the order.

- *Wi-Fi health* now averages the bars.
- `weakest_bucket_observed` is the fewest bars seen in the latest
  mission (0 = none, 4 = full), as documented. It returned the strongest
  before.
- `stability_pct` did not depend on the order and is unchanged. It is a
  spread in bars, not a percentage, whatever its name says.

## The cleaning mode can be changed again (@ar2000ar)

The *Cleaning mode* select showed the mode of the robot's last start
whenever there was one, and that won over a mode picked in Home
Assistant. Since almost every start carries a mode, a pick snapped back
at once, and a clean started from Home Assistant used the old mode, not
the picked one. It only worked when the robot's last command was not a
start, which is why it "rarely" worked.

A pick now holds until the robot starts again. A start from the iRobot
app after the pick shows that start's mode, because that is what the
robot did. The pick survives a restart of Home Assistant.

## The problem zone names only a room it knows (@albertompinto)

*Error – Problem zone* counted every room a stuck mission had been
sent to. On @albertompinto's j9+ it named the kitchen, where the robot
had never got stuck: one of four stuck missions had rooms at all, three
of them, each counted once, and the first won. A stuck mission records
where it was sent, not where it got stuck. Now:

- only a mission sent to a single room counts, for that room;
- a docking error (18) counts for no room;
- a room is named only when it leads with at least two missions.

Otherwise the sensor is empty, which is the honest answer.

## Under the hood

- **`roombapy-prime[map]==0.8.3`** instead of 0.8.2.
- **`roombapy>=2.0.2` instead of `roombapy==2.0.2`** in the manifest.
  From Home Assistant 2026.11 its built-in Roomba integration pins
  `roombapy==2.0.2`, and Home Assistant's own check (hassfest) rejects a
  custom integration pinning a package Home Assistant depends on. The
  minimum lets Roomba+ follow when Home Assistant updates the library.
  Nothing changes for an installation today: both ask for 2.0.2. CI
  still tests 2.0.2.
- `scripts/check_ci_pins_match_manifest.py` compares a minimum in the
  manifest like a pin.
- `diagnostics._prefix_matches_deployment()`; the field reads the
  robot's `svc_deployment_id`, which roombapy-prime 0.8.3 sets.
