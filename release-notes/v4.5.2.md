# Roomba+ 4.5.2

**Ready for Home Assistant 2026.11. The cleaning path no longer gives up
on a robot that is slow to give its first position, a backup now
includes the mission archive, Prime robots no longer log a false "no
mission started" after every room clean, and a run with no start time
that cleaned nothing is no longer recorded as a mission.**

---

## Home Assistant 2026.11

Home Assistant 2026.11 moves its built-in Roomba integration to `roombapy`
2.0.2, the version Roomba+ uses. Until 2026.10 the two needed different
versions of the library, and whichever loaded second failed. From 2026.11
both load.

- **New notice: a robot set up in two integrations.** An old entry of the
  built-in integration that could not load before now loads, and connects
  to the robot. A robot takes one local connection at a time, so the two
  take it from each other. Roomba+ names the robot; remove it from one of
  the two. A different robot in each integration is fine and gets no
  notice.
- **The "two Roomba integrations" notice** about the library is shown on
  2026.10 and earlier only.
- **The setup errors about an old `roombapy`** name the built-in
  integration as the cause on 2026.10 and earlier only.
- **The workaround folder** from the troubleshooting guide (an empty
  `custom_components/roomba`) can be deleted after updating to 2026.11.

Checked against Home Assistant 2026.11.0b4: the full test suite passes,
and the built-in integration imports with `roombapy` 2.0.2.

## The cleaning path when the robot is slow to answer (@nareso)

On robots that do not report their position on their own (i7, j7, s9 and
others), Roomba+ asks for it while they clean. If no position came in the
first two minutes of a mission, it stopped asking until the next one. On
@nareso's j7+, a zone clean started from Home Assistant sometimes took
longer than that: the path stayed empty for the whole mission, and the
*Cleaning path* showed iRobot's coverage dots instead. Started from a
favourite, the same robot answered at once, which is why it only happened
sometimes.

A robot that has given positions before is now asked again after a pause
(30 s, then 60 s, then every 120 s, a bounded number of times), as Roomba+
already did for a robot that falls silent in the middle of a mission. A
robot that has never given a position is still left alone for the rest of
the mission.

**A correction to 4.5.1.** Its notes named the Clean Base emptying the bin
as the cause of these dots. @nareso's log showed otherwise. The 4.5.1
change stays right on its own (emptying the bin is not a new mission), but
it was not his cause.

## A run with no start time that cleaned nothing is not a mission

On the maintainer's 980 the battery ran out during a mission. Hours later,
when the robot came back on, a "completed" run with no start time, no
area and no mission number was recorded, with a duration of 0 minutes.
iRobot's history has no such mission. Such runs are no longer recorded:
"completed", nothing cleaned, nothing stuck or lifted, and no known start.
A run with no known start that did clean something is still kept, and so
is everything with a start time (the half-minute rule for those is
unchanged).

## The backup includes the mission archive

*Create backup* left two stores out: the mission archive (up to 800
missions; on Classic paged back from iRobot's history) and the turn of
the cleaning path that Roomba+ learns per map. A backup restored on a
new Home Assistant came back without both. They are in it now. A
backup made with an earlier version restores as before, still without
them. Found in the code, not reported.

Left out on purpose, as before: the state of the mission running at
the time, the map pictures (drawn or fetched again) and when demand
cleaning last started a run.

## "Accepted, but no mission started"

Roomba+ has logged a warning when a room clean was taken by the robot
and nothing started within 20 seconds: a cliff sensor reading a dark
rug as a drop-off, a room start sent away from the dock, a stale map.

- **On Classic, zone cleans and Start are watched too.** A zone clean
  is the same command as a room clean and is ignored the same ways. A
  Start from the dock is watched as well; a Start into a paused or open
  mission is not, because it resumes, and whether the robot took that
  cannot be told from its state.
- **No more false warning on Prime.** A Prime robot has no local state
  for the check to read, which it took for "no mission". Every room
  clean on a Prime robot since 4.0 was followed by this warning, with
  `phase=None, notReady=None, error=None`, whether the robot started or
  not. Prime robots are not watched now. Found in the code, not
  reported.

## Smaller changes

- **The cloud check after a mission ignores the bin being emptied.** It
  counted the Clean Base emptying the bin after docking as cleaning and
  started over for the same mission; with the emptying more than two
  minutes after the end, it could log "giving up for this mission" for
  nothing. The same rule as the cleaning path since 4.5.1. Found in the
  code, not reported.
- **A repeated state after the end keeps the cleaning path.** A cleaning
  phase under the start time of the mission that has just ended (within
  two minutes) no longer starts a new mission on the map, the same rule
  the mission records have had for this. A precaution: no case of it on
  the map has been seen.

## The release page

The release page now shows the channel next to the title, a warning when
the notes contain a breaking change, the parts of the repository changed
since the previous release (counted in files), a table with the version,
date, comparison, requirements and downloads, and links to the
documentation and the issue tracker. Suggested by the release pages of
FaserF/ha-openwrt. The notes themselves are unchanged in the repository.

## Under the hood

- `live_position.LivePositionStream`: a timeout without a first position
  goes to `_stalled()` when the robot has answered before
  (`_stalled(what=...)` names the reason in the log).
- `callbacks.async_record_mission`: the half-minute rule also applies
  without a start time when nothing happened; the warning about a missing
  start no longer promises a record.
- `callbacks.make_mission_complete_callback`: phase or cycle `evac` does
  not count as cleaning.
- `image.RoombaMapImage._replays_ended_mission()`,
  `MISSION_REPLAY_WINDOW_SECONDS` (120 s).
- `services._BACKUP_STORES` gains `mission_archive` and `path_turn`;
  `_NOT_BACKED_UP` names the stores left out on purpose, and a test
  holds every store in `_STORAGE_KEYS_TO_REMOVE` to one of the two.
- `services.watch_for_swallowed_command()` starts the watch for room
  clean, zone clean and the vacuum's Start; `_async_warn_if_swallowed`
  returns at once without a local robot.
- Two tests depended on today's date (a 30-day and a 90-day window over
  fixed dates); one failed from 29 October 2026. Both are pinned now.
- `repairs.core_roomba_shares_our_library()` (HA 2026.11 and later);
  new issue `core_roomba_same_robot`.
- CI: `ruff` 0.17.3, `mypy` 2.4.1, `actions/checkout` and
  `actions/upload-artifact` v7 (neither change in them touches these
  workflows: no `pull_request_target` or `workflow_run`, one zipped
  file uploaded). A backup test stub now takes a path
  in parts, as HA 2026.11's `Store` asks for one.
- `scripts/build_release_body.py`; `release.yml` checks out every tag and
  publishes the built body.
- CI: the current-HA job runs HA 2026.10.3; `ruff` is pinned. Three test
  stand-ins for `hass` ran executor jobs on the loop's default executor
  and left a thread behind, which HA 2026.10's checks report; they run
  them inline now.
