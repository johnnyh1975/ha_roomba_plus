# Roomba+ 4.2.0b2

The second beta of the async rewrite. **Everything in 4.2.0b1 still
applies** — see those notes for what the rewrite changes and what is
worth testing. This adds three field fixes and clears the suite's
warnings.

If you are already on b1, this is a straight update. If you are on
4.1.1, read the b1 notes first: the two connection settings disappear
there, not here.

---

## A Roomba 980 was told to replace a bag it does not have

`binary_sensor.<robot>_maintenance_due` turned `on` with
`due: ["clean_base_bag"]` on a 900-series, which charges on a plain dock
(@liblit, R980020, with diagnostics).

Every per-part entity was already suppressed for those robots — no Clean
Base status, no wear-rate sensor, no reset button. The maintenance-due
path was not: it walked all four consumable roles regardless. And the
cloud could not contradict it, because there is no cloud record for a
part the robot does not have, so the check fell through to the local
hour count — which counts **runtime**, not bag use. With nothing ever
reset and a 30-hour default, the bag went due at 30 hours and reported
75 overdue at his 105.

Absence is now a property of the consumable itself rather than a check
at one call site, so the sensor, the API view and the Repairs backstop
all inherit it.

**Not gated: side brushes.** The report suggested the same treatment for
those, but a 980 has one — gating it would silence a real reminder on
every robot without a Clean Base.

Three existing tests had to change with it. They described a robot with
no dock and asserted the bag came back due, so they were pinning the
bug.

## Cleaning passes and suction now actually change

Two settings that have never worked on i/s/j robots and reported success
every time.

The firmware reads `noAutoPasses`+`twoPass` as one value, and
`carpetBoost`+`vacHigh` as another — one handler per pair, which looks
up both keys and gives up if either is missing. Roomba+ sent them as two
separate messages, so the robot accepted each and applied neither.

Three separate things agreed on that: the handler itself, in two
firmware families; a wire measurement where single keys produced nothing
and the pair echoed back in 0.65 s; and dorita980, which has never sent
them any other way.

The fix needed a library change, which is now upstream in roombapy
2.0.2. A guard fails the build if either half is ever sent alone again —
it is the kind of edit that looks perfectly reasonable and does nothing.

## CI was testing a library nobody runs

A dependency of Home Assistant 2025.5 declares `pycares>=4.0.0` with no
upper bound. pycares 5 removed a function that dependency uses in its
own type annotations, so a fresh CI run broke on `import aiohttp` before
collecting a single test — through no change on this side.

Pinned, with the reasoning written down next to it. Two more problems
surfaced while reproducing that environment properly for the first time:
type checking ran against the wrong Python version, and a real type
error underneath it that only the supported Home Assistant reveals.

## The test suite runs without a single warning

Down from 41, and RuntimeWarnings now fail the build.

None of the 41 turned out to be a real bug — every unawaited call in the
integration itself is correctly inside a task. But a warning that is
always there is one nobody reads, and a genuinely dropped coroutine
looks exactly the same in the output. That failure mode is a command
that silently never reaches the robot, which this project has shipped
once already.

---

## Still what this beta is for

No part of the async rewrite has run against a real robot. Every check
that can be made from a keyboard is green — 6,219 tests, type checking,
eleven guards — and none of it says whether the connection comes up
cleanly on your firmware, or what happens when your Wi-Fi drops
mid-mission.

**The failure to watch for is a command that silently does nothing.**
The robot does not move, nothing appears in the log. If you press
something and it is ignored, that is worth reporting even if you are not
sure.

4.1.1 remains stable and has every fix from this week that does not
depend on the rewrite.
