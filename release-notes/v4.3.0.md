# Roomba+ 4.3.0

**One iRobot account for all your robots, and the end of the 4.2 line.**

4.3 changes how Roomba+ uses your iRobot account: how you set up
several robots, and how they log in to iRobot's cloud. It does not
change what your robots do. Ten betas tested it, and each one also
carried the fixes of the 4.2 release next to it, so **every fix through
4.2.22 is in here**. 4.2.22 was the last 4.2 release.

If you are on 4.2.22, this is a normal upgrade. Built on
**roombapy-prime 0.5.0**, installed with the update.

[Upgrade notes →](../docs/UPGRADING.md#v430--from-v42x)

## Setting up several robots

Until now every robot was its own setup from scratch: the account typed
in again for each, one robot per run, and on the local path the HOME
button held on every robot.

- **Set up the first robot with your iRobot account, and the others are
  offered.** They appear in *Settings → Devices & services* under
  **Discovered**; one click adds each, nothing needs to be entered. A
  Classic robot is looked up on your network, and only if it cannot be
  found does the setup ask for its address (with Home Assistant in a
  container without host networking, or the robot on another subnet).
- **An account already in use is offered, not asked for.**
- **No HOME button for a robot of a known account.** When Home Assistant
  finds a Classic robot whose account a robot here already uses, its
  password comes from that account. If the robot refuses it, the HOME
  button step appears as before and says why.
- ***Set up with my iRobot account* comes first**: it works for every
  robot, finds all of them and needs no button. Setting up without any
  cloud account works as before.
- **The robot list says which robots are already set up**, and a robot
  appearing on the network no longer closes a setup you are in the
  middle of.

## One login per iRobot account

Every robot used to log in on its own: three robots, three full logins
within a second on every restart. iRobot limits sessions per account
and locks an account after too many attempts, and a restart with
several robots was the moment most likely to hit either.

- **The first robot to start logs in; the others take that login.**
- **Renewals are shared too**, on both generations. A Prime robot whose
  token is due takes a fresh login another robot has just made, and its
  map requests relog through the account.
- **A failed login answers for the others for half a minute** instead
  of every robot trying again. Against a locked account every attempt
  extends the lock.
- **A password change is entered once.** Every robot with the same
  account address and the same old password takes the new one and
  restarts. A robot with a different password is left alone.
- **A cloud login that failed at startup is retried ten minutes later**,
  not a day later, and is no longer reported as wrong credentials.

Nothing about the login is written to disk.

## Cloud errors in your language

Every cloud error now says its cause in all eight languages: login
rejected, **account temporarily locked** (do *not* re-enter your
password; wait about ten minutes), too many sessions, a certificate
this machine cannot check, a problem on iRobot's side, or no
connection. The setup forms no longer blame the robot for a cloud
problem.

## Prime robots: a rebuilt cloud connection

roombapy-prime 0.5 runs a Prime robot's cloud connection on Home
Assistant's own event loop, with aiomqtt. What goes over the wire is
unchanged. How it gets through a drop is not:

- **A robot could go silent until Home Assistant restarted** after a
  drop at an unlucky moment, with the log still saying "watch resumed".
  Fixed.
- **The hourly token renewal no longer shows as a drop**, and a real
  drop logs one "dropped" and one "resumed" line.
- **No reconnect loop** when the server never confirms a subscription.
- **Unloading or stopping Home Assistant closes the connection for
  good**, instead of leaving one behind to compete with the next.

## A live cleaning path for robots that report no position

An i7 or S9+ on lewis, or a Braava jet m6, never sends its position on
its own, so the cleaning map showed the last finished mission from the
cloud. These robots do answer when asked. Roomba+ now asks about once a second while the robot
moves, and draws the path live. Confirmed across whole missions on an
S9+ (91 minutes, 3,799 positions) and a Braava jet m6 (131 minutes,
5,223 positions) (@ScenicSystemsLLC).

- **On by default, for these robots only**: Configure → *Connection
  settings* → *Ask the robot for its position*.
- **Live picture only.** Whether the robot's frame lines up with the
  cloud map has not been checked, so the path does not feed the coverage
  heatmap, door markers or room learning, and the map carries no
  `calibration_points`/`rooms` while it shows such a path.
- **An i3 on daredevil does not answer.** @AlakazipLabs asked one 2,875
  times over a whole run: no reply. The 4.3.0b8 notes counted the i3
  among the robots that answer; nothing on record supported that. A
  j-series has not been tried. Robots that stay silent are asked three
  times per mission, then left alone.

## The mission archive reaches further back

The cloud ignored the parameters the archive used to page back (Roomba
980 and i7, thanks @Thonno), so it only ever held the recent window.
It now pages back with the two that work, up to 800 missions, once,
in the background, one page every two seconds. A mission-counter reset
ends it, so two missions never share a number.

## Since 4.3.0b10

- **Maintenance resets on robots that keep their hours in
  `runtimeStats`.** The sensors read the hours there; the reset
  buttons, the to-do list, the due check and the cloud hydration read
  `bbrun.hr` only, which a j7+ and a j9+ do not carry (@msva17). A
  filter reset recorded 0 hours, so the filter read 0 the moment it was
  reset; side brush and bag resets left them at 0; and *Maintenance
  due* never came on. Everything now reads the same hours. **A part
  that read 0 after a reset needs the reset pressed once more.**
- **Importing rooms from roomba_rest980** took clean zones as well, so a
  zone could overwrite a room with the same number, and a second
  floor's rooms were filed under the current map. It now takes rooms
  only, and only the current map's.
- **Diagnostics**: every id field a clean zone carries on the active
  map (`cloud.clean_zone_ids`, no geometry), the region types beside
  the ids of each sent command, and the *Clean zone* button's start on
  the record (@Hardy-196).
- **roombapy-prime 0.5.0** is pinned; its code is 0.5.0b2's, which b6 to
  b10 ran on.
- The comparison with roomba_rest980 was re-read for this release.

## Under the hood

- **`cloud_api.py` is gone.** Roomba+'s own cloud client for Classic
  robots moved into roombapy-prime unchanged: the same query, body bytes
  and signature, tested there request by request. Both generations use
  one library for the cloud.
- **`_prime_login_bridge.py` is gone**, replaced by `cloud_account.py`,
  keyed by the account instead of the robot.
- **The diagnostics have a `cloud_account` section**: whether the entry
  shares its login and with how many, how old the login is, how many
  robots the account has, and the reason of a recent failed login. No
  address, no password, no hash of either.
- **`cloud_errors.py`** turns an error's reason into a translation key.
  A test holds the texts to the library's list of reasons, so a reason
  added upstream without a text fails the build.
- **Removed translation keys:** `invalid_cloud_credentials`,
  `cloud_rate_limited`, `cloud_ssl_certificate_error`, `cloud_auth_failed`
  and `cloud_unavailable` in the forms; `cloud_credentials_invalid`,
  `cloud_temporarily_unavailable`, `prime_login_rejected`,
  `prime_login_failed`, `prime_cannot_connect` and
  `prime_shadows_unavailable` in the error messages. One
  `cloud_<reason>` key per cause replaces them. The
  `prime_classic_analytics` setup step is gone.
- **`lifetime_hours()`** in `const.py` is the one reader of a robot's
  running hours; a test fails if anything else reads `bbrun.hr` or
  `runtimeStats.hr` directly.
- A map picture the cloud answers with nothing is now an error (502
  from the mission-map view) instead of an empty map.
- **CI takes about a quarter of the time**: uv instead of pip (same 143
  packages, same versions), the suite on every CPU, coverage measured
  in the HA 2026.8 / Python 3.14 job only.
