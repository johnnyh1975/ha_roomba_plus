# Roomba+ 4.1.0

**Rooms and zones now work the same way on both generations.** Four
bugs found in one week of field reports, all of them silent, and the
one control Prime robots were missing.

> **A note on the number.** 4.1 was going to be the async rewrite. It
> still is — it just moves to 4.2. This release adds entities, and new
> entities appearing in someone's installation is not what a patch
> release should do.

---

## 🐛 Four silent failures

Every one of these looked like nothing happening, which is also what
success looks like when a robot was already where you wanted it.

**📅 The calendar could not write a schedule on i/s/j robots.** It built
the LEGACY schedule object and wrote it under the MODERN key — an
object where the robot expects an array. Reading always worked, so
schedules were visible and simply never changed. Provable without a
robot in the end: feed a real entry through the writer and back through
this project's own parser and the count goes from one to zero.

The entry shape now follows the firmware's own validation — `type`,
`enabled`, `cmd`, and `start` with a day array — a write replaces the
whole list, so existing entries are carried through untouched, and
there is a 21-entry ceiling that now says so rather than losing the
surplus (@AlakazipLabs).

**🎯 A zone was cleaned as a room.** `clean_zone` routes through the
same code that cleans rooms, and that code sent every region as
`type: "rid"`. The robot's own command schema enumerates
`["rid", "zid", "wid", "tag"]`, and ids are numbered per map — so a
zone sent as a room very likely named a real but different region. The
Prime path was fixed when the service was first written; the Classic
one was not.

**🗺️ The zone button ignored your selection.** The comment above it read
*"prefer the active map's entity"*. The code required it. So a room
picked on a map the robot was not currently using was discarded, and
the button fell through to whatever ran last — @ScenicSystemsLLC
selected Hallway and his robot cleaned the Bedroom. It prefers now, as
it always said it did.

**🔤 `clean_room` did not know about rooms on other maps.** The name
list came from the active map only. That restriction was deliberate —
two maps sharing a room name would otherwise clean the wrong floor
silently — but it also meant a room existing only on another map could
not be named at all. Rooms from every map are in the list now, added
last, so a duplicate name still resolves to the active map exactly as
before.

## ✨ Prime gets the room selector Classic has had for years

`select.{name}_select_room_or_zone` and a companion clean button.
Rooms and zones in one list, across every map. Previously a Prime
dashboard needed an automation behind it to do what a Classic dashboard
did with two entities.

**One selector, not one per map.** Prime ids already carry their map, so
the list does not grow with the number of floors.

**And no active-map check**, deliberately. @ScenicSystemsLLC captured
the iRobot app sending a Classic robot to a room on an *inactive* map,
which it did without complaint — so there is nothing here to check for.
That capture also settled the question behind the button fix above.

## ⭐ `run_favorite` works on Classic robots

The favourite BUTTONS have worked there since v3.x, sending the stored
command verbatim. Only the service was scoped to Prime, so a Classic
household could press a favourite by hand and not from an automation.
There was no structural reason; it had simply never been extended.

Worth knowing what this buys: **a favourite carries its own map**, fixed
when it was created. So it reaches a room on a map the robot is not
currently using — which is the shortest route to the thing several
people have asked for. Make a favourite per room in the iRobot app and
each one becomes a button.
