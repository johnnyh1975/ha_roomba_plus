# Roomba+ v4.0.0a11

Consumable parts for V4/Prime robots, plus three sensor corrections from field reports.

## Consumable parts

Filter, brushes, mop pads and dirt disposal bag now appear as sensors — the same view the iRobot
app shows, including its own units: hours for the filter, routines for pads, evacuations for the
bag.

The data was always reachable; the integration simply never asked for it. Requested by a tester
who attached a screenshot of the app's own view, which made obvious that everything in it was
already within reach.

Some details worth knowing:

- **Sensors are created per part your robot actually reports**, not from a fixed list. A
  vacuum-only robot has no mop pads; one without a self-emptying base has no dirt bag. They also
  appear later if a part shows up mid-life — attaching a self-emptying base, for instance.
- **The unit comes from the server per part.** The same robot reports hours for one consumable and
  routines for another, so a single fixed unit would mislabel most of them.
- **No reset button yet.** The library's reset call takes no part argument and appears to reset
  *all* counters at once, with its request shape unverified. Someone replacing only a filter would
  lose their brush and pad counters irreversibly. Not shipping that until the behaviour is
  confirmed.

## "Returning to dock" no longer sticks — the real cause this time

A tester saw the vacuum status stay on "Returning to dock" while the robot sat on its dock. Two
earlier attempts corrected the state mapping and neither helped.

His diagnostics download settled it: the robot was reporting `phase: "charge"`, `cycle: "none"` —
data that maps cleanly to "docked". **The data had been right the whole time.** Nothing was asking
the entity to look at it again.

The vacuum entity reads its activity from the status coordinator, but only subscribed to the cloud
and mission-event ones. So it re-rendered whenever a mission event arrived, and never when the
phase changed — leaving a phase that settled to "charge" after the last event permanently
undisplayed.

Worth recording as a habit rather than just a fix: when the data is correct and the display is
not, the bug is in the subscription, not the logic. Both earlier attempts were in the wrong layer.

## Room cleaning now works on Prime robots

`roomba_plus.clean_room` — and the three services that build on it, `clean_overdue_rooms`,
`auto_clean_dirty_rooms` and `smart_start` — can now send a Prime robot to specific rooms by name.
The vacuum entity advertises the capability too, so it appears in the UI rather than only being
reachable by hand-writing a service call.

This had been blocked by a refusal whose stated reason was that region commands "have had zero
effect in two live field tests". That was true when written and is not any more: field testing
confirmed the transport works, and the actual blockers were a missing `initiator` field and two
wrong wire keys. A refusal justified by a finding is only as good as the finding.

What Prime robots get:

- **Rooms by name**, including accent-tolerant matching — "kuche" finds "Küche", which matters
  because accents are awkward on phone keyboards and absent from voice assistants entirely.
- **Two-pass cleaning per room**, and **suction level per room**, which the Classic payload has no
  equivalent for.
- **Multi-floor handling.** Rooms from every saved map are offered, so an automation works whether
  or not the robot is parked on that floor. Where a room name exists on more than one map, the one
  the robot is currently on wins — the same rule the Classic path has used for a long time.
- **A refusal rather than a guess** when the robot has several maps and is not reporting which one
  it is on. Choosing wrongly cleans the wrong floor.
- **The same "map is updating" check Classic has.** A robot rebuilding its map has region ids in
  flux, so a command sent now can target a room that no longer exists by the time it arrives.

Internally both generations now sit behind one interface, and `map_capability` — a Classic-only
concept that no Prime robot could ever satisfy — is no longer consulted for room cleaning
anywhere.

## Three sensor corrections

**"Schedule hold active" no longer displays as "Running / Not running."** It reports whether the
schedule is *paused*, so that label was the inverse of its meaning. A tester saw it showing "Off"
during a scheduled run — which was correct, but almost impossible to read that way.

**The mop-tank sensor no longer appears on robots without a tank.** It was created for any robot
that *can mop*; a Combo whose water lives in the Clean Base passed that test and got a sensor about
a tank it does not have. It now checks whether the robot reports the field at all — while an
explicit "no tank fitted" still produces a sensor, since that is a real answer.

**System uptime is documented as powered-on hours, not device age.** Confirmed by two testers whose
robots had wildly different downtime. On a robot unplugged for months the two differ by more
than half.

## Diagnostics

The download now includes consumable parts and a `push_freshness` block — the latter distinguishes
"quiet because nothing is happening" from "quiet because the connection died", which nothing
previously could.

## Robot discovery no longer offers robots it cannot set up

The local setup list now requires a **positive Classic match** rather than the absence of a Prime
one. Previously an SKU nobody recognised appeared in the list, looked like a valid choice, and then
failed at password retrieval with a message about the HOME button that had nothing to do with the
cause.

That filter was defensible while the Classic SKU table was patchy — it missed most of the retail
range, so excluding unknowns would have locked out working hardware. It no longer is: Classic is a
closed generation and its table now covers it, while Prime keeps gaining models. An unrecognised
SKU today is far more likely to be a new Prime robot.

**Nothing is excluded silently.** A robot that cannot be classified produces a log line saying what
to do now — use the iRobot-account setup, which is very likely to work.

## An unrecognised model asks to be reported, after setup succeeds

If account-based setup works for a robot whose SKU we do not recognise, the log offers a prefilled
GitHub issue.

The timing is deliberate. At discovery all that exists is an SKU string and a guess. Once setup has
succeeded it is a fact — account setup only works for a Prime-generation robot — and a diagnostics
download exists carrying the capability flags and shadow structure. That data is what makes a new
model worth reporting; every capability gap this project has found came from exactly it.

The issue is prefilled because "please open an issue" is a request most people decline, and those
who accept still have to work out what to include. The SKU identifies a product model, not a
person. The BLID is deliberately left out.

## Internal

Four fields removed from the runtime data object, left behind when v3.5.0 removed the Repair Issues
they fed. Two were never written again; two were recomputed on every cloud update — including a
median over ten mission records, in two separate places — for a consumer that had not existed for
two minor versions.
