# Roomba+ v4.0.0a28

Requires roombapy-prime **v0.2.0b14**.

Calendar schedules can be deleted and edited — which they could not before, on either generation, for
a reason nobody had noticed.

## Delete and edit were unreachable

Home Assistant passes an event's `uid` back when a user acts on it, and our calendar events had none.
So both handlers looked complete and could never be called.

It went unnoticed because **creating needs no uid**, and creating was the only direction anyone
exercised — the delete tests ran through the services rather than the calendar. A path nobody walked
looked like a path that worked.

Prime events now carry the schedule id, Classic events their weekday. That is the whole identity a
legacy schedule has.

## Classic robots can have their schedules written

Field-confirmed on a 900-series: the schedule was read, written back unchanged, read again identical,
and the iRobot app still showed it afterwards. That last step is the one that counts.

It was never a transport problem — `set_preference()` already writes `carpetBoost`, `childLock` and
`ecoCharge` the same way. What was missing was confirmation that the robot accepts the structure it
reports.

**The legacy format holds much less than Prime's**, and what it cannot express is refused rather than
approximated: one entry per weekday, no frequency, no rooms, no name. Approximating any of it would
put a robot on the floor at a time nobody chose.

Two keys exist across firmware generations, and the key the robot reports is the key it gets back —
writing under the wrong one would create a second, competing schedule.

## Schedules say what they will do, and listen when you say it

Calendar events now show the operating mode: `Cleaning (vacuum, then mop): Kitchen, Hallway`. The
iRobot app shows the same thing above its room list, and a schedule that mops is a different thing
from one that vacuums over the same rooms.

**And it reads the mode back out of what you type, in eight languages.** "Küche wischen", "aspiration
puis lavage", "stofzuigen dan dweilen" all land correctly. A word for "then" between the two verbs
means sequential; both verbs without one means simultaneous.

Recognised in eight languages, displayed in one — Home Assistant does not translate calendar
summaries, and reading only English would have been a step backwards from the room matcher, where the
names come from the robot and therefore work everywhere.

Saying nothing changes nothing: a schedule keeps whatever mode it had.

## A single-run schedule is drawn once

@DaRealGuGu created a one-off cleaning from the calendar. The robot stored it as `ONCE` and the iRobot
app showed it that way; Home Assistant painted it on every Thursday for the next two months.

The frequency check let `ONCE` through — correctly, the run exists — and the generator then repeated
it, because repeating is all it knows. It now draws exactly one, which is also what happens: the
server deletes a fired one within minutes.

## Time estimates, corrected against a real response

The library's model had been built from the app's simulator response and read a real one as empty
(see b14). Three consequences here:

- **Mission progress matches on region ids**, not room names. A room without a name — one of
  @DaRealGuGu's four has none — would otherwise have left the sensor permanently blank, because one
  unknown room discards the whole calculation.
- **The calendar picks the estimate for the mode the schedule actually runs.** Every region carries
  dozens, one per parameter combination, and the first is not the right one.
- **A whole-house schedule keeps the flat hour.** There is no whole-mission figure in the real
  response, and summing the rooms would be a different number from what the robot does.

## Four silent signature faults, found in one night of debug logging

Every one failed on **every** call, and every one produced output indistinguishable from having
nothing to report (@utkjmitch).

## The mission history call has never worked

```
TypeError: get_mission_history() missing 1 required positional argument: 'blid'
```

The sync then reported `imported 0 missions`, which reads exactly like a robot with no history.

The comment beside that call already documents the previous life of the same bug — a required `days`
argument that made every sync fail silently since the feature shipped. **Fixing that one moved the
TypeError up a line rather than ending it.** a27's ordering fix did its job; it is what exposed this.

Four sensors have been blank because of it: clean streak, last mission, last duration, area cleaned
today.

## The trail was never cleared, and the dock never observed

```
AttributeError: 'PrimeStatusCoordinator' object has no attribute '_trail_mission_id'
```

`_note_phase_for_timer` lives on `PrimeStatusCoordinator` and reads `self._trail_mission_id`, which
was only ever initialised in `PrimeCoordinator` — a different class it does not inherit from.

So the block raised on its first line, hourly, on every install. **Everything downstream never ran:**
the trail clearing rewritten in a27, the observed dock position added in a26, and the mission timer's
`on_phase_run`. Two releases of work that could not execute a single line.

## Calendar edits could not complete

```
TypeError: _container_lock() missing 1 required positional argument: 'container_id'
```

The lock is per container, and the container is not known until the schedule has been found — so the
read that finds it now happens first, and the lock is taken around the decision and the write, as the
service handlers already do.

Fixing it exposed a second one in the same function: an edit with no rooms set `rooms: None`, and the
key's presence is what triggers the room rewrite — so the resolver was asked to iterate nothing. The
create path had always only set it when non-empty.

The pattern is four for four: each was a DEBUG-swallowed exception whose visible symptom was
"nothing to report" -- no history, no save button, no progress, no cleared trail. All four are
**structural**: they fail on every call, not occasionally. A `raise` on first occurrence would have
surfaced each of these the day it shipped.

- A guard that had been failing quietly since calendar editing was first built now has its exception
  recorded.
