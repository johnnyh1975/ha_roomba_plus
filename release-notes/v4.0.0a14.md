# Roomba+ v4.0.0a14

Prime robots gain a proper room map, thirty sensors that were empty since v4.0.0a0, schedule and
setting switches — and a device tracker fix for a Home Assistant deprecation.

## Prime room map

A second map entity alongside the existing one, built with the Classic renderer: room polygons with
rotating fill colours, and the room names exposed as attributes for the
xiaomi-vacuum-map-card — the same shape a Classic card configuration expects, so one config works
for both.

Both maps stay. iRobot's own image shows where the robot actually cleaned; this one shows the floor
plan. Different information.

It is also available immediately rather than after the first mission: Prime robots receive finished
room polygons from the cloud, where Classic robots have to infer them from where they have driven.

xiaomi-vacuum-map-card calibration works too. Anchored on the map's bounding box rather than the
dock origin — for a robot docked in a corner, which is where people put them, the dock maps outside
the image and corrupts the card's transform. Classic learned that in v2.7.2 and it would have
reproduced here exactly.

## Thirty sensors that were empty

Every persistent store was left unset for Prime since v4.0.0a0, so around 30 sensor lookups read
from nothing while the data sat available over REST. Now wired:

- **Mission history** — last mission, result, duration, clean streak, anomaly count. Translated
  from the cloud's own history rather than accumulated from events.
- **Maintenance dates** — filter, brush, pad and battery last replaced. These record when the USER
  changed a part, so they were never generation-specific; only the store was missing.
- **Mission progress** — elapsed time and remaining estimate, driven by phase transitions.
- **Long-term statistics** — daily cleaned area, duration and completion count are backfilled, so a
  statistics graph shows history instead of starting from today.

## Schedule switches

One switch per schedule on the robot, so an automation can disable just the weekday routine.
Writing schedules was field-confirmed twice and has sat unwired since; this is that wiring.

Read-modify-write, because the endpoint takes the complete schedule list — sending only the changed
one would delete the rest.

## Setting switches

Child lock, eco charging, two-pass cleaning and extra suction. All four are confirmed writable and
read-back on real hardware; child lock additionally has an audible confirmed effect.

`schedHold` is deliberately absent: it writes and reads back successfully and the robot ignores it
entirely. A switch the robot accepts and does nothing about would make the UI state something
false.

## Device tracker: room and area as attributes

`location_name` stops working in Home Assistant Core 2027.7 (thank you @mdarocha, #54). The room
moves to state attributes, and gains something on the way:

- `room` — what the robot calls it
- `area_id` — the Home Assistant **area**, resolved through the segment mapping configured for
  Clean Area, falling back to a name match

`area_id` is the one worth automating on: it survives a room being renamed in the iRobot app and is
stable across languages. HA zones were not an option — they are geographic, and creating one per
room would misuse the concept.

**And the tracker now runs for Prime robots too**, with the room taken from the mission timeline's
room events. Not from the mission planner: that only knows the rooms when Home Assistant started the
mission, so a robot cleaning on its own schedule — the common case — would have reported nothing.

### If you automate on the tracker's STATE, please read this

The entity's state still shows the room name, and Home Assistant stops supporting that mechanism in
**Core 2027.7**. There is about a year, and nothing breaks today.

What to change when you get to it:

```yaml
# before
condition: state
entity_id: device_tracker.roomba
state: "Kitchen"

# after
condition: template
value_template: "{{ state_attr('device_tracker.roomba', 'area_id') == 'kitchen' }}"
```

`attributes.room` carries the same string the state does, if you prefer a direct swap. `area_id` is
the better target: it does not change when you rename a room in the iRobot app.

The property will be removed in a release before 2027.7 rather than on the deadline, with a repair
notification rather than only a release note.

## Pins the first beta of the Prime library

roombapy-prime reaches **0.2.0b1**. The virtual-wall write path is confirmed on two independent
accounts, including a full round trip — written, read back on the new map version unchanged,
written again. That was the last item outstanding before the library could leave alpha.

No behaviour change from that: the library's code is identical to the alpha this release would
otherwise have pinned. The version number now says what testers have actually been running.

## Saved favorites, three ways

Prime robots keep saved routines — "clean the kitchen and hall on deep, twice". All three routes
below run the same favorites; which you use depends on what you are building.

- **A button per favorite.** Needs no setup, works with voice assistants. On by default, and there
  is now an option to turn them off — fifteen favorites means fifteen entities, and someone driving
  everything from automations does not need them.
- **A `favorites` attribute** on the vacuum entity, with IDs and names. Costs no entity, and covers
  what buttons cannot: automations that iterate, templates, and the xiaomi-vacuum-map-card's menu,
  which reads attributes.
- **A `run_favorite` action**, taking the favorite's ID.

The ID matters. A favorite's name is what you typed in the iRobot app and can change there at any
time — an automation keyed on the name breaks silently when it does, and a name is all a button or
a dropdown could ever offer.

## Buttons: locate

`find` is the one simple command confirmed for Prime. Classic's evacuate, power off, spot clean and
map training have no identified Prime equivalent, so they are absent rather than present and
non-functional.

## Suction level

A select entity with the three levels the robot actually reports — light, normal and deep, taken
from per-room defaults captured on two accounts. It also lights up the xiaomi-vacuum-map-card's
menu icons, which read a select's options.

Pad wetness is deliberately not offered. It is three separate values (one per pad type) with
separate lookup tables per type, so a control writing one level across all three would be wrong for
at least one of them — and the robot would accept it silently.

## Per-room cleaning preferences

The vacuum's room map now exposes `room_preferences`: the profile, suction level, two-pass and
scrub settings you configured per room in the iRobot app.

Read only, on purpose. A service that wrote these would discard a preference you set by hand, with
no way back. Reading them lets an automation honour what you configured rather than override it.

## Diagnostics: shadow contents

Diagnostics used to list which robot shadows had been loaded and nothing about what was in them.
They now dump the contents of all nine, with identifying fields (MAC, serials, household ids)
redacted at every depth.

This is not a cosmetic change. Several open questions — what a populated pad-wetness block looks
like, what the audio settings contain — have been unanswerable for months because the answer was
only reachable by a tester typing key names out by hand.

## Rooms without names

Two real map captures on the same day differed: one carried room names — "Salon", "Bureau",
"Couloir" — and the other carried none at all. Same firmware family, same endpoint.

A room without a name rendered as a blank label on the map and an unnamed entry in the card's room
list, which reads as a bug rather than as missing data. It falls back to `Room <id>` now, which at
least identifies the room and matches what the cleaning services accept.

## Favorites, three ways

Saved favorites — the routines you build in the iRobot app — are now reachable from Home Assistant:

- **One button per favorite**, which needs no setup and works with voice assistants
- **A `favorites` attribute** on the vacuum entity, listing id and name, for automations that
  iterate and for the xiaomi-vacuum-map-card's menu, which reads attributes
- **A `run_favorite` action** taking the favorite's **ID**

The ID matters. A favorite's name is whatever you typed in the iRobot app and can change there; an
automation keyed on the name breaks silently when it does. The ID does not change, and a button or a
dropdown could only ever offer the name.

The buttons can be switched off in the options if you have many favorites and drive everything from
automations — the attribute and the action cover that case entirely.

## Suction level, and a locate button

Suction level is a select with the profile names the app uses: light, normal, deep. Those values come
from real captures on two accounts rather than from guessing at a range.

Locate is the one simple command with a confirmed Prime equivalent. Evacuate, power off, spot clean
and map training are absent rather than non-functional — no command has been identified for them, and
a button that does nothing when pressed is worse than one that is not there.

Pad wetness is deliberately **not** offered. It turns out `padPlate` has its own value table, separate
from the other pad types, so a control writing one level across all three would be wrong for at least
one of them — silently, because the robot would accept it.

## The room map shows where the robot has driven

A live trail on the rooms map, from the position stream. Confirmed possible by a tester's
diagnostics: 904 position points across 451 messages in a single mission — the open question was
whether Prime reports enough positions to draw a path or only enough to place a dot.

Jumps over 500 mm are dropped, the same guard the Classic renderer has used since v2 — without it a
relocalisation draws a straight line across the whole home. The trail clears when a new mission
starts, but survives a pause.

## Room preferences, read-only

Each room's `room_preferences` — profile, suction, two-pass, carpet boost — as set in the iRobot app,
exposed as a map attribute. An automation can now honour what you configured per room rather than
override it.

Read-only on purpose: the robot already stores these, set by hand, and a service writing them would
discard that with no way back.

## Consumable sensors update when a mission ends

They come from a REST poll every six hours, and the counters only move when the robot cleans. So a
mission that finished at 06:08 showed unchanged filter and brush hours until the next poll —
@chairstacker saw his four maintenance sensors update at 12:14, when he restarted Home Assistant,
and nothing at all at six o'clock.

The mission timeline reports when a mission concludes, so that is now the trigger. Polling faster
would have been the wrong fix: a cloud request every few minutes for values that change twice a day.

Specifically on `fin`, not `evac` — @chairstacker's own timeline shows evac at 06:08:37 and fin at
06:08:56, and a self-emptying base can empty mid-mission with the robot carrying on afterwards.

## Fixed

- **The map is written once per mission, not once per frame.** The previous release saved on every
  frame — roughly 17 MB per mission and 6 GB a year, on hardware that is commonly an SD card, when
  only the last frame is ever read back.
- **Uninstalling deletes the stored map.** A new store had been added without a removal entry,
  leaving a file behind containing a picture of the user's home.
- **Mission records are persisted.** They were held in memory only, so every restart lost them and
  re-fetched from the cloud — which looked like it worked until a mission aged out of the endpoint's
  window.
- **Pending map and timer writes are flushed on unload**, so a reload cannot have the old instance's
  delayed write land after the new one loaded.
- **Room ids carry their map.** Ids are assigned per map, so two floors both have a room "1" —
  picking a downstairs room while the robot sat upstairs cleaned upstairs, silently.
- **`push_freshness` no longer claims a fault where there is none.** Shadow updates arrive on
  change, and a robot parked on a full battery changes little.

## Diagnostics

Now reports whether the **robot** is connected to iRobot's cloud, whether the login carries a token
expiry, and the state of each store. An offline robot and a broken push stream look identical from
outside and need opposite responses.
