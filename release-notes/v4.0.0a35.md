# Roomba+ 4.0.0a35

Requires **roombapy-prime 0.3.0b6**, pinned automatically.

Eight fixes, and most of them are things testers reported that turned out to be
worse than the report. Three entities that could not be managed, three room
names that vanished, a switch that has never worked on one robot, and a table
of values this project invented.

## The favourite button was never registered

@chairstacker chased this for three rounds. His favourite appeared in Home
Assistant as **"Unmanageable"** — no rename, no hiding, no area assignment, no
reliable reference from an automation.

Twice I told him it was a leftover registry entry from a deleted favourite.
His last report ruled that out completely: the entity **tracks his favourites
exactly** — it appears when he creates one, updates when he adds another, and
disappears when he deletes one. A stale entry does none of those things.

`PrimeFavoriteButton` set no `unique_id`. Home Assistant will not register an
entity without one, so it lives in the state machine and never reaches the
registry. It was never stale; it was never registered.

@ratpic83's log carried the other half from a different robot on the same day:
*"attempts to attach a device to an entity without a unique ID"*. Two testers,
two symptoms, one missing line.

A test now walks every Prime entity class and fails if one ships without an id.

## Favourites appear and disappear on their own now

The list was read once, at entry setup, and nothing refreshed it. So a
favourite created in the iRobot app never got a button until you reloaded, and
a deleted one left its button behind forever.

Both halves are fixed: the list refreshes on the schedule cycle, and buttons
follow it. That is @DaRealGuGu's schedule-switch problem from a19/a20 in a
different entity type, and it reuses the same two lessons — match on the id,
and read the registry rather than a list of what this session happened to add.

**Favourites have no push channel.** All nine named shadows were checked and
none carries them: they are a cloud resource, and the robot never learns that
one changed. Six hours is too long for a favourite you just created; reloading
the entry still re-reads immediately.

## Room names came back

The Prime map split gave the Rooms Map plain outlines, on the reasoning that
xiaomi-vacuum-map-card draws its own room overlay. Right for the **fills**.

Carrying it to the **labels** disabled an explicit user option on exactly the
entity the code's own comment says the option exists for: *"a plain
picture-entity shows an image and nothing else, so for them the names have to
be in the picture or they do not exist."*

@chairstacker: *"no room shading colors and no names at all (even room names
are gone)"*. The shading is deliberate. The names were not.

## Zones have names now too

Two testers reported this independently and neither was answered.
@connormxy: *"the zones seem to lack a name but have a number"*.
@chairstacker: *"zone names are missing, though — just as they are in the
Whole_House map"*, i.e. on both his maps, so not a multi-map problem.

`CleanZoneFeatureProperties` carries `name` — it is the one field
distinguishing a saved clean zone from an ad-hoc one. Nothing read it: the name
lookup read the `rooms` layer and stopped there, so every zone fell through to
`Zone {id}` in the calendar, in room lists and on the map.

That lookup had already been fixed once for exactly this symptom, on the rooms
side.

## Three option labels this project made up

`pwReturn` carries two ranges in one field. The lower three are `evRoom`,
`byTime`, `byArea`. The upper three the vendor calls `mission`, `refill` and
`refillAndRoom` — and this integration labelled them **standard / medium /
high**, as though a three-value range had to be a scale.

@ratpic83 opened that select beside a dock reporting `pw: 3`, read the three
labels, and reported that the heat levels were present and confirmed. Then he
went into the app, found no heat control anywhere, and **retracted his own
correct observation as "noise"**. The noise was ours.

A wrong value gets rejected by the robot. A wrong label gets believed. The
value guard compared value sets only and passed this every time; it now checks
that our option strings are recognisably the vendor's words.

## A capability table that was 70% invented

Five product modes get narrower option lists than the enums declare. The table
implementing that was written from the research report's **prose** rather than
from `v3_sku_value_lists.json`, which was in the same package.

Seven of its ten entries were wrong: pad-dry overrides invented for three SKUs,
an interval override invented for a fourth, and a real `autoevacFreq` narrowing
missed entirely. The tests agreed with the invented version.

A test now reads the vendor file directly and compares, so the table cannot
drift from it again.

## Settings switches follow key presence

`available` on a setting switch is "the robot reported a value", so a switch
whose key the robot does not report is created and then permanently
unavailable. @ratpic83's **`prime_vac_high` has been in that state since
setup**: his `cap.suctionLvl` is 4 so the capability gate passes, and `vacHigh`
is simply not among his rw-settings keys.

The selects have used key presence since a33. A capability says what the
hardware can do; the key set says what *this* robot lets you configure, and
@utkjmitch's robot showed the two disagreeing months ago.

## The device name flipped 72 times an hour

@ratpic83 found this from the far end: `friendly_name` alternating between his
robot's name and `Roomba 6099` across every entity at once, four times in an
hour, each flip dropping every connected websocket client with *"4096 pending
messages"* — a wall-mounted tablet and two browser sessions together, which is
what ruled out a slow client.

Two sources for one name. `roomba_reported_state()` returns `{}` on a Prime
entry by design, so the rename helper fell through to a BLID-derived fallback
and overwrote the name the device info had just set — from every entity's
`async_added_to_hass`.

On Prime there is nothing to resolve: the name is decided once, at config entry
level.

## Also

- **A third phase category.** `padWash`, `padDry` and `refill` were in neither
  the cleaning set nor the ending set, and this project had been asking testers
  which they belonged to. The answer was in the research package:
  `isCleanDockTask` names all three as a **dock task** — neither cleaning nor an
  ending. The phase sensor now carries `dock_task` as an attribute. A combo
  robot washing its pad mid-mission is not "cleaning" by this rule, and an
  automation gating on that deserves to know why.
- **Pad wetness control** (`padWetness.padPlate`), gated on `cap.ppWetLvl` —
  which is `0` on @ratpic83's 405 and `3` on @chairstacker's. Same robot model,
  different dock, and the first robot that should not get the control.
- **`sensor.*_job_initiator` on Prime**, which never existed. Prime reports
  `cleanMissionStatus.initiator` exactly as Classic does, so the nineteen
  labels added in a34 were readable on one generation only. The last command
  is an attribute rather than a second entity — "Started by" and "Last command
  by" side by side would be two names one letter apart in meaning.
- **Quiet hours read the endpoint they are written to.** The sensor read the
  schedule container while `set_quiet_hours` writes to `/settings/dnd`, so a
  successful write could leave the sensor unmoved.
- **Mission progress is documented as an estimate.** It is elapsed time against
  a rolling mean whenever there is no planned room order, and it caps at 99
  because "finished" is a phase transition rather than a percentage.
  @ratpic83 watched it climb at 1% a minute while `area_cleaned_today` stayed
  at 0.0 m².
- **A data-privacy page.** What a diagnostics download contains, what is
  removed, and — the part that matters — what is **not**: room names,
  schedules, map geometry and mission history all stay, because the download is
  useless without them. Schedules describe when a home is likely empty, and
  @ratpic83's map name was the name of his town.

## Upgrading

Nothing changes an entity ID or an action's arguments. The favourite buttons
will be **registered for the first time**, so they become manageable — you can
now rename them, hide them, and assign them to areas.
