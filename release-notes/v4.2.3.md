# Roomba+ 4.2.3

Two room-tracking faults, both found by testers watching their robots
rather than reading their logs.

## The room display ran one room ahead

The first drive of a mission goes from the dock to the first room.
Ending that drive means **arriving**, not leaving — but it was being
counted as a room change, so the display moved on before the first room
had been touched.

One tester watched it read "Corridor" while his robot was cleaning the
Bathroom, then "Living Room" once it reached the Corridor — wrong by
exactly one room for the whole mission (@Thonno).

There was a guard meant to stop this: a drive ending within a minute of
entering a room was treated as repositioning. That measured the wrong
thing, because the clock includes the drive itself. One tester's dock
departure took 12 seconds and was caught; another's took longer and was
not.

**A drive is now only a boundary if the robot actually worked in the
room behind it.** The robot reports when it is vacuuming or mopping, and
before it has done either there is nothing to advance away from.

## A list of rooms passed from a template was refused

Passing several rooms to `clean_room` from an automation variable
failed with "Unknown room(s)" — naming rooms that were listed as known
in the very same message.

`room_name: '{{ room_list }}'` renders the template to text, and a list
rendered to text is its printed form: one string with brackets and
quotes in it, where several names were meant. No robot has a room by
that name.

The template is not wrong. Quoting a template in YAML is how they are
written, and most survive as native types. This one does not, and it
now arrives as the list it was meant to be. Both `clean_room` and
`clean_zone` take names this way, so both handle it.

Reported three times across as many releases, each time correctly
insisting the rooms existed (@mrsnyds).

## Cleaning a second map could stay broken after the fix

4.2.2 stopped sending a map id paired with another map's version. For
anyone who had already hit it, nothing changed — and the reason is worth
writing down.

The robot **records** a start command it then refuses to act on: it
writes it down, reports a localisation failure, and stays on the dock.
We read that record back as "the version the robot last accepted". So
the bad value we sent once was stored by the robot and handed back to us
on every retry.

A command that ended in a localisation failure is no longer treated as a
source of truth.

**If you are stuck on this**, one cleaning started from the iRobot app
on the affected map clears it on any version: the app writes a good
record, and we read that instead.

## Two Roomba integrations no longer fail in silence

Home Assistant installs integration dependencies into one shared
environment. Roomba+ needs `roombapy` 2.x; the built-in **Roomba**
integration expects 1.x. Only one copy gets installed, so one of the two
stops loading — with nothing but an `ImportError` in the log to show for
it, and nothing anywhere connecting that to having two integrations for
the same robots.

Neither integration can fix this; it is a property of the platform. What
Roomba+ can do is say so, and now does: setting up alongside the
built-in one raises a repair notice explaining the choice.

Not offered as a one-click fix, because both answers are reasonable —
somebody running only older robots may well prefer the built-in one.

## Favourites now appear on Classic robots too

The `favorites` attribute listed only Prime robots' favourites, and a
comment beside it claimed Classic had no equivalent. It does: they are
fetched from the cloud, they run, and they already appeared as buttons.
Only this attribute did not read them — so automations that iterate,
templates that list, and the map-card menu got nothing on Classic.

## A zone can be cleaned by its name

`clean_room` refused a zone name as an unknown room. The room/zone
distinction is an internal one — from outside it is a named area you
want cleaned, and the selector and buttons have always treated it that
way.

Zones now resolve by name on both robot generations, carrying the
marker that tells the robot to treat them as a zone rather than a room.
That marker is the real protection: a zone sent as a *room* is what
made one tester's mission finish in 71 seconds having cleaned nothing.
Excluding zones fixed that symptom; naming them properly fixes the
cause.

## Diagnostics

Downloads now list the **version each map carries**, not just which maps
exist. A start command pairs a map with that map's version, and the two
faults above both came down to that pairing being wrong — diagnosing it
meant inferring the pairing rather than reading it.
