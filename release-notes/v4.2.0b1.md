# Roomba+ 4.2.0b1 — the Classic library goes async

**A beta with no new features.** Everything it changes is underneath: how
each command reaches a Classic robot. If it works, you will not notice
anything at all — which is exactly why it needs testing before it becomes
a release.

> 4.2 was going to be this work all along. 4.1 took the number that was
> reserved for it, because 4.1 added entities and that is not a patch.

---

## What changed

Roomba+ now uses **roombapy 2.0.1**, the async rewrite of the library it
has used since the beginning. The old one was synchronous, driven from a
worker thread, so every command travelled through Home Assistant's
executor — **46 call sites of it**. Those are now plain `await`.

Nothing about what the robot does should differ. The command that reaches
it is byte-for-byte the one that reached it before.

**What did NOT move into the event loop:** map rendering, UMF alignment
and the backup ZIPs. Those compute rather than wait, and 20 executor
calls remain for them deliberately — putting them in the loop would
freeze every other integration in the house while a map is drawn.

## Two settings are gone from the options form

roombapy 2.x keeps one supervised connection and reconnects on its own.
It has no polling mode, so **Continuous connection** and **Connection
delay** no longer exist.

**If you had continuous connection turned OFF**, your robot now keeps a
persistent connection anyway. That is what the option's own description
recommended, and for nearly everyone it is an improvement — but it is a
change to a setting you chose, so it is written to your log once at
startup. The stored values stay in your config entry, unread; downgrading
to 4.1.0 brings the form back with them intact.

## The last Platinum rule is met

`async-dependency` sat at `todo` with a measurement against it: the
pinned roombapy 1.9.1 defined 61 functions and **zero** `async def`. The
new pin defines 18, including `connect`, `disconnect`, `send_command` and
`set_preference`.

It is `done` now, and checked rather than claimed — a test asserts both
that the library really exposes those coroutines and that none of them is
being run in a worker thread. **41 of 41.**

## What this beta needs from you

This is the hard part of testing a rewrite: **when it works, nothing
looks different.** A break would show up somewhere specific rather than
everywhere, so poking at particular things beats using it normally for a
week.

Worth trying once each, on whatever robots you have:

- **Start, pause, stop, dock, locate** — the five verbs
- **Clean a room, and clean a zone** — different code path from the verbs
- **Press a favourite button**
- **Change a setting** — cleaning passes, suction, edge cleaning, child
  lock: anything with a switch or dropdown
- **Create or move a cleaning in the calendar**
- **Reload the integration**, and restart Home Assistant once

Each of those is one or more of the 46 converted call sites. A command
that silently does nothing is the failure mode to watch for — the robot
not moving, with no error anywhere.

**Also worth a look in your log** at startup: if it mentions the
persistent connection having been off, that setting is the one described
above.

## Everything from 4.1.1

The three selector fixes and the two room-name fixes are all here:
the zone selector loading its list, `zid_` surviving the segment
decoder, zones sorted by name, region names resolving across every map,
and zones read from a map's `zones` list rather than only its `regions`.
See the 4.1.1 notes for what each one was.

## Also in this release

**CI tests versions you can actually have.** One job pinned Home
Assistant 2025.1.4 on Python 3.12 — a combination no installation can be
in, since this integration's own minimum of 2025.5 requires Python
3.13.2. It now runs 2025.5 on 3.13, alongside the existing 2026.8 on
3.14. The migration forced the issue: roombapy 2.x could not be installed
in the old environment at all.

**Two new guards, both written after a real mistake in this work.** One
fails the build if a roombapy coroutine is handed to the executor — a
mistake neither mypy nor the tests can see, and one that had 46 instances
mid-migration while all 6,197 tests passed. The other checks every
attribute read off the robot client against the real class, which caught
two renamed attributes that would have raised on a live robot.

**The test suite lost 13 files and gained a test.** Consolidating them
turned up a class that had been shadowed by another of the same name for
months, and so had never run.
