# Roomba+ 4.0.0a40

**Upgrade from a39 immediately if you have Classic robots.** a39 breaks
the cloud coordinator on every refresh, taking favourite buttons and
room maps down with it.

Requires roombapy-prime 0.3.0b9, which comes with the HACS update.

## a39 broke the cloud coordinator

@ScenicSystemsLLC, three robots, every cycle:

```
ValueError: dictionary update sequence element #0 has length 31; 2 is required
```

a39's typing pass annotated `get_mission_history()` as
`dict[str, Any]` and wrapped the response in `dict()` to match. The
endpoint returns a **list** of mission records — and the caller two
screens away checks `isinstance(raw_history, list)`. The real shape was
documented in the code that reads it, and the annotation won over the
code.

Same shape as a38's `last_seen_segments`: satisfying the type checker
instead of answering the question it asked.

**The damage was larger than the failing fetch.** Favourites and pmaps
are fetched first and succeed; the ValueError escaped the handler
(which catches CloudApiError, ClientError and TimeoutError) and killed
the coroutine before it could return. Python returns nothing from a
raising function, so both were discarded every cycle. Favourite buttons
went unavailable and every room map went blank.

His second point was the one that mattered: **one failing sub-fetch
should not discard the rest.** The automations fetch already had that
treatment, commented "fails gracefully". History did not. It does now —
while still letting network errors reach the outer handler, where they
become the grace period that keeps the last good data.

## Repair issues were never cleared

Also his. A stale `smart_zones_need_naming` survived a rollback and a
reinstall, pointing at zones that were already named.

Home Assistant keeps issues in its own registry, so nothing about
unloading or removing an integration clears them. Cleared on unload
now — both the per-entry ids and the singletons without one.

## Mission results never matched

@chairstacker's `clean_streak` and `area_cleaned_today` both read 0 on
a robot with 128 stored missions.

The `done_code` translation table contained `success`, `completed`,
`failed`, `aborted` — plausible English words matching nothing a robot
sends. Every one of his missions became "unknown", which no sensor
counts.

Rewritten against the values confirmed from app 3.0.0, which are
abbreviated camelCase. A second bug surfaced fixing it: the lookup
called `.lower()` on the code, invisible while the table was
all-lowercase and fatal once it was not.

## Area sensors ignored your unit system

Also his. They declared square metres and converted correctly but
carried no `device_class`, so Home Assistant had nothing telling it
this was an area. Imperial setups will read square feet now.

The iRobot account's "Metric Units" switch stays irrelevant: it is not
in the data we receive, and a vendor setting should not override a Home
Assistant preference.

## Zone names appear

Zone names live in `lastCommand.regions[].region_name`, not in the map.
@chairstacker's zones report `name=None` from every map source while
his app labels them "Guest Access Zone" and "Living Room @Wall" —
both readings correct, different fields.

Missing map names are filled from the last command now. Nothing is
written anywhere.

## Calendar entries can be edited

Three separate causes, all from @chairstacker's #71:

- **The summary went nowhere.** The update function took a `name`
  parameter and never put it in the payload.
- **The weekday could not change.** Existing days are preserved unless
  an explicit recurrence names others — right, but nothing ever passed
  explicit days, so preservation was the only path. `BYDAY` is read on
  edits now.
- **Rooms typed into Location were ignored**, and an unmatched name
  silently inherited another schedule's target, which is why every
  event he created came back as "Cleaning: Kitchen". An unmatched name
  is refused now, and **zones are in the name list** alongside rooms.

## Also

- **The device tracker reports rooms**, and refetches names when its
  cache is empty — the list is fetched once at setup, before the map
  bundle usually exists.
- **Mission progress reads 100% on a completed run** rather than
  freezing wherever the estimate had it. A stopped mission still keeps
  what it reached.
- **Diagnostics carry a mission record**, not just a count, and
  `room_preferences` works — it read `config_entry.hass`, an attribute
  ConfigEntry does not have, so every download ever taken returned
  `{"note": "no hass on this entry"}`.

## After two bad releases

a38 and a39 each broke a working system, both from the same typing
work, both narrowings at a boundary with someone else's code.

Everything changed since a37 has now been compared: 45 cast wrappers,
55 return types (**zero narrowings**), 5 new attributes, 4 signatures.
Nothing else of that shape is findable statically — but both that got
through needed a running system to surface, and @ScenicSystemsLLC and
@utkjmitch found them within hours of each release.
