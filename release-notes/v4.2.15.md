# Roomba+ 4.2.15

## No carpet boost control on robots without carpet boost

An i7 showed a **Carpet boost** select that could not be changed. Every
choice snapped back to *eco*, the service call reported success and
nothing was logged (@azrael-229).

**Why.** The robot reports the settings `carpetBoost` and `vacHigh`, but
it has no carpet boost and ignores a write to them. Roomba+ offered the
control whenever those two settings were present and the robot's
capability list did not mention carpet boost. That is exactly the case
on robots without it: iRobot's own sample states show the setting on the
i7, j7, j9 and even the Braava jet m6, and declare carpet boost as 1
only on the s9. An i3 was measured dropping both writes earlier.

Now the robot's capability list decides: carpet boost is offered when
the robot declares it (`cap.carpetBoost` is 1), as the 980 and the s9
do. A robot that reports no capability list at all keeps the old rule.

On robots without carpet boost:

- the **Carpet boost** select and the **Setting – Carpet boost** sensor
  are removed. They are removed only when the robot has reported its
  capability list; without one nothing is removed
- the vacuum no longer offers fan speeds, which wrote the same two
  settings

## A room the robot only reached into is not a cleaned room

In a closed-door test (door verified shut), the cloud reported the room
behind the door as finished, with 4 of its 106 sq ft cleaned: the
doorway strip. Room history counted it as cleaned (@FJSoninC).

A room event now counts as a cleaned room only when it covered at least
**10 %** of the room's floor, whatever its status. In the same mission
the office had 97 of 160 sq ft (61 %); real cleans stay well below
100 % because of furniture, so the line is set low. It separates
"reached into the room" from "cleaned it". An event that carries no
area figures is judged as before.

This applies to room history, the stored list of cleaned rooms, the
cleaned rooms in the last mission summary and the overdue rooms.

**When no room counts, that is the answer.** A mission sent only to the
closed room has one room event, below the line. Its list of cleaned
rooms is now empty. Until now an empty result fell back to the rooms
room tracking saw during the mission, which would have brought the
closed room back. A mission whose timeline lists no room events at all,
such as a whole-home clean, still keeps the tracked rooms.

The covered share itself is not hidden: `room_coverage` (below) still
shows the bathroom at 0.038, so a retry rule can use it.

## Room coverage in the mission list

The REST mission list (`/api/roomba_plus/<entry>/mission_history?format=records`) had a
`room_coverage` field on every row, and it was always null: it read a
value nothing ever wrote (@FJSoninC).

It now carries the covered share of each room with a finished pass,
0.0 to 1.0, from the mission's own room events, for example
`{"Office": 0.606, "Bathroom": 0.038}`. Rooms are named from the map the
mission ran on. The shares are the same figures as the `room_coverage`
attribute of the last mission summary; on an account with several maps
the summary names rooms from the active map instead.

## No false room-cleaning warning on a 900- or 600-series

At every start, a Roomba 980 logged that room cleaning was not offered
and that iRobot credentials or smart zones would make rooms available.
The credentials were there and working, and neither would help: a robot
that keeps no map between missions cannot be sent to a single room.

That robot now gets a debug line instead of a warning. In the
diagnostics download, `withheld_features` gives the reason
`no_persistent_map` instead of `no_room_data`.

Whether a robot keeps maps is read from its capability list (`cap.pmaps`,
or more than one `cap.maps`), not from Roomba+'s own map setting. An i7
with the map option turned off is still warned about, as before, and so
is any robot with a smart map but no room list.

## A recorded mission shows up at once

After a mission was recorded, the vacuum's **last cleaned rooms**
attribute kept showing an earlier mission's rooms until the robot's next
status message; a robot that has just docked sends few
(@ScenicSystemsLLC's Braava, a five-room run shown as one room from the
day before). 4.2.14 fixed this for the cloud's room events; a mission
recorded by Roomba+ itself now also updates every entity of the robot
straight away.

## Room times learned from every mission, per cleaning mode

A Braava m6's five-room mop run showed 99 % progress after an hour of a
two and a half hour clean (@ScenicSystemsLLC). The figures behind
mission progress, the current room and the time left come from how long
each room takes, and a Braava gave Roomba+ none:

- the cloud's own per-room estimates are filed by one or two passes,
  a setting Braava commands do not carry
- room tracking measures a room when it sees the robot move to the
  next, and a Braava sends no travel signal

So the estimate fell back to the average length of all recent missions,
whatever the number of rooms.

**Room times now come from the cloud's room events, after every
mission**, on every Classic robot with an iRobot account. Each room
event says when the robot started on that room; the next room or drive
says when it finished. Several passes over one room add up.

- Only a room with a finished pass counts, and not one the robot only
  reached into (below the 10 % line)
- A mission that got stuck, failed, was cancelled or was paused teaches
  nothing: the waiting would count into whatever room it happened in
- Each mission is learned once, however often the cloud lists it; the
  history already stored is learned from at startup
- With an account, room tracking no longer adds its own live
  measurement as well, which put two samples of one visit into the
  same average

**Per cleaning mode.** Measurements have been kept per mode since 4.1,
but the estimate took the shortest of them, so on a Combo a vacuum time
could stand in for a mop run. The estimate now uses the mission's own
mode first: vacuum, mop or both, read from what the robot reports
(a Braava always mops). A room measured only in another mode still falls
back to that figure. Measurements stored by earlier versions are read
by the same modes and averaged in.

**A room without a figure gets a typical room** of this robot, in the
same mode, instead of the whole-mission average, once at least one room
has been measured.

**The current room never goes backwards.** With room times for every
room, the current room follows the clock on more robots than before. It
still may run ahead of room tracking, as it could before, but it no
longer shows a room the robot has been seen to leave.

## Rooms guessed without a room signal wait for the cloud

A robot that reports neither its position nor when it drives between
rooms (a Braava) leaves room tracking to the clock. The rooms it
recorded were a guess: after a five-room run that ended with the robot
stranded, two rooms were recorded and neither was confirmed by anything.

When such a robot has an iRobot account and the mission planned more
than one room, the record now claims no rooms until the cloud's room
events arrive, usually minutes later. Room history, the last mission
summary and the vacuum's last cleaned rooms follow the cloud's answer.

- The guess is kept beside the record (`tracked_rooms`, with
  `rooms_source: awaiting_cloud`)
- If the cloud reports the mission without any room events, the guess
  is used straight away (`rooms_source: tracked`)
- If the cloud never reports the mission, the guess is used after a day
- Without an account, or for a robot that does report its drives,
  nothing changes

## Naming Smart Map zones without an iRobot account

On a robot without an iRobot account, Roomba+ asks you to name the
rooms and zones it finds in your schedules. The dialog had two problems
(@liblit):

- **Six empty boxes, no labels.** There is one field per zone, and the
  zone's ID was meant to be its label. Home Assistant shows no label for
  such a field, so nothing said which box was which zone. The ID is now
  shown inside each field.
- **It sent you to a black image.** To find out which zone is which, the
  text pointed to the rooms map. That map draws room shapes from the
  iRobot account, and this notice only appears on robots without one,
  so the map was always empty. The text now explains what works instead:
  - start one room or zone on its own from the iRobot app, then look at
    `smart_map` → `last_command_summary` → `region_ids` in the
    diagnostics download
  - or add the iRobot account to the robot (Configure → iRobot cloud
    credentials). Roomba+ then takes every name from the account, and the
    notice goes away

The text also no longer asks for `id=Name` lines, which only the version
with a single text box (more than 15 zones) still uses.

## The rooms map says why it is empty

When there is no room layout to draw, the **Rooms map** image showed a
plain dark square. It now says why: that the layout comes from the
iRobot account and where to add it, or that Roomba+ is still waiting for
it from the iRobot cloud.

## Correction: why #183 failed

The 4.2.13 and 4.2.14 notes said that on the robot in #183 the active
map version was made by a user, and that the version Roomba+ sent was
an edit that never became active. @cburrell16's diagnostics from 4.2.14
show otherwise: the version sent in 4.2.12 (260913T011853) is the active
one and was made by the robot, and his user version is 250610T143229.
So #183 was the same case as the j7+ and the two S9+. The behaviour of
4.2.14 is unaffected, and it is confirmed on his robot.

## Under the hood

**CI takes about a quarter of the time.** Measured locally with 2 CPUs,
the coverage run went from 212 s to 58 s.

- **Dependencies are installed with uv instead of pip.** The packages
  are the same: all 143 at identical versions, checked side by side. A
  cold install takes 19 s instead of 113 s.
- **The suite runs on every CPU of the runner** (`pytest -n auto`).
- **Coverage is measured in the HA 2026.8 / Python 3.14 job only.**
  There coverage.py uses `sys.monitoring`, so branch coverage costs about
  10 % instead of doubling the run. The per-module 95 % gate moved with
  it; every module is above 95 % on both HA versions.
- **The guard tests parse each source file once instead of about 18
  times.** A check at the end of each run fails it if a test changed a
  shared tree. It found one test that did, and that test was fixed.
- **Collection on HA 2025.5 takes 10 s instead of 25 s.** pytest-asyncio
  0.26 checked every fixture again before each test, and now only checks
  newly added fixtures.
- **The hand-made test stubs get one storage folder per process**, so
  parallel workers do not share files.
