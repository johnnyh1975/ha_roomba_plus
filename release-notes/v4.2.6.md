# Roomba+ 4.2.6

Room tracking on a robot in auto pass mode.

## The display stayed on the first room for the whole mission

4.2.4 removed the six-second drive floor that was rejecting real room
crossings, and that part worked. But the crossing it correctly spotted
was never confirmed, because the flag meaning "the robot worked in this
room" was read, reset — and never actually set. The route that no longer
needs a time estimate could not be reached at all.

Reported with the debug log that shows the crossing being spotted and
then dropped, on the fourth run of the same two rooms
(@ScenicSystemsLLC).

## Cloud-connected robots track rooms from their own reports

A cloud-connected robot tells Roomba+ which room it has moved to, with
more precision than a locally connected one — and all of that was going
into an automation event and nowhere else. The room display could only
move by comparing elapsed time against an estimate, which is the route
that fails in auto pass mode.

It now follows the robot's own report, the same way the locally
connected path does.

## Your robot now learns how long its own rooms take

Per-room time estimates come from the iRobot cloud, and in auto pass
mode there are none — the robot decides how many passes to make while it
runs, so there is nothing to estimate in advance. Roomba+ then fell back
to a whole-house average divided by the number of rooms in the mission,
which on a two-room clean meant expecting nearly six hours per room.

Roomba+ measures how long each room actually takes, and it was throwing
that figure away the moment the room finished. It is now kept and used,
so the second mission through a room already has a real number. A cloud
estimate still wins where one exists.

## Zone names in the room tracker

A zone showed as "Room 101" instead of the name you gave it. Zone ids
carry a type marker that the name lookup did not know about, so every
zone fell through to a number (@chairstacker).

## The cleaning mode dropdown is now used

On cloud-connected robots the Cleaning mode control was read by nothing
— the robot cleaned in whatever mode it was already in, whatever the
control showed. Locally connected robots had the same gap when cleaning
a zone rather than a room.

## Diagnostics show which map version the robot is on

Roomba+ reads this from the cloud to draw your map and never recorded
it, so a diagnostics download could not show it. Its absence was
repeatedly mistaken for the robot not reporting a map at all.

## Zones are drawn on the map

Zone outlines and names were missing entirely. The map entity kept an
empty list of zone shapes and never filled it from the floor plan,
though the floor plan had them all along. Zones now appear with their
names, in a lighter colour than room labels since a zone sits inside a
room.

## Ticking an entity option now takes effect

"Separate sensor per room and zone" and the blocking sensors option are
read when the integration starts, so switching one on saved the setting
and created nothing until the next restart. Saving now reloads the
entry, as it already did for the schedule calendar.

## "Follow the robot" works while the robot is parked

A cloud-connected robot reports which map it is on while it is
navigating, and reports nothing once it is docked — which is exactly
when you are picking a room. So "follow the robot" offered every map
and narrowed nothing, and choosing a map by hand was the only setting
that did anything.

It now falls back to the map the robot last cleaned, which is where it
is standing unless you carried it. A command that ended in a
localisation failure is not used for this: that is evidence of where
the robot is not.

## Rooms were sent to the wrong map when two maps share a region number

If your robot has two maps and a room number exists on both, the room
took its name from one map and its map assignment from the other. The
command then went out with the right room number, the wrong map, and
that map's version — which the robot answers with a localisation
failure.

It looked intermittent because it depended on which rooms you picked: a
name unique to the active map worked, one whose number was reused on the
other map did not. The same room could succeed one day and fail the
next.

Found by reproducing the failure deliberately and capturing the
diagnostics on the spot, after four wrong theories of mine (@Thonno).

## Cloud failures at startup now say what went wrong

If the first cloud fetch failed when Home Assistant started, the log
said so and nothing else — a rate limit, a DNS failure while the network
was still coming up, and a rejected login all produced the same
sentence. Two separate incidents have been argued about without anyone
knowing which it was.

The reason is now in the message, with a full traceback at debug level.

The same message also promised a retry without saying when. The cloud is
polled once a day, so that retry could be 24 hours away — which reads as
never. It now says so, and points at reloading the entry as the way to
get rooms back immediately (@ScenicSystemsLLC).
