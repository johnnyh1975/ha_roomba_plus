# Roomba+ v4.0.0a25

Requires roombapy-prime **v0.2.0b13**.

Four sensors that read "unknown" on every Prime robot now have data behind them, and the robot
marker points the right way.

## Clean streak, last mission, last duration, area cleaned today

All four read a mission store that only the Classic path ever filled. On a Prime robot they read
"unknown" forever — reported as four separate faults (@DaRealGuGu), and they were one.

The fix uses the same endpoint Classic uses, `GET /v1/{blid}/missionhistory`, and the shape is
settled rather than assumed: the app's own restservices package returns a bare `List<MissionHistory>`
with no envelope class in 63 files, and every field of the vendor's own 20-entry sample maps onto
the parsed entry. That sample is now a test fixture, so the mapping is checked against real data
rather than against fixtures we invented.

Imported once at setup, in the background. The history grows when a mission ends, and these four
sensors are summaries rather than live values — polling would be a cloud request per interval for
something that changes a few times a week. Ids are built from robot id and mission number, so a
restart re-imports without duplicating.

**Duration means time cleaning, not wall clock.** Four minute fields exist and are not
interchangeable: a robot that returns to charge halfway through reports a wall-clock figure several
times its actual cleaning time.

## The robot marker points forwards

The library added half a turn to the heading, undocumented, with a test that asserted the addition
rather than checking it. It survived because nobody could see it — the marker was never drawn, so
the angle it was drawn at was never visibly wrong. The first observation came the day the marker
started appearing (@DaRealGuGu, 505).

## Schedules stop reading "On" long after the robot has finished

A schedule says when it starts and never how long it takes, so every calendar occurrence was given
a flat hour. @chairstacker ran a scheduled mission that finished in minutes and watched the entity
stay "On" for the rest of the hour.

Two things changed. Occurrences now use the robot's **own** time estimates — the sum for a schedule
naming rooms, the mission figure for one cleaning everywhere. And a running occurrence ends when the
robot is demonstrably resting, whatever the estimate said: a prediction is about the future, a robot
on its dock is about the present.

The flat hour remains the fallback. Poorly-rated estimates are excluded rather than shown, because a
percentage built on one looks exactly as authoritative as a good one.

## Mission progress works on Prime

Same source. It divides elapsed time by per-room estimates, and on Prime it had none.

## The trail clears between missions

Clearing was gated on catching a shadow update while the robot was actually cleaning, and a Prime
robot may only push `ro-currentstate` around the edges of a run. @chairstacker ended up with four
missions' trails on one map and could only clear it by reloading. It now acts on the mission number
changing, whatever the phase.

## Also

- **The three schedule services have descriptions and field forms.** They worked from a24, but
  Developer Tools showed them bare (@utkjmitch).
- **`ONCE` schedules are confirmed to clean themselves up** — the server removes a fired one within
  minutes, and a cancelled mission still consumes it (@utkjmitch). No spent entries to collect.
