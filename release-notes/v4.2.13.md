# Roomba+ 4.2.13

## Room cleaning sends the map version the robot uses

On a Classic i-series with one Smart Map, every room clean failed. The
robot accepted the command, reported *Smart Map localization failed*
(error 224) and stayed on the dock, and each attempt added to the
failed-missions count. App favourites for the same rooms worked every
time (@cburrell16, #183).

A room command carries the map's id and a version of that map. Roomba+
sent `260913T011853`; the iRobot app and the favourites sent
`250610T143229`.

**Where the wrong one came from.** iRobot's cloud keeps several versions
per map: the active one, and the last one a user made. Roomba+ meant to
read the active one first, but looked for it under a key that no record
we have seen contains. It therefore always took the last user version,
which is harmless while the two agree, as they did on every account we
had data from. After an edit that never became active they differ, and
the robot cannot localise against the newer one. The active version is
now read first.

**One answer for every way of starting a room.** Four features build a
room command, and they looked the version up in three different orders:

- **Clean room** and **Clean area** asked the cloud, but only for the
  active map
- **Send command** with regions and **Repeat last mission** never asked
  the cloud. They used the robot's own map list, which reports the
  version the robot is still working on, not the one it uses

All four now use the same lookup:

1. the cloud's active version of the map being cleaned, whichever map
   that is
2. otherwise, the version the robot last accepted for that map
3. otherwise, the newest version stored in a schedule or favourite for
   that map
4. only then the robot's own map list

Step 3 is new. Before, the robot's own list came right after the last
command, and any dock, stop or whole-house start replaces the last
command.

**On a robot with more than one map**, room commands for a map that is
not the active one now also get that map's version from the cloud.
Before, they used the robot's own list.

## Missions closed by the safety check are recorded again

When a mission ends without the robot saying so clearly, a check every
30 seconds closes it. Since 4.2.11, a mission closed this way was never
recorded, so it was missing from mission history and statistics. The log
showed *Task was destroyed but it is pending* and
*coroutine 'async_record_mission' was never awaited* (two missions on one
i7+ in a single day).

**Why.** Home Assistant runs a timer's function on its event loop only
when the function is marked for it; otherwise the function runs in a
worker thread. The check was not marked. Until 4.2.10 that did no harm,
because the code it ran handed its work back to the loop itself. 4.2.11
removed those hand-overs, because robot messages now arrive on the loop.
The check was the one caller that still came from a thread. It also ran
the whole mission tracking from that thread, alongside the robot's
messages on the loop.

The check runs on the loop now. The same mistake was in the per-room
sensors of Prime robots, which added new sensors from a worker thread
when room names arrived. A test now checks every timer, event and signal
handler in the integration for this.

## Diagnostics show every map version

The diagnostics download listed the cloud's maps and their owners, but
not their versions, so a report like #183 could not be checked against
the right version. It now includes:

- every version field of every cloud map, with its processing state
- the version each favourite carries
- the version a room command would carry right now, per map

## Under the hood

- The cloud's map picture (UMF) is fetched for the same version a room
  command carries, so the geometry shown matches the map the robot
  localises against
- The room sensors' 30-second refresh was also started from a worker
  thread. That was harmless, but it now runs on the loop too, so the new
  test needs no exceptions
- A comment in the smart-zone picker said the smart-zone button looks
  up a map version. That button sends none, deliberately, and the
  comment now says so
