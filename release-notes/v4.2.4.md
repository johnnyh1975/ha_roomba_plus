# Roomba+ 4.2.4

The live room display, rebuilt around what the robot reports rather
than what we predicted it would do. Plus two service fixes and a
security-hygiene change.

## The room display

Three separate things stopped it, each found by a tester watching their
robot rather than reading a log.

**A drive is a room change only if the robot worked in the room behind
it.** The first drive of a mission goes dock → first room, and ending
it means arriving, not leaving. That was counted as a room change, so
the display moved on before the first room had been touched — reading
"Corridor" while the robot cleaned the Bathroom, and staying one room
ahead for the whole mission (@Thonno).

**A drive's length says nothing about whether it crossed a room
boundary.** There was a six-second floor: shorter drives counted as
repositioning inside one room. One tester's real crossing took 3.8
seconds and was thrown away, while his 17-second drive off the dock was
accepted — both decisions wrong, in one mission (@ScenicSystemsLLC).
Another tester's drives ran 12 seconds, 69 seconds and 11.3 minutes
(@AlakazipLabs).

**And a missing time estimate could block a room change the robot had
already reported.** The check asked for a per-room time estimate before
it would accept anything. Where the cloud offered none, it fell back to
a whole-house mission average divided by the rooms in that mission —
10.7 hours on one robot, so a threshold no real mission could cross.

Estimates now refine the decision instead of gating it. Where one is
genuinely needed, the shortest estimate the cloud offers for that room
is used, and confident estimates are remembered so a day when the cloud
returns none is not a day the display stops working.

## Rooms and zones

**A zone can be cleaned by its name.** The room/zone distinction is
internal; from outside it is a named area. Zone names now resolve
through `clean_room` on both robot generations, carrying the marker
that tells the robot to treat them as a zone (@theChef613).

**A list of rooms from a template works.** `room_name: '{{ room_list }}'`
was arriving as one string with brackets in it. Comma-separated names
work too (@mrsnyds).

## A healthy side brush reported as thousands of hours overdue

On a robot whose iRobot account does not serve parts data, the side
brush and the Clean Base bag had no starting point recorded — so
`maintenance_due` counted the robot's **entire lifetime** against a
150-hour threshold. One tester's 980 reported a perfectly good side
brush as 2102 hours overdue, and there was no way to clear it from
inside Home Assistant: no reset service for those two parts, and the
reset button only exists when the cloud serves them.

Both now get a starting point on first setup, exactly as the filter and
main brush already did. Where the cloud does supply parts data, it still
wins — the local starting point is only a fallback.

Found, diagnosed and fixed in a live install by @azrael-129, including
the reason no test had caught it.

**And the smaller half of that report turned out to be the larger one.**
Those starting points were set once, during startup, from the robot's
reported state. When Home Assistant starts before the robot has sent
anything — which is common — there were no hours to record, and nothing
tried again afterwards. On such a system *no* part ever got a starting
point, filter and main brush included. They are now set on the first
message that carries the robot's hours, whenever that arrives.

## Rooms and zones now take the same options

`clean_room` offered two-pass cleaning; `clean_zone` offered smart
scrub and pad wetness. Only cleaning mode was on both — and that one
was being refused outright on zones, with an error naming a field the
interface itself had offered.

All four are available on both services now. There was never a
technical reason for the split: both reach the robot the same way
(@theChef613).

## Rooms from a map your robot is not on are no longer offered

If your robot has more than one map, Roomba+ listed every room from
every map in one flat list. Pick one from a map the robot is not
standing on and it cannot localise: it accepts the command, fails, and
stays on the dock reporting a localisation error. One tester hit that
three releases running, with the robot on its own dock — his second map
is his father's house, where the robot used to live.

The list now follows the robot: the map it reports standing on, or an
explicit choice where the map selector exists. A robot that reports no
location still sees everything, as before, and a single-map robot is
unaffected.

## Four maintenance items had no way to be reset

The pad, the wheels, the charging contacts and the bin could all be
marked as done in the code — and nothing could reach it. Each was
advertised as a service that had never been registered, so calling it
returned "service not found", and there was no button either.

All four now have a button, alongside the filter, brush and battery
ones. The seven phantom services are gone from the documentation, and a
build check now compares what the interface offers against what the
services actually accept.

## Also

- Two Roomba integrations installed at once now raise a repair notice
  instead of failing with an unexplained `ImportError`
- Favourites appear on Classic robots, not only Prime
- Diagnostics show the version each map carries, and how far the live
  position chain has got
