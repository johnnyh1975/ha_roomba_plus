# Roomba+ 4.0.0a38

Requires **roombapy-prime 0.3.0b8**, which comes with the HACS update —
nothing to install by hand.

Almost all of this release is invisible. It is the result of running a
type checker over the integration for the first time, and the useful
part is not the type annotations.

## Eleven bugs, none of them from a field report

**Three services could never be invoked.** `clean_sequence`,
`create_backup` and `restore_backup` took `(hass, call)` as arguments;
Home Assistant calls service handlers with the `ServiceCall` alone. Any
attempt to run them raised `TypeError` before reaching a single line of
their own code. The eleven handlers that work read `hass` from
`call.hass`.

**Three whole-house start paths were dead on Classic robots.**
`smart_start`, the blocking-sensor manager and the dirt-index fallback
all called `roomba.start` — an attribute `roombapy.Roomba` does not
have. It exposes `send_command`, which is what the vacuum entity's own
start action has always used.

**The vacuum crashed on every cloud refresh.** `_handle_coordinator_update`
read `last_seen_segments` and called `async_create_segments_issue`.
Neither exists — not in `StateVacuumEntity`, not in this integration.
Both are now real, and the segment-remap warning they were meant to
raise is implemented, in all eight languages.

**A coverage pass died on its first line.** `MissionStore.records` is a
property; one caller wrote `ms.records()`. A Sequence is not callable,
so `_async_update_gs_smart_coverage` raised `TypeError` every time it
ran.

**The zones-need-naming prompt never appeared.** It was created through
`homeassistant.components.repairs`, which has no `async_create_issue` —
that lives in `helpers.issue_registry`, where every other repair issue
in this integration gets it from.

**Presence scheduling crashed on Prime.** The arrival handler read the
local robot's state to decide whether to re-freeze schedules, before
the branch that would have protected it. A Prime entry has no local
robot, so a Prime user with presence scheduling enabled got an
`AttributeError` the first time somebody came home.

**Two room-cleaning methods existed only on the Prime backend.** The
rooms image, the calendar and the dirt manager all called them through
the base type. On Classic: `AttributeError`, two of them inside a bare
`except` that swallowed it.

**A store lost its tuning on a failed load.** `RoomSegStore` reset
itself by calling `self.__init__()`, which takes `min_distance_cells`
and `merge_ratio` as parameters with defaults — so a store built with
non-default tuning silently reverted the first time a stored payload
failed to parse.

**Two wrong types cancelling each other out** in the stuck-hotspot
pattern detector, and a stale tuple declaration in the calendar that had
been four fields behind the parser it reads from.

## The pattern underneath

In five of these, a **test fixture supplied what the real class was
missing**: setting `.start` on a mock, setting `records.return_value`,
setting `last_seen_segments` on the entity by hand. The test created the
precondition production did not have, so the suite passed against the
bug it existed to catch.

That is worth knowing about any test suite, including this one.

## Also in this release

**@jouwdan's PR #88.** The Rooms Map publishes each room's id and
xiaomi-vacuum-map-card sends it back on a tap — but room resolution only
matched names and slugs, so a card selection resolved to nothing. The
card he made work in an earlier PR could draw rooms and not clean them.
Bare region ids now match, and ambiguous ones across multiple maps are
refused rather than guessed: cleaning a room on the wrong floor is worse
than an honest miss.

Also from #88: the vacuum's `status` attribute read `None` on every
Prime robot. It now falls back to the activity derived from the mission
phase.

**mypy runs in CI.** `--strict`, no disabled error codes, no exemptions
for this integration's own code. The two that remain are for Home
Assistant itself and are explained where they are declared.

## Five from @chairstacker, filed the same evening

**The device tracker always said "Docked."** It read the phase from the
local robot, and a Prime entry has none — so the phase was always empty,
the docked branch always matched, and the Prime room lookup right below
it was unreachable. It reads the `ro-currentstate` shadow now, and will
report room names while cleaning.

**Calendar entries landed a day early.** `datetime.weekday()` counts
from Monday; the robot's wire format counts from Sunday. The raw value
was handed straight over, so a Monday entry became Sunday — in Home
Assistant *and* in the iRobot app, because it really was written wrong.

Third time this conversion has gone wrong here: schedule *edits* shifted
one day the other way on a30, from a second table that counted from
Monday. That table was fixed; this call site was still feeding it the
wrong basis. Four tests now pin both ends.

**Area sensors ignored your unit system.** They declared square metres
and converted correctly, but carried no `device_class` — so Home
Assistant had nothing telling it this was an area and displayed the
native unit regardless. With `SensorDeviceClass.AREA` set, HA converts
to whatever your system is.

The iRobot account's "Metric Units" switch stays irrelevant, and should:
it is not in the data we receive, and a vendor setting should not
override a Home Assistant preference.

**Mission progress dropped to Unknown at the end of a run.** The last
figure is held until a new mission id appears, so a completed clean ends
at its final value instead of a gap, and an aborted one keeps whatever
it reached.

**A room typed into a calendar event's Location was ignored.** Rooms are
matched by text across the event's fields — and `location`, the one
field a calendar UI labels for "where", was the one field never read.

## Two from @utkjmitch

**The dock status sensor read "unknown" on a dock that reports nothing.**
He has reported this since a32. His dock block is the whole of
`{"fwVer": "", "known": false, "error": 0}` — no `state`, no `cap`.
@chairstacker's, for contrast, carries
`{"cap": {...}, "state": 301, "pdState": 701, "known": true}`.

That comparison answers a question he had left open: he asked whether
another robot carries a `cap` where his carries nothing, because that
would mean `known: false` is about **identity** rather than capability.
It does, and it is — his dock is mute rather than passive; the robot
does not recognise it, so it reports no capability fields at all.

The sensor was right to have nothing to say. It now says which nothing.

**The part id space is per-SKU.** His robot numbers the same three parts
149 / 69 / 68 where the table already held 148 / 71 / 72. Both sets are
listed now, and the fallback that shows a bare id is doing real work
rather than covering a gap: a part labelled with an invented name is
worse than one labelled with a number its owner can quote at iRobot
support.

He named his by reading the app's robot-health screen beside the ids,
and flagged 68 — reached by elimination — as the weakest of the three
himself.

## Upgrading

Normal HACS update. If you have more than one Prime robot you may see
fewer favourite buttons than before — that was fixed in a37, and the
ones that disappear belonged to your other robot.
