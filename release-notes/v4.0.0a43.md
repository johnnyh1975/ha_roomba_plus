# Roomba+ 4.0.0a43

Requires roombapy-prime 0.3.0b14, which comes with the HACS update.

A note on the pin: a42 shipped still pinned to **b11**, two library
versions behind its own release. Nothing broke, but the fixes in b12
never reached anyone. The pin is checked in CI now.

## Two maps, and neither of them was the one you meant

@dduff617, S9+, four Smart Maps. His room-cleaning history showed
correctly named rooms next to raw ids — `"2"`, `"5"` — for rooms the
iRobot app named without difficulty.

He traced it himself, correctly. `cloud_coordinator.regions` filters to
the **active** map, deliberately, so a room *command* cannot go to the
wrong floor. But every historical record was resolved against that same
dictionary, so a mission run on another map had no entry and its ids
survived unresolved.

The distinction that fixes it: **naming a past mission's rooms is not
the same question as deciding where to send the robot now.** Each record
now resolves against its own map, with the active map as fallback for
records that carry none.

Two more places had the same fault, which he did not report but which
share the resolver: **rooms-overdue** counted an unresolved id as its
own never-cleaned room (so permanently overdue), and **visit counts**
split one room's visits across two entries.

Nothing is rewritten and there is no migration — the fix changes how
stored data is *read*, so existing history gets its correct names on the
next read.

## clean_zone refused to run on a two-map robot

@chairstacker, `zone_id: 101`, and: *"This robot has 2 maps and is not
currently reporting which one it is on."* Mid-mission too.

The map lookup reads `cleanMissionStatus.p2mapId`, which his robot does
not fill. But **a zone belongs to exactly one map**, and that was
already known — so the map is derivable from the ids you gave, with no
need for the robot to volunteer it. Zones spanning two maps are still
refused, because there is no honest single answer.

## The calendar could not change a weekday

Three releases, two correct fixes, no visible difference. Both repaired
the *handling* of a day Home Assistant never sent.

The events carried no recurrence rule, so HA treated each occurrence as
a one-off and showed no recurrence fields at all. There was nothing
wrong with how the weekday was processed; **there was no way to state
one.** Events now carry `FREQ=WEEKLY;BYDAY=…`, on both generations —
and the Classic edit path reads BYDAY too, which it did not before.

## Two map images had the same name

@pk-1966 asked what three map entities show. The answer was more
awkward than expected: `image.map` and `image.cleaning_map` were **both
called "Cleaning map"**, in seven of eight locales. He had not confused
anything; he used the name the interface gave him.

- Cleaning path · Coverage **heatmap** · Live cleaning map · Room map

"Coverage" alone reads as *how much is done*; it means traffic. A guard
test found a second collision on the way: Spanish called the dust bin
and the water tank the same thing — on Combo robots that have both.

## Favourites reported zero while the cloud said six

Same download, same account. Not a favourites bug: **both diagnostics
paths read a Prime-only field**, which is permanently empty on a Classic
robot. The buttons were fine; the report was looking in the wrong place.
It now names which tier answered, and for Classic reports three numbers
instead of one.

## New for Prime

Prime had none of the room-level sensors Classic has had for a while.

- **Room cleaning history** and **rooms overdue** — one entity each,
  same shape as Classic. Zones as well as rooms, so there is more to
  fall behind.
- **A "last cleaned" entity per room and zone**, off by default and
  available on **both** generations under Settings. @chairstacker asked
  for these; @dduff617's four maps are why they are opt-in.
- **`roomba_plus_room_completed` fires on Prime.** It has existed for
  Classic all along and came from a Classic-only code path.
- **Pad drying is a switch**, alongside the start/stop buttons rather
  than replacing them. The dock reports whether it is drying, so the
  switch shows what is happening rather than what was last pressed.

## Smaller

- **`clean_zone` takes a cleaning mode** — vacuum, mop, both, or
  vacuum-then-mop. `clean_room` has had this all along; the zone
  service simply never passed it on.
- **Blocking sensors accept `input_boolean`**, plus `schedule`,
  `person` and `device_tracker`. The check always read plain states and
  never cared about the domain — only the picker was limited. A house
  in vacation mode can now block a mission.

## The live map on 900-series robots

A long thread of small decisions turned out to rest on one borrowed
number. `MAX_POSE_JUMP_MM = 500` came from another project; the comment
justifying it cited ~300 mm/s and updates every 1–5 seconds, which is up
to 1500 mm. Measured on a real 980, poses arrive about every 1.8 s — so
full-speed straight-line driving covers up to **542 mm** against a 500 mm
limit. Ordinary movement sat just over the threshold.

Rejecting a pose left the previous one as the comparison anchor, so
every later real position measured against a stale point. A mid-mission
checkpoint in a 106 m² home once had 1413 points stranded inside a
0.7 m × 0.7 m pocket. Everything built afterwards — a rejection streak,
a reconnect two updates later — was working around that.

**Nothing is discarded any more.** A suspicious pose is kept and the
*line* breaks instead. The anchor stays current, so the cascade cannot
form. A discontinuity now shows as a visible gap rather than a straight
line across a room nobody drove.

**The threshold measures itself.** Both terms come from the robot's own
stream: the message interval from the median of recent gaps, the speed
ceiling from a high percentile of observed steps. Both use a robust
statistic on purpose — an average would be dragged upward by exactly
the stalls and jumps it exists to catch, and would then wave the next
one through.

### Coverage had holes, and they were at the doorways

Disk stamps were placed only where poses landed. At 542 mm apart with a
170 mm footprint that leaves ~200 mm of floor between them — floor the
robot demonstrably drove over, recorded as never visited. Those gaps
concentrate on long straight runs, and a gap in a threshold reads as a
wall to the room finder.

Stamping now follows the path between poses, and stops at a
discontinuity: a jump means the robot was elsewhere, not that it drove
the line between.

### Rooms appeared too early, then changed

Room detection ran after a single mission — the sparsest map the robot
will ever produce, and the worst case for this kind of algorithm. On one
real archive: 7 rooms after one mission, 6 after four, 5 once coverage
settled. Two of the seven were never rooms.

Detection now waits for three **completed** missions. A run that ended
early has no perimeter pass, so its edges sit further from the real
walls; counting it would defeat the point of waiting.

### Room outlines were never drawn

The canvas auto-fits to the pose trail, but a room outline is drawn
*outside* the covered cells — it suggests where the wall is. So it fell
off the canvas essentially always, and since a dashed rectangle draws
only its edges, nothing of it survived. A real room produced a frame
byte-identical to no room at all.

### Being carried is not drift

The dock correction assumed error grows gradually. Set a robot down two
metres away and every pose after that is off by the same two metres —
the first as much as the last, so a gradual ramp drags points that were
still accurate. `bbrun.nPicks` already recorded the lift; the map never
asked.

A mission can also break more than once, and the dock only verifies the
stretch that ends at the dock. Earlier stretches are now left alone
rather than corrected on evidence that does not cover them.

### Coverage from before a break can now be placed

Those earlier stretches were being written into the accumulated map at
unverified positions — permanently and invisibly. They are now matched
against known coverage by sliding and turning the pattern until it fits,
and **dropped if the fit is not clear**. A segment's cells are worth
little; the next mission re-drives them. A wrongly placed segment folds
the map onto itself and nothing repairs it.

## Three sensors that changed only when the robot did

"Area cleaned today" kept yesterday's figure past midnight, and a reload
cleared it. That pairing was the whole diagnosis: the calculation reads
today's date on every call and was never wrong — nothing called it. The
value comes from the mission store, written at mission end, so between
the last run of one day and the first of the next there is no event to
recompute on. Midnight is not an event here.

Looking for anything else with that shape found two more, neither of
which anyone would have reported:

**Clean streak** stayed at 13 after thirteen daily missions and a day
off, then jumped to 1 the moment the next mission ended — so the break
it exists to show was never on screen. It now drops to 0 when the day
rolls over. The meaning is unchanged: not having cleaned *yet* today
does not break a streak, a whole day missed does.

**Battery age in days** was off by one from every midnight until some
unrelated state write happened to correct it. Quietly wrong, with a
plausible number.

All three now recompute at local midnight — one scheduled callback
rather than a per-minute tick, which would have meant 1,440
recomputations a day to catch one moment.

A check written after the first report was supposed to catch this class.
It matched value functions with "today" in the name, so it passed while
two sensors sat there with the same fault and neither had "today"
anywhere. It now looks for functions that read the current date, which
is the actual cause rather than a naming habit.
