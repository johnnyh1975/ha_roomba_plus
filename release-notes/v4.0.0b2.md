# Roomba+ 4.0.0b2

Requires roombapy-prime 0.3.0, unchanged from b1.

One fix, and a check for the shape of mistake it belongs to.

## `no_contact` never fired on a Prime robot

It shipped in a46 and could not work. The silence check read
`coordinator.last_message_ts` — an attribute neither coordinator has.
What both of them write, and what diagnostics, the binary sensors and
the Classic version of this same check all read, is
`runtime_data.last_mqtt_message_ts`.

`getattr` returned `None`, a type guard added for safety turned that
into "never stale", and the feature was silently inert on one
generation while working on the other.

Found by **@utkjmitch**, who upgraded specifically to see his silent
robot report `no_contact`, got `stuck`, and read the source instead of
filing "doesn't work".

## The check that would have caught it

`scripts/check_runtime_data_reads.py` fails the build when code reads
an attribute off runtime data that the class does not declare.

`getattr(x, "phantom", None)` returns None and execution continues.
A default value is not a licence to invent an attribute — it is what
makes an invented one invisible.

This is the third instance of that shape in a week: a bundle read with
`getattr` on a dict, a dock field read under the wrong name, and this.
The second one shipped in the same release as a guard script written
for the family and a release-notes section naming five members of it.
That guard checks which *object* is read; this one checks whether the
*attribute* exists.

## Known and not fixed

A robot that fell silent before Home Assistant started has no message
timestamp at all, so the silence check cannot fire and the last known
phase reads as fresh after every restart. @utkjmitch's robot is exactly
this case.

The connection state does survive a restart and could decide it. That
would change behaviour for every robot in the first minute after
startup, so it is a decision rather than a patch, and there is now a
test asserting the current behaviour so that changing it has to be
deliberate.

## Documented

**A paused mission expires after ninety minutes.** The robot sets
`expireTm` to now plus 5400 seconds when you pause, and drops the
mission when it runs out — resuming afterwards does nothing, because
there is nothing left to resume. It also drains about 0.3% battery per
minute while paused.

The sensor for it already existed; what nobody knew was what the value
means on a paused mission. Measured by @Young9898, who is running his
own MQTT client against a dedicated i3+ and has been sending
protocol-level findings all week.

# 🗺️ The 980's own map, gone over with real data

Four diagnostics downloads of one running mission — 22, 138, 401 and
1069 trajectory points — from an R980040 with 445 lifetime missions.
The first time this pipeline has been checked against a live robot
rather than stored archives.

## Lifetime area was wrong by a factor of 100

`bbrun.sqft` is not square feet. It counts in units of 100 ft².

That robot reports `sqft: 1947` over 450 operating hours — **0.40 m² per
hour** read literally. A 980 cleans 30–60. The time counters on the same
robot are consistent (445 missions × 77 min average = 571 h against 450
reported), so the fault was in the area field alone.

With the factor: 40.2 m²/h. dorita980's own README example, a different
robot, gives 22.6 the same way and 0.23 without.

Not protocol-proven — the official app does not read this field at all,
so it documents no unit. Two field observations and one prior
implementation. Applied because the uncorrected value has no reading
under which it is true, and a lifetime sensor showing 181 m² after 450
hours is wrong in a way anyone can see.

## A third of the room list was stale

12 rooms totalling **8814 cells** against a grid of 6614. Sixteen
overlapping bounding boxes. Two doors at identical coordinates
connecting different room pairs.

`confidence` is `recompute_count / 10`, so the history is readable:
four rooms had been **re-recognised zero times** since they were
created, 931 cells between them.

The cleanup asked whether 80% of a room's cells were absorbed by
**matched** rooms. When those cells had scattered across clusters that
were themselves new, nothing absorbed 80%, and the room survived
forever.

Segmentation is handed the whole cumulative visited grid, not one
mission's slice — so a room that fails to match was **not unobserved**.
Its cells were in the input and the segmentation divided them
differently. Refuted, not unseen. Absorption is now measured against
everything the recompute produced.

## Two things that read like faults and are not

**The room list does not update during a mission.** Segmentation runs
after completed missions; rooms derived from one pass over-segment
badly. Diagnostics now report `grid_cells_now` beside
`last_cell_count`, so a stale-by-design listing is distinguishable from
a stuck one.

**`clean_area` withheld with "no room data" while a dozen rooms are
listed.** Those are different lists: coverage-derived rooms are for
display and cannot be cleaned individually. The explanation now says
so.

## And the cell size stays at 150 mm

A general recommendation said 50. This robot's own data says otherwise:
median pose spacing **148 mm** across both samples, robot radius 170 mm
giving a 340 mm track, and a stamping step of `max(radius, cell/2)` that
is 170 mm at either size. At 50 mm the same 202 densified points produce
175 cells instead of 117 — more cells, identical information.

# 🧭 Both map images now share one frame

Overlaying the cleaning path on the room map in
`xiaomi-vacuum-map-card` did not work, and **@Thonno** diagnosed why
before reporting it: *"the shape and proportions correspond — the
problem is that the Cleaning Path is rendered independently"*.

Exactly right. Each image auto-fitted to its own content — the room map
to every room, the cleaning path to whatever one mission covered — and
each published `calibration_points` correct for itself and meaningless
against the other. The card was handed two valid, incompatible
coordinate systems.

The room map now publishes its extent and the cleaning path renders
into it. Both report the same calibration and overlay directly.

⚠️ **A single mission will look smaller than before.** Three rooms out
of eight now occupy three-eighths of the floor plan instead of filling
the canvas. The old rendering made every mission look like a
whole-house clean.

Not made an option: two views of one home at different scales is not
something anyone would choose, it is a consequence of the two images
having been built separately.

# 🔎 Fixes from the last round of reports

**Zones were missing from the room list a template can read.** The
`rooms` attribute on the *Rooms overdue* sensor was built from the cloud
coordinator's `regions` property, which holds rooms; clean zones live in
a separate property nothing was reading. On a Prime robot, which has no
cloud coordinator at all, the list came back empty. Found by
**@ibernstone** asking how to enumerate zones in a `for_each`.

**A menu entry with no label.** *Cleaning frequency per room* was
offered by the config flow and had no string, so Home Assistant drew a
blank row. It worked when clicked — only the name was missing. Present
long before b1; **@Thonno** is the first to mention it.

Both now have build checks. The translation checks compared the
language files against each other and against `strings.json`; all eight
agreed perfectly, because all eight were equally missing the same key.
Nothing compared any of them against the code.

**Silence now survives a restart.** `no_contact` measured from the last
MQTT message, which lives in memory — so a robot that was already quiet
before a Home Assistant restart never got a timestamp and the check
could not fire at all. It falls back to when the entry was set up: an
hour of uptime with no message is an hour of silence.
(**@utkjmitch**, whose robot was silent for nine days.)

**The superseded pad-dry buttons are hidden on new installs.**
**@chairstacker** asked for the pair to be replaced by one switch, and
the switch was built beside them — so he got three entities for one
action. Existing installations keep the buttons and any automation
calling them keeps working.

# 📦 roombapy-prime now installs from PyPI

The library this integration depends on is published, so the manifest
pins `roombapy-prime[map]==0.3.1` instead of a git URL. Home Assistant
resolves that without git and without cloning a repository, which makes
a first install faster and works on systems where git is not available.

Nothing changes for anyone already running it — the same version, from
a different place.

The pin guard needed widening for the same reason it needed widening
once before: it matched only the old spelling, so the day the manifest
changed it reported the pin as **absent** rather than as changed. A
pattern that cannot match says the same thing as a missing line, and
the two need different fixes.
