# 🤖 Classic robots

*Everything that speaks local MQTT.*

## ✨ New

| | |
|---|---|
| **🧽 Mopping from Home Assistant** | Cleaning mode selector — vacuum · mop · both · vacuum-then-mop. `clean_zone` takes a mode too, plus pad wetness and smart scrub for a single run. |
| **📅 Schedules are writable** | Create, edit and delete from HA; changes reach the robot. Previously read-only. |
| **🚫 More blocking sensors** | `input_boolean`, schedules, people, device trackers. A house in vacation mode can block a mission. |
| **🕐 "Last cleaned" per room** | Optional, off by default — a four-map household makes a lot of entities. |
| **🧹 `clean_area` on Combo robots** | Did not work before. |
| **🔔 "Robot went silent" blueprint** | A robot that stops reporting does not clear its entities: battery keeps showing its last percentage and nothing looks stale. @utkjmitch's sat that way for nine days. |

> **The mopping one has an awkward history.** The send path had accepted a
> cleaning mode for a long time. The selector that sets one lived in the
> Prime-only branch — so there was nowhere to say it. The wire was
> connected at one end.

## 🐛 Fixed

**📅 The calendar could not change a weekday.** Three releases fixed the
handling of a value HA never sent. The events carried no recurrence rule,
so HA showed no recurrence fields at all — nothing wrong with the
processing, no way to state one.

**🗺️ Room history showed raw ids on multi-map households.** Every record
was resolved against the *active* map, so a mission from another floor
kept its ids. Rooms-overdue counted an unresolved id as permanently
overdue, and visit counts split one room in two. *Nothing is rewritten* —
past missions get their names on the next read.

**🎯 `clean_zone` refused to run on a two-map robot**, even mid-mission,
because it waited for the robot to say which map it was on. A zone
belongs to exactly one map — so the map comes from the zone.

**🏷️ Two map images had the same name** in 7 of 8 languages. A check
added while fixing it found a second collision: Spanish called the dust
bin and the water tank the same thing.

**📐 Area sensors ignored your unit system**, and counts were declared as
measurements.

**⭐ The favourites diagnostic reported 0** while the cloud reported 6.
Not a favourites bug — the diagnostic read a Prime-only field that is
always empty on Classic.

## 🔬 900-series: the live map, rebuilt

The pose pipeline was rebuilt against the robot's own navigation
architecture rather than against assumptions. Lifetime area was wrong by
a factor of 100 on two robots; a third of the room list was stale
history; both map images now share one reference frame, so the trail
overlays the floor plan instead of sitting beside it at a different
scale.

> ⚠️ **A single mission will look smaller than before.** Three rooms out
> of eight now occupy three-eighths of the floor plan instead of filling
> the canvas. The old rendering made every mission look like a
> whole-house clean.

# ☁️ Prime robots

*Combo and Plus 400-series, Max 705 — cloud-only, no local protocol.*

## ✅ Confirmed working

| | |
|---|---|
| 🔑 **Setup & control** | Sign in with your iRobot account. Start · stop · pause · resume · dock · locate. Classic robots on the same account are found too. |
| 🎯 **Room & zone cleaning** | Including vacuum · mop · both per run. |
| 🗺️ **Live map** | iRobot's own rendered map, plus a rooms map with floor plan, furniture and live trail. Interactive room selection. |
| 📅 **Schedules** | As an HA calendar — create, edit, delete, with recurrence. |
| ⭐ **Favourites** | As buttons, appearing and disappearing as you change them in the app. |
| ✂️ **Map editing** | Rename rooms, split and merge them. |
| 🔧 **Maintenance & settings** | To-do list with the dock's real part names. Evacuate · pad wash · pad dry. Suction, carpet boost, pad wetness, child lock. |
| 🕐 **Room-level history** | Cleaning history, rooms overdue, per-room "last cleaned", `roomba_plus_room_completed` event. |
| 🌙 **Do Not Disturb & blocked reasons** | No Classic robot reports these. |

> **Region cleaning, and why we call it confirmed.** A single-room command
> on a Combo 105 produced a 27-minute run covering **234 sq ft** — against
> two prior whole-house runs at exactly **644**. An acknowledgement proves
> delivery; the area proves scope.

## 🟡 Known limits

*These work as far as anyone can tell. Nobody has watched a robot
respond, and the hardware that could answer is not in the test group.*

- 🌙 **Do Not Disturb actually taking effect.** Readable and writable;
  whether the robot obeys is unverified. That is why quiet hours are
  offered as an automation rather than as a control promising an effect.
- 💧 **The pad-wash upper range on some docks.** Values are offered that
  at least one dock does not appear to accept.
- ⬆️ **Uploading a modified map** back to the robot is **not built** — no
  request payload has ever been captured, and restoring a map is rare and
  destructive enough that guessing its shape is the wrong trade. Reading
  and editing maps is unaffected.

**Whole-house cleaning is `vacuum.start`**, confirmed on several robots.
Do not expect a region command with an empty room list to mean
"everything" — there is no such payload, and one tester's robot answered
a malformed region command by cleaning the whole house.

## ⛔ What Classic has and Prime does not

| | |
|---|---|
| 🔌 **Working without internet** | Structural, not a gap to close — Prime robots have no local protocol at all. Connection down = robot unreachable. |
| 📊 **Dirt ↔ sensor correlation** | Grew out of the Classic health-tracking path, not carried across. |

Everything else — room cleaning, schedules, maintenance, presence-aware
scheduling, mission maps, room rhythms — is on both.

# 🩹 Fixed during the beta

*Everything here came from a field report. Several were diagnosed by the
person who reported them.*

## Missions filed as the wrong thing

**A mission that ended on a self-clearing error was recorded as
completed.** @ScenicSystemsLLC's Braava hit error 42 while travelling to
dock; the error cleared itself, and by the time the mission-end message
arrived the field read 0. @AlakazipLabs documented the same shape for
error 46. Any error seen at any point during a mission now counts.

**A resumed mission was filed as abandoned.** @ScenicSystemsLLC's robot
got stuck, was freed by hand sixteen minutes later, then cleaned four
more rooms and drove home — 168 minutes, a genuine dock finish, recorded
as abandoned. He found the asymmetry himself: the stuck event is a
before/after snapshot, the recovery a live phase transition whose
timestamp is rewritten on *every* re-entry into an active phase. The
classifier was measuring "time since the last phase change" and calling
it "time since the robot resumed".

**A flat battery counted as getting stuck.** @AlakazipLabs walked an i3
down to 6%, sent `dock`, and watched it give up thirteen seconds later
with error 46 while the robot's own stuck counter advanced. A robot that
repeatedly runs itself flat scored identically to one that repeatedly
gets trapped.

**Mission records rewrote themselves.** From @mdarocha's live-instance
investigation: terminal fields — duration, initiator, timestamps, result
— now freeze on first write, and a stale phase pulse hours later no
longer re-opens a finished mission.

## Sensors that said the wrong thing

**Mission progress froze mid-clean.** @Thonno watched the percentage hold
at 20% while elapsed time climbed past 32 minutes — two mutually
impossible numbers. Lewis firmware sends mission status only on state
changes, so between rooms the sensor read a stale phase and returned a
cached value.

**`current_room` now says how it knows.** It comes from elapsed mission
time against per-room estimates and never checks a position. A new
`current_room_source` attribute reads `estimate` or `mission_timer`. The
sensor still gives you a room; it no longer asserts one without saying
where it came from.

**The device tracker called a working dock a cleaning robot.**
@chairstacker's tracker showed "Docked" at the end of a mission and
flipped back to "Cleaning" minutes later, with the robot in its dock the
whole time. Two causes: the dock's own pad wash was in no phase set and
fell through to the active branch, and the tracker was subscribed to the
map coordinator while its state came from the status one — so it rendered
a phase that had already ended. New state: **Dock busy**.

**Lifetime energy could go down**, utilisation could exceed 100%, error
sensors reported the literal string `"None"`, and the 30-day error
attributes disagreed with their own state about which errors were in
window.

## Entities that appeared or vanished for the wrong reason

**Dock entities depended on when Home Assistant restarted.**
@AlakazipLabs logged 15 flips of the robot's dock-identity flag across
24,900 messages — 11 within seconds of a user dock command, returning on
their own minutes later with no dock contact. That flag gated the
pad-wash and pad-dry sensors, the wash/dry buttons and the pad-dry
switch, and it was read once, at startup. A restart inside one of those
windows cost a real AutoWash dock its entities until the next reload
happened to fall elsewhere. The gate is re-evaluated on every update now,
and it can only ever add.

**Zone names reached the device tracker.** The name cache only refetched
while empty — and rooms arrive first, so the first room to land closed
the gate and no zone was ever picked up (@chairstacker).

**Zones appeared in the room list templates can read.** The `rooms`
attribute was built from a source that holds rooms and not zones, so no
zone ever appeared — and on a Prime robot the list came back empty
(@ibernstone).

**`no_contact` never fired on a Prime robot.** Shipped in a46; the check
that would have caught it was added alongside the fix.

# 🔍 Two things we know we cannot see

Written down rather than guessed at, because a wrong guess here is worse
than the gap.

**A swallowed command from a paused robot is invisible.** The watcher
that reports "the robot accepted this and did nothing" asks whether a
mission started — the right question only when none was running.
Detecting the paused case needs a success signature, and no accepted
region start from a paused robot has ever been recorded. @AlakazipLabs
preregistered the experiment and ran it: a robot with its best
localisation reading in weeks still refused, while `resume` two minutes
later took instantly. Localisation is excluded as the cause.

**Prime readiness codes may be wire values or indices.** The Classic
sensor decodes before looking up a label; the Prime one does not, and
nothing establishes which form Prime sends. An unrecognised code renders
as "unrecognized", which is honest; a wrong decode would render a
confident wrong label.

# 🧭 Why 4.0.0 now

The 4.0 line has been in the field since the first alpha, and the beta
has been running for weeks. What is still unverified will not become
verified by waiting — it needs robots and docks nobody in the test group
owns, and a stable release reaches people the beta channel never did.

**Further fixes ship as 4.0.1.** That is faster for everyone than holding
a release until the next report arrives, and this beta produced a report
almost every day.

**One thing worth checking before you update:** automations matching the
status sensor's old value will stop matching. The status sensor is
translated now, and its state values changed with it.
