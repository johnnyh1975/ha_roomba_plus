# Roomba+ v4.0.0a30

Requires roombapy-prime **v0.2.0b16**.

Four faults reported by testers on a29, and the two worst of them were things this integration did
*to* people rather than failed to do for them.

## The maintenance list is now something you ask for

@chairstacker found a to-do list in his sidebar he had not asked for — **the second time something
appeared there uninvited.** He said he would hide it immediately, and he was right to.

A to-do list is not a quiet entity: Home Assistant gives it a place in the navigation, which is the
user's space rather than ours. It is now an option, and **unlike the calendar it defaults to off**.
The calendar defaults on only because it existed before there was an option, and turning it off would
have taken it from people using it.

## Editing a schedule no longer destroys its recurrence

@DaRealGuGu moved a Mon/Tue/Wed schedule from 20:50 to 21:00 and watched every occurrence but one
disappear — in Home Assistant *and* in the iRobot app, where it became a one-off.

Home Assistant's edit dialog sends only what the user touched, so no recurrence rule came with a time
change. Reading a missing rule as "once" is right for a **new** event and destroys an existing one.
An edit that says nothing about recurrence now keeps what the schedule has.

**The write always succeeded. It wrote the wrong thing** — which is why nothing looked broken until
the app was checked.

## A one-off schedule sits on its own date

Also his: the same single event appeared on 31 July, 29 June and 10 August depending on which month
the calendar was showing.

a29 drew the first occurrence generated *within the requested window*, which is "the first matching
weekday you happen to be looking at". It now uses the schedule's real anchor date, and draws nothing
at all when there is none — a schedule placed arbitrarily is worse than one not shown.

## Zero means two opposite things

His maintenance list showed one item due while the iRobot app and the robot's light ring said nothing
was.

Two of his parts count the same 90 pad washes: the pad has 210 washes of life left, the wash counter
reads zero *since the last one*. **On a replacement part zero means used up; on a maintenance part it
means just done.** The category was already being read — for the verb, "Clean" versus "Replace" — and
now decides this too.

## Zones no longer need a running mission

@chairstacker ticked clean, keep-out and no-mop zones, reloaded twice, and saw nothing. Correct
behaviour, and useless: the zone data came only from the live map bundle, which arrives on a
map-update message — that is, only while the robot is driving.

**Zones barely ever change, and nobody inspects their keep-out areas mid-clean.** The room map's own
bundle carries the same three files and is fetched whenever the map is built; it is now the fallback.

## Room naming, from @connormxy's setup

Three separate faults in the same doorway:

- **Two option keys for the same thing.** The naming flow writes `smart_zone_labels`; the capability
  check read `smart_zone_data`, which only the rest980 migration ever writes. Someone who named their
  rooms through our own flow still failed the check.
- **The naming step read only `cleanSchedule2`**, so a robot whose owner never built a schedule *with
  rooms* had nothing to name. His robot knows its twelve rooms; they simply are not in a schedule. It
  now also reads the last command and the cloud coordinator.
- **An empty naming step reported itself finished**, which reads as "done" when it means "found
  nothing". It now says which of the two it was.

## Presence scheduling and demand cleaning now work on Prime

Six options — the enable switch, the mode, the person entities and two delays — were offered in the
dialog, stored, and read by nobody on a Prime robot: setup branches for Prime and both managers were
built in the Classic function.

**A user could switch presence scheduling on, pick their household and set two delays, and nothing
would happen.** No error, no message. They did not merely not get the feature; they believed they had
it, and an automation built on it was silently inert.

Classic pauses schedules with `schedHold`. A Prime robot accepts a write to that field, reads it back
changed, **and runs anyway** — APK research found it appears once in the Prime app, with no
serialisation annotation and no consumer across 3801 classes. Inherited plumbing, not a control. So
Prime disables the schedules instead, which is what the iRobot app itself does.

Only schedules *we* switched off get switched back on. Enabling everything would turn on one the user
had deliberately disabled before leaving, and nothing in Home Assistant would explain why the robot
ran on a day they had opted out of.

**One visible difference:** a paused Classic schedule still looks scheduled in the app; a paused Prime
one looks switched off. It is — but it is not what Classic does.

Demand cleaning goes the other way: **Prime has the better source.** Classic infers dirt density from
mission records, builds a weekday baseline from at least four, and compares with a user-set
multiplier. A Prime robot reports a value per room and the threshold to judge it by, in one response —
so instead of starting a whole clean, it starts the room that needs it. One room per evaluation,
the dirtiest: sending everything above the line would be a whole-house clean by another name.

## Phase and readiness, and with them the device triggers

`phase` is the most basic state sensor there is and Prime did not have it. Found by comparing every
Classic value function against a real Prime shadow — not by anyone reporting it, which is the point:
**a missing sensor generates no error and no complaint, only a person quietly giving up.**

`readiness` says why the robot will not start, and matters more here than on Classic: a Prime robot
refuses a start silently, and this is the only place that says why. An unmapped reason shows as its
code rather than a blank — @connormxy's error 236 is exactly the case that went unnamed because
nothing displayed it.

**The device triggers came with it and needed no code.** They do not listen for events; they watch
entity state, found by translation key. "When the robot starts cleaning" simply did not appear in the
automation editor for Prime users, because there was no phase entity to attach to.

## The to-do list is opt-in on both generations

@chairstacker found one in his sidebar he had not asked for. It is now an option — and after being
added for Prime only, extended to Classic too: his point, that a to-do list takes a place in the
navigation and should be asked for, says nothing about which robot it is.

**Classic users who use the list will need to switch it back on.**

## Also

- **Diagnostics say why a capability is withheld** (`withheld_features`). @connormxy's `clean_area`
  simply did not appear — no error, no log line — and he reinstalled three integrations looking for
  the reason.
- **Backups include a Prime robot's cloud state**: map versions, favourites and schedules, fetched
  rather than read. "It is already in the cloud" is not a reason to skip it; a cloud can change its
  API, and this project has spent weeks reverse-engineering one that did.
- **`CONF_CLEAN_DELAY_MIN` was offered, stored, and read by nothing.** Now wired: the away delay
  waits to be sure everyone has gone, this one waits before cleaning.
- **A room clean with no known map was sent anyway on Classic.** @Echovictor37 found that a region
  command without a map id returns a PUBACK **and cleans the whole house** — accepted, effective, and
  not what was asked. Asking for the kitchen would have got every room, with a success in the log. Now
  refused, with an error that says what would otherwise have happened.
- **`async_remove_config_entry_device` was named in the plural** and took a list where Home Assistant
  passes one entry, so Home Assistant found no hook and refused every device removal — with nothing
  in our logs, because our code was never reached.

5,174 tests.
