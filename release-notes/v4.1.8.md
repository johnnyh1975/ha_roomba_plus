# Roomba+ 4.1.8

Two fixes, both about rooms and zones being told apart — or not.

> **Check your automations if any of them read the readiness sensor.**
> Its state used to be English text (`Ready`, `Off dock`); it is now a
> key your language translates for display (`ready`, `off_dock`). A
> comparison against `"Ready"` stops matching, and it stops silently.

## The readiness sensor speaks your language now

**Status – Readiness** showed English text — "Ready", "Off dock" — in
every language. The translations existed all along, in all eight, fully
written and reviewed. The sensor produced a value none of them could
match, so not one of the 73 ever appeared.

A German user read "Off dock" with "Nicht in Station" sitting unused in
the file beside it.

## And it was naming the wrong states

The value a robot sends is turned into a state name through a table.
This used the formula the iRobot app appears to use, and it was wrong
for most of the range: the robot's own firmware maps those values
through an arbitrary lookup whose order is deliberately broken.

**The clearest case: two testers' robots reported a value shown as "Off
dock" while sitting on their docks, charging.** It means the robot is
loading a map. @Thonno had also noticed his map-saving notification stop
and his automations stall — the same cause, presented as a docking
fault.

The table is now taken from the firmware itself. Everyday states that
were bare numbers before are named: bin full, insufficient charge, tank
low, map version mismatch, invalid pad, and eighteen others.

A value this project has not confirmed now shows as its raw number
rather than an invented name. That is deliberate — guessing is what
caused the above.

## Mission results are translated

`stuck_and_resumed` and its five siblings appeared as raw text in every
language, English included. All six are translated in all eight
languages now — "Steckengeblieben, dann fortgesetzt" rather than
`stuck_and_resumed`.

## Cleaning rooms by name could fail for rooms that plainly exist

Passing room names to `roomba_plus.clean_room` could come back with
"Unknown room(s)" for rooms visible in the selector and in the room
display at that very moment (@mrsnyds).

The names come from two places. The display and the selector read a
cached list; the service read only the map data. When the map data was
empty — not fetched yet, or a fetch that failed — the service saw no
rooms while their names sat on screen beside it.

The service now falls back to the same cached names the display uses.
On a robot with more than one map it still declines, because that cache
does not record which map a room is on and guessing a floor is worse
than saying no.

## `clean_zone` no longer accepts a room name

The zone service resolved names against a list holding every region on
the map, rooms included. Passing a room name sent that room's id as a
zone — a zone that does not exist, so the robot cleaned nothing and
reported success.

That is the mirror image of the bug fixed in 4.1.6, where a zone went
out as a room. Both directions are now closed.

---

Both fixes come out of the same underlying shape: the cached name list
is flat, with no record of what is a room and what is a zone. Anything
reading it has to get that distinction from somewhere else.
