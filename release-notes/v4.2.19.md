# Roomba+ 4.2.19

## Naming rooms: the map is in the form

Configure → *Rooms & zones* asked for names by number, and nothing in
Home Assistant said which room a number was (@liblit, on a 980 and an
i7):
- **The instructions started with
  `[formatjs Error: MISSING_VALUE]`.** Since 4.2.5, the text of both
  steps named a value the code never passed.
- **The text pointed to "zones drawn with their numbers" in the iRobot
  app.** The app shows no numbers, and a 980 has no map at all.
- **On Smart Map robots, it asked about rooms the iRobot account had
  already named.** Every region number the robot had ever reported got
  a field, pre-filled with "Zone 21". Saving the form unchanged stored
  those placeholders as names.
- **On a 980, the fields were labelled `zone_room_1`.** That is an
  internal id, and nothing on the map matched it.

The step now asks only what can be answered in Home Assistant itself:

- **The form shows the robot's map, and the fields carry the numbers on
  it.** Each unnamed room or area is drawn with its number, and the
  field with the same number names it. The fields are empty; leave the
  ones you do not want to name.
- **Smart Map robots with your iRobot account:** names come from the
  account, as everywhere else in Roomba+. Only a room on the map with
  no name anywhere is asked about. Numbers known only from old
  schedules or earlier cleans are on no map, and are left out.
- **Smart Map robots without the account:** Roomba+ knows the rooms only
  by number and has no map to show. The step now says so, and points to
  Configure → *iRobot cloud credentials*. *Manually enter Smart Map
  zones* is still there if you know a room's number.
- **900-series robots:** the form shows the *Cleaning path* map, where
  every unnamed area is drawn with its number.
- **No map, no form.** If the map image is turned off, or the robot has
  not cleaned yet, the step says what is missing.

The maintenance list's *Reconfigure rooms* item follows the same rule.
It no longer stays open for rooms that your iRobot account has named.

The map in the form is an image served through a signed link, which
Home Assistant issues for that form only and lets expire after 30
minutes. If a form stays open longer, close and reopen it.

## Clean zones on Classic robots

On an i7+ the cloud zone select listed every clean zone by name, and
none of them could be cleaned (@Hardy-196):
- **`roomba_plus.clean_zone` with a zone name answered "not found".** It
  read only the Prime robots' name sources. On Classic it now takes the
  names the zone select shows: the account's name, or your own from
  *Zone management*. Matching ignores case and accents, as `clean_room`
  does.
- **`roomba_plus.clean_zone` could not have worked on Classic even with
  an id.** The zone went to the robot under its internal marker, as a
  room. It now goes out as a zone, without the map version that makes
  the robot refuse a zone-only command (error 224).
- **The *Clean zone (Smart Map)* button sent every selection as a
  room.** A clean zone now goes out as a zone.
- **Zones listed under `zone_id` in the account's map data had no id
  in the select.** The select now reads both keys the account uses,
  for rooms as well.

## A room renamed in Roomba+ can be cleaned by its new name

A room renamed under Configure → *Zone management* shows its new name
everywhere: in the room select, on the rooms map and in the card.
`clean_room` did not know that name, and answered "Unknown room(s)" for
the room the card had just offered. It now takes the new name. The
original name keeps working, so automations written before the rename
still run.

If the new name already belongs to another room, the name stays with
that room, and the log says so.

## Obstacle pins share the robot's coordinates

`format=hazards` of the mission history API mixed two coordinate
systems:
- **Stuck pins** came in millimetres from the dock, the frame of the
  cleaning path and the coverage map.
- **Obstacles the robot learned, and keep-out zones**, came in the
  map's own units, under the same `x_mm`/`y_mm` fields. Their bearing
  and distance "from the dock" were measured from the map's origin.

Placed on a map, they landed in the wrong spot, and the Roomba+ card
stopped drawing them. Each pin now carries a `space` field:
- **Once the map is aligned with the robot's coordinates**, the
  obstacles and keep-out zones are converted, and every pin says
  `pose`.
- **Before that**, they keep the map's units, say `umf`, and have no
  bearing or distance rather than wrong ones.

`x_umf`/`y_umf` carry the map's own coordinates either way. Details:
[API.md](../docs/API.md).

## Event entities for mission end, room end and stuck

Home Assistant lets only administrators subscribe to an integration's
own bus events from the frontend. A dashboard card opened by any other
user never heard a mission end, and its history stayed stale until the
page was reloaded.

The three moments are now also event entities:
- **`event.{name}_mission_completed`** and
  **`event.{name}_room_completed`**, on both generations;
- **`event.{name}_stuck`**, on Classic robots only, because Prime robots
  report no stuck event.

Each changes when its bus event fires for that robot, and carries the
event's payload as its attributes. The bus events fire exactly as
before, so automations and device triggers are unaffected.

**Prime `roomba_plus_mission_completed` now carries the Classic fields.**
It sent `entry_id` alone; the logbook, automations and the new event
entity now get one shape on both generations. `stuck_count` is `null`
on Prime. A sync that imports several missions at once fires once, for
the newest, and `missions_added` says how many; the first sync after
setup imports the whole history. Both generations add `mission_id` and
`missions_added`.

## A guide link on each consumable

Part sensors now carry a `guide_url` attribute where iRobot's parts
catalogue has a replacement guide for that part. It is the
manufacturer's own page, for your robot's model and in your Home
Assistant language.
- **Classic:** the filter, brush, side brush and dust bag sensors, with
  the iRobot account added.
- **Prime:** every part sensor.

The catalogue is read once per setup, in the background, without
logging in. If it cannot be read, the links are missing and nothing
else changes. iRobot is still filling the catalogue in, so not every
part has a guide yet.

## The coverage map says where it draws

`image.{name}_coverage_map` has a new attribute, `render_extent_mm`. It
gives the millimetres the square image covers. The existing `x_min_mm`
to `y_max_mm` attributes are the bounding box of the visited cells, and
on a floor plan that is not square, a point placed by those lands in the
wrong spot. The renderer now takes its scale from the same calculation,
so the attribute and the picture cannot drift apart.

## Documentation

- **Prime do-not-disturb entity ids:** the switch is
  `switch.{name}_prime_quiet_hours_active` and the binary sensor
  `binary_sensor.{name}_prime_quiet_hours`. The feature guide and the
  automation examples named ids that do not exist.
- **The schedule calendar is writable on both generations.** It was
  described as read-only in the README (Prime) and in the automation
  guide (Classic). The README now gives the Prime calendar's real id,
  `calendar.{name}_prime_schedule`.
- **The maintenance to-do list is opt-in.** The README's first steps
  said it appears automatically. The starter dashboard in the
  automation guide says so too, and gives the Prime map's id.
- **The REST API version rule is written down** in API.md: when
  `X-Roomba-Plus-Api-Version` rises and what counts as breaking. It is
  now **2**, for the `format=hazards` change above. Readers that check
  it compare with `>=`.
- **xiaomi-vacuum-map-card:** the guide said the card's Roomba+
  platform was not yet merged upstream. It is, and the card documents
  it.

## Prime: the REST API exists

The mission history API (`/api/roomba_plus/…`) was registered only when
a Classic robot set up. A household with only Prime robots had none of
it, and the card's history, household and today views had nothing to
call. It is now registered by whichever robot sets up first.

Prime missions in `format=records` now list their rooms by name, and
carry their bin emptyings, which came back empty before. Not available
for Prime: obstacle pins (`format=hazards` is empty), and the mission
path and mission map endpoints (404). The data behind them comes from
the local connection, which Prime robots do not have.

In the household summary, `maintenance_due` now works for Prime robots.
It read the hour counters a Classic robot reports over its local
connection, which a Prime robot never sends, so a Prime robot was never
due there. It now follows the Prime maintenance list: a part the robot
reports as used up is due. A pad wash that has just been done is not,
and neither is a part the dock does not have.

## Prime: two sensors that were never created

*Rooms overdue* and *Room cleaning history* were announced for Prime
robots in 4.0.0, and never appeared. They were created only when the
Classic cloud connection was present, and a Prime robot never has one.
They now exist whenever the robot keeps a mission history, which every
Prime robot does. A test built on real Prime runtime data now fails
without the fix; the old one passed regardless.
