# Roomba+ 4.1.4

**Fixes a regression in 4.1.3 that stopped every entity from loading.**
If you are on 4.1.3 and your robots vanished from Home Assistant, this
is the fix. If you rolled back to 4.1.2, you can go straight to this.

## What happened

4.1.3 included a change meant to silence a Home Assistant deprecation
warning, by preferring a newer registry call where it exists. That call
takes more arguments than the one it replaced, and the version here
passed only one:

```
TypeError: DeviceRegistry.async_get_device_by_identifier()
           missing 1 required positional argument: 'config_entry_id'
```

Every entity reaches that code during setup, so nothing loaded at all —
339 entities across three robots on HA 2026.8.1, 100+ across two on
2026.9.1. Anyone on Home Assistant 2026.x was affected; anyone on an
older release was not, which is why it was not caught before release.

**Why it was not caught:** the newer call does not exist in Home
Assistant 2025.5, the minimum this integration supports. Nothing in the
test environment could invoke it, so its signature was written from its
name rather than read.

**The fix is not a revert.** Home Assistant's own migration note gives
better advice than either version of the call: inside an entity, prefer
`self.device_entry` over a registry lookup. That property has been on
`Entity` for years, works on every supported release, and removes the
question of which lookup method to use. The registry call remains only
as a fallback for the case where the entity has no device yet.

A guard now fails the build if anything reaches for the unverifiable
method again.

## `clean_room` logged an error after working

The action ran, the robot cleaned, and then Home Assistant reported:

> Failed to process the returned action response data, expected a
> dictionary, but got `<class 'NoneType'>`

`clean_room` was registered as supporting a response but never returned
one. `OPTIONAL` does not mean the handler may return nothing — it means
the caller may ask for a response, and the handler must then produce
one. It is registered as returning none now, which is what it does.

Nothing about the cleaning changes. Reported by @mrsnyds, who filed it
as low priority because the robot worked, and asked what he had left out
of his action — nothing; there was nothing to leave out.

A guard now checks every service registered with a response against its
handler.

## Everything else from 4.1.3 is unchanged

The room/zone duplication fix, cross-map rooms, the Clean Base bag on
900-series robots, the evacuation phantom mission — all still here.
