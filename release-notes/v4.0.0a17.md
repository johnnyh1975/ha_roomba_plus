# Roomba+ v4.0.0a17

**Update if you have shared a diagnostics file, or plan to.** This release fixes a privacy problem
in that export.

## Diagnostics were leaking a password hash

`ro-configinfo.passwordHash` was not redacted. **[@jouwdan](https://github.com/jouwdan)** found it in
his own export and removed it by hand before attaching the file to a public issue.

That is the worst shape a gap of this kind can take: the file says `**REDACTED**` in half a dozen
places, so it reads as safe. Anyone less careful would have attached it as-is and reasonably assumed
the tooling had done its job.

The cause was that the redaction list had been assembled from fields somebody happened to notice,
never from asking what a *category* of secret looks like. There are now two layers:

- named fields — `passwordHash` and eleven similar
- **a substring check** on every key at every depth, for anything containing `password`, `token`,
  `secret`, `apikey`, `credential` or `passphrase`

Verified against field names that appear in no capture — `wifiPasswd`, `authToken`, `deviceSecret` —
which are precisely the ones a hand-written list would miss.

## The vacuum showed "idle" during a pad wash

A robot having its pad washed reports `phase: "padWash"`, a value this integration did not know.
An unmapped phase left the vacuum entity showing whatever it had shown before — so the state fell to
"idle" mid-wash and returned to "docked" afterwards.

Reported as a feature request by **@DaRealGuGu**, whose logbook showed it plainly. It was a bug.

`padDry` and `refilling` are deliberately **not** added on the same pattern: neither has appeared in
any capture, and a wrongly mapped phase is silently wrong forever, where an unmapped one costs a log
line.

## A vacuum-only robot was given pad sensors

An evacuation-only dock reports `cap: {"evac": 1}` — the object is present, and the absence of `pw`
inside it says the dock cannot wash. The code was treating that like a missing capability object,
where "unknown" correctly means "create the entity anyway".

That rule is right for the *robot* capabilities and wrong for a nested object that is present.
@jouwdan's own diagnostics named the reasoning: `"created (capability unknown -- failing open)"`.

## New: dock activity on the vacuum entity

A `dock_activity` attribute — `pad_washing`, `pad_drying` or `evacuating` — for building a card or
an automation around what the dock is doing.

Requested by @DaRealGuGu, who wanted it as a *state*. Home Assistant's vacuum entity has exactly six
states and a vacuum reporting anything else is broken rather than extended, so an attribute is as far
as this can honestly go.

## New: start pad drying

`drypad` was left out of the dock buttons because the iRobot app does not offer it. @DaRealGuGu
pointed out the cost: stop the drying and the only way to restart it is another full wash — a tank of
water for nothing.

The original reasoning conflated two things. Guessing at a *command* is what this project refuses to
do; offering a *workflow* the app does not is a separate question, and here it is plainly better.

## Also fixed

- **A stored automation naming an unknown trigger** raised `KeyError` during attach, breaking the
  automation with a traceback. It now logs a warning and detaches cleanly. Found by searching for the
  pattern after the same shape crashed a tester's tooling twice.
- **Dock error codes are named.** All 84 confirmed dock states appear as `error_name` alongside the
  number — which is how a missing dock water tank is reported, since there is no presence field for
  one.
- **The robot water tank sensor was renamed.** It reads the *robot's* tank, not the dock's; on a
  robot whose dock holds two tanks the old name read as though it covered them.
- **Consumable part 213 is Cliff Sensors.** Identified by **@arielgr**, who put the app's maintenance
  list beside Home Assistant's and matched the numbers — four agreed in sequence.
- **Parts 202 and 212** are now named for the counter and the action rather than left numeric:
  pad washing, cleaning due and replacement due. Not for the physical component, because the app
  names two candidate dock parts and nothing distinguishes them.
- **Diagnostics now include the schedules** the robot actually reports, which is what the calendar
  reads. Neither shadow carries them, so a calendar showing nothing could not be diagnosed before.
