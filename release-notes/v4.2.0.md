# Roomba+ 4.2.0

**The async rewrite, and everything from the 4.1 line.**

Two things happened in parallel. The 4.1 releases fixed a run of field
bugs, one after another, as testers found them. Meanwhile 4.2 rebuilt
how commands reach a Classic robot. This release is both: **every fix
from 4.1.1 through 4.1.8 is in here**, and the 4.1 line has ended.

If you are on 4.1.8, this is a normal upgrade. If you are on an earlier
4.1, you are also collecting whatever you skipped.

---

## What changed underneath

The library that talks to Classic robots became asynchronous, and every
command path moved with it — 46 call sites. From the outside nothing
should look different: the same entities, the same services, the same
behaviour.

**Cleaning passes work on i7/s9/j7-class robots.** They had no effect at
all before — not intermittently, never. The firmware reads the setting
as one half of a pair and silently drops both halves when they arrive
separately, reporting success either way. That fix went upstream into
`roombapy` and comes back here, and it is confirmed on hardware: two
firmware families, both halves echoed back by the robot, surviving a
restart, and a 2.6m² room that took 7m42s with a visible second pass
(@ScenicSystemsLLC).

**Suction is fixed but unconfirmed.** It was broken twice over. The
same paired-setting fault applied, and separately the carpet-boost
control could not find its own robot: it looked the vacuum up under the
wrong identifier, so the command never left Home Assistant at all. The
dropdown flashed the new value and snapped back. Both are fixed; only
the first has been verified on a robot, because the second was in the
way of testing it.

## Rooms and zones

Most of the 4.1 line was about telling rooms and zones apart, and about
reaching a room on a map the robot is not currently using.

**Zones are recognised as zones.** The robot's map data marks every
region as one or the other, and that marking was being ignored — a zone
went out as a room id, the robot found nothing and reported success
about a minute later.

**Zones work on robots with two maps.** The zone's map was knowable all
along; a prefix on the id stopped the lookup finding it.

**Rooms on every map can be cleaned and mapped to Home Assistant areas.**
Each id carries the map it belongs to, so a room upstairs is reachable
by name. Cleaning rooms from two maps in one command is refused rather
than half-done.

**A room name can no longer come from the wrong map.** Region ids repeat
across maps; the map the command actually named now wins.

**`clean_room` no longer reports rooms as unknown** when the map data
has not arrived. It falls back to the same cached names the display
shows.

**`clean_zone` no longer accepts a room name** — the mirror of the same
fault.

**`clean_room` remembers the rooms it last resolved.** The room selector
always did: when a lookup fails it keeps the previous list, so the
dropdown stays usable and the button still cleans. The service asked
afresh every time and, on a robot where the lookup came back empty,
reported rooms as unknown while the very same rooms sat in the dropdown
beside it. One tester's button had worked for weeks while his service
call never had (@mrsnyds).

## The room display follows the robot

**Read this one with a caveat.** The mechanism below is right and the
fault that kept it from ever running is fixed, but no robot has yet
been seen to advance a room live. There is a second check in front of
it that needs a per-room time estimate, and whether every robot has one
is not yet known.

Roomba+ shows which room is being cleaned. It used to work that out from
a phase the robot reports between rooms, and S9-series robots never
report one: the display sat on the **first room of the plan** for entire
missions.

The robot has been sending a second signal all along — it reports when
it is *driving* rather than cleaning, and a drive that ends is a room
boundary. Confirmed from the iRobot app's own code and from the robot
firmware independently before being relied on.

New attribute **`room_progress_observed`**: `false` while the room name
is still a plan rather than something observed.

## The readiness sensor

**It now says something useful, in your language.** Two changes, both
larger than they sound.

The states were English text that no translation could match, so none of
the 73 in any of the eight languages ever appeared. And the value the
robot sends was being turned into a state name by a formula that does
not exist — the firmware uses an arbitrary lookup table. Two testers'
robots reported "Off dock" while charging on their docks; the value
means the robot is loading a map.

The table now comes from the firmware, checked against a second image
and against the app's own display strings. Twenty-three states that were
bare numbers are named, and the wording follows what iRobot tells users
rather than the robot's internal constants — "Near a virtual wall"
rather than "In RCON".

**An unconfirmed value shows as its raw number.** Guessing is what
caused the above.

## Smaller, and worth knowing

- **The cleaning-mode selector only offers modes your robot can perform.**
  Picking a mopping mode on a vacuum used to stick and then be ignored
- **Gentle mode appears on S9-series robots**, which call the setting by
  a different name
- **Mission results are translated** — `stuck_and_resumed` and its five
  siblings, in all eight languages
- **A Roomba 980 is no longer told to replace a Clean Base bag** it does
  not have
- **A bin evacuation no longer opens a phantom mission**
- **`last_cleaned_rooms` no longer reports an earlier mission's rooms**
  during a new one
- **An empty navigation record no longer counts as a measurement** —
  some robots report all zeros, which was feeding a quality metric

## If you have automations

**Two state values changed** in the 4.1 line and are worth checking:

The **readiness sensor** used to report English text (`Ready`,
`Off dock`); it now reports a key your language translates for display
(`ready`, `off_dock`). A comparison against `"Ready"` stops matching,
and it stops silently.

Everything else is unchanged.

---

## Under the hood

A new build-time guard checks the four ways a region-cleaning command
can reach a robot — the service and the button, on each generation —
against the concerns all four have to handle. They had drifted: the
wrong-floor warning reached three of them, and `clean_zone` carried the
mirror of a fault already fixed in `clean_room`.

Nothing about this is visible in use. It exists so the next fix lands in
all four places rather than in whichever one the bug was reported
against.
