# Roomba+ 4.0.0a34

Requires **roombapy-prime 0.3.0b5**, pinned automatically.

A percentage that never appeared, two safety guards that were switched off on
exactly the tier they were written for, and a map that can finally be both
things at once.

## The mission progress sensor worked and never said so

@utkjmitch's Y351020, mid-mission: `mission_progress` reading `unknown`, and
its own attributes reading `elapsed_run_min 10.7`, `estimated_remaining_min 42`
against a persisted 52.2-minute mean. Everything the percentage needed, sitting
next to a percentage that was not there.

Zero `mission_progress:` debug lines across fifty minutes, which is what made
the diagnosis short: `native_value` was returning before its first log call, at
the phase gate.

`roomba_reported_state()` returns `{}` on a Prime entry **by design** — there
is no master_state-shaped translation for V4. So a phase read through the
Classic shape is `""` for the life of the entry, and every gate built on it is
decided before the robot says anything. The attributes read the same dead phase
and simply did not gate on it, which is why they worked.

Three fixes were needed and this was the third: storage (a32), the estimates
fetch (a32), and the gate. Field-verified the same day on a patched a32: first
percentage this sensor has ever produced on a Prime robot, climbing against the
rolling mean, and the idle and docking gates closing exactly as on Classic.

Diagnosis and patch by @utkjmitch.

## Two guards that failed OPEN on Prime

The same shape appeared at four more sites, and two of them fail in the
dangerous direction:

- **`advance_room`** compares the phase against `"run"` to refuse advancing
  during an active mission. On Prime the phase is `""`, so it never matched:
  the guard was permitted mid-mission, on the tier it exists for.
- **`dirt_threshold`'s "robot must be docked" gate** compares the cycle
  against `"none"` and always passed.

Two more fail quietly rather than open: per-room time estimates read
`lastCommand.regions` for pass counts and found nothing, so a two-pass mission
was estimated at one-pass durations — the exact bug a comment two lines above
records as already fixed, reached from the other side.

All four now read the Prime shadow when the Classic shape is empty. A test
counts the remaining call sites: adding one means deciding whether a Prime
entry reaches it.

## The Rooms Map is now interactive and live at the same time

Contributed by **@jouwdan** (PR #76).

The card takes one raster source and cannot stack a cleaning camera above a
room-selection map, so the integration composites the live layers into the
calibrated Rooms Map instead. Room selection stays first-class and the card
tracks the active clean.

Also in that work:

- **Live layers survive a reload**, persisted rather than held in memory
- **Walls and doorway cut-outs** — doorways are holes in a polygon, and the
  floor plan keeps them now
- **Room selection uses stable IDs**, so a room renamed in the iRobot app no
  longer breaks a saved card configuration. Name, slug and id all resolve, and
  an id counts only when unique across maps
- **Rooms that only the bundle names** are selectable — @DaRealGuGu's fourth
  room shows in his app and was missing here
- **Every `roomba_plus.*` action was absent on a Prime-only installation.**
  The Classic setup registers them in a phase the Prime path returns before
  reaching. The actions existed, the entities existed, nothing connected them

## Zones followed the robot instead of the map

@chairstacker selected Master_Bathroom in the dropdown while a Whole_House
mission ran, and saw Whole_House's clean and keep-out boundaries drawn over the
bathroom floor plan. His summary was exact: two sets of maps switching
properly, one set of zones that is either on or off.

The live bundle belongs to the map the robot is **driving**, and it was
preferred unconditionally. Right while a robot had one map; with several it
draws the wrong boundaries on the right floor plan — worse than drawing none,
because a boundary in the wrong place invites trusting it.

## Start blocked, and what still works

Four fault codes stop a mission before it starts, and all four have been in the
error catalogue for weeks with nothing drawing a conclusion from any of them.
Three do not mean "broken":

```
287  pad plate fitted        mop works, vacuum does not
290  pad plate missing       vacuum works, mop does not
234  plate fitted, no cloth   vacuum works, mop does not
286  robot off the floor      neither
```

`binary_sensor.*_prime_start_blocked` says which, in words and in a form an
automation can branch on — `blocked_modes`, `available_modes`,
`blocked_reason`. A device trigger fires when a block appears.

**Nothing is refused.** A vacuum command against 287 still goes out. The app
takes the other route and greys out every dock control once a task begins,
which is why a drying cycle it started cannot be stopped there — and this
integration deliberately does not copy that.

`234` and `290` are different states, and folding them together would tell
someone to attach the plate they already have on.

## Do Not Disturb, in all three of its parts

Quiet hours turned out to be two mechanisms plus a display, and the integration
had none of them:

| | |
|---|---|
| `roomba_plus.set_quiet_hours` | writes the daily window, or a one-off "quiet until" |
| `switch.*_do_not_disturb` | turns DND on and off right now |
| `binary_sensor.*_in_quiet_hours` | whether a scheduled window covers this moment |

The window and the ad-hoc state are separate in the robot's own protocol, and
the two entities can legitimately disagree — the switch on while no scheduled
window covers now. They are named for the different questions they answer.

**Its effect is unproven, and the action says so when you call it.** A Prime
robot has been observed cleaning inside its own quiet-hours window. The setting
is accepted and reads back; whether the robot honours it is a separate question
no field report has answered yes. Keep automations that depend on quiet hours
in Home Assistant.

## Rejected commands are no longer silent

A command call that returns without an exception, on a robot that then does
nothing, has been diagnosed by elimination every single time it happened.
`schedHold` is accepted and ignored; a vacuum command against a fitted pad
plate is refused. Two very different failures that look identical from here.

The library has offered a rejection watcher for months and nothing called it.
It runs now, at most one log line per minute, with no entity — nothing is known
about what the robot puts in that payload, and building a sensor on an
unobserved shape would be inventing a contract.

It may well never fire. It rides the same namespace that went quiet for three
alpha releases while shadow traffic continued, and @utkjmitch has just shown
that timeline reports do not arrive on the topic this integration subscribes
to. Silence there would be evidence about the namespace rather than the robot.

## Also in this release

- **Nineteen missing initiators.** "Started by" knew six values and fell
  through to "None" for the rest — the same answer as "no information at all".
  `dockBtn`, `alexa`, `siri`, `ifttt`, `team` and fourteen more are named now.
  A household with a schedule *and* a voice assistant could not tell them
  apart.
- **Diagnostics downloads on Prime were missing four blocks**, including the
  `favourites` block built specifically to investigate missing favourites. It
  sat in the Classic path, which a Prime entry returns before reaching. Every
  download taken to answer that question omitted the answer.
- **`get_favorites_raw()` carried the bug it was built to reveal** — a wrapped
  response captured as an empty list, so a download meant to establish whether
  the server returns anything answered "no" either way. Fixed in b5, and the
  block now carries the raw response beside the count.
- **The pad-drying switch was offered for docks that cannot dry.** It had no
  capability gate at all, and the dock capability was being fetched at the call
  site and discarded.
- **`multiPass` level 3 means one pass only.** The rule excluded only an
  explicit 0, so a robot that cannot do two passes was offered the toggle. No
  current tester is affected, which is the kind of bug that waits for different
  hardware.
- **Selecting a mop-wash interval on five product modes** offered values the
  robot's own app does not show. Two of those five became recognisable as Prime
  in the same release as the controls themselves.
- **`padWashesUsed`** — the vendor spells this count type two ways and only one
  was mapped, so a robot reporting the other showed a bare number.

## Upgrading

Nothing here changes an existing entity's ID or an action's arguments. The new
entities appear on their own; `image.*_rooms_map` keeps its ID and gains the
live layers, so an existing xiaomi-vacuum-map-card configuration needs no
change.

## Two questions for anyone with the hardware

**Which phase does a combo robot report while washing MID-mission?** A robot
with `pwReturn = 2` washes its pad during cleaning, not only at the end. The
phase handling has a gap exactly there, and one observation closes it.

**Does the iRobot app offer you an "empty now" action?** @utkjmitch's robot has
an auto-empty dock and reports `dock: {"known": false}`, so the empty-bin
button is withheld. Whether that is right depends on whether the dock accepts
the command at all.
