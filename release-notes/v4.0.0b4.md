# Roomba+ 4.0.0b4

Two fixes and a new blueprint, all from field reports since b3.

Still requires roombapy-prime 0.3.1, unchanged.

---

# ⚠️ A mission that ended on an error is no longer filed as completed

**@ScenicSystemsLLC**'s Braava hit **error 42** — a localisation
failure — while travelling to dock. The error cleared itself, and the
mission was recorded `completed`.

The classifier does check for errors. But it read
`cleanMissionStatus.error` from the **mission-end message**, and by then
the field was back to 0. **@AlakazipLabs** documented the same shape for
error 46: transient, self-clearing once the robot stops trying.

Any error seen at any point during the mission now counts, not just the
one still showing when it ended.

**Third instance of one root cause.** `nStuck` needed a counter that
only goes up; resumption needed the cloud record; this needed
remembering. All three were the same mistake — reading a property of a
whole mission off its final frame.

# 🔔 New blueprint: Robot went silent

The four existing blueprints cover starting and reporting. None covered
**the failure that looks like nothing is wrong.**

A robot that stops reporting does not clear its entities — battery keeps
showing its last percentage, phase its last phase, and nothing looks
stale. @utkjmitch's robot sat that way for nine days.

Triggers on the status sensor reaching `no_contact`. There is no event
to listen for, because silence is the absence of messages and an absence
fires nothing; the integration turns it into a state and the blueprint
watches that.

An extra wait (default 15 minutes, on top of the integration's hour) is
configurable, because a robot carried to another room or a router
restart can produce a gap that resolves itself.

# 🔎 Live-instance investigation fixes

**@mdarocha** ran an investigation against a live instance and fixed
what it turned up — re-verified against b3 source before touching
anything, which is why several items on his original list came back as
"already fixed, not re-touched".

**Mission records stop rewriting themselves.** Terminal fields —
duration, initiator, timestamps, result — freeze on first write. Later
messages for the same mission merge additive fields only, and only
inside the MQTT re-delivery window; anything materially later is a real
multi-recharge segment and still appends as its own. A completed
mission's duration no longer changes after the fact.

**And a stale phase pulse no longer re-opens a finished mission** —
a robot flipping back to `run` hours later is a replay, not a
continuation.

**Sensors that violated their own contracts.** The lifetime energy
sensor could report *less* than before; it now floors at a persisted
high-water mark. Utilisation could read above 100%. The 30-day error
attributes and the state disagreed about which errors were in window.
Error sensors reported the literal string `"None"`.

**Maps refresh once per completed mission**, including missions with no
pose data — previously the refresh only fired for some. And the
coverage-ratio sensor keeps its last valid reading across sparse
missions instead of dropping out.

**Plus** device-tracker labels in all eight languages rather than six
falling back to English, firmware-internal favourites no longer exposed
as buttons, and the smart-zone selector staying enabled instead of
latching off the first time it sees no zones.

Full icon registry coverage across every platform, with a test that
enforces it going forward.

# 📊 Mission progress no longer freezes mid-clean

**@Thonno** watched the percentage hold at 20% while `elapsed_run_min`
climbed past 32 minutes — and the two numbers were mutually impossible:
20% implies an average mission of 164 minutes, 23 minutes remaining
implies 56. One of them was a cached value, not a fresh one.

The percentage is cached and returned from cache whenever the phase is
not `run`, `hmMidMsn` or `evac`. That guard exists for a good reason —
@chairstacker reported the value dropping to "Unknown" the moment a
mission ended, so the graph of a completed clean ended in nothing.

**But it assumes the phase is current.** Lewis firmware sends
`cleanMissionStatus` only on state changes, so between rooms the sensor
reads whatever arrived last. If that is not an active phase, the
percentage freezes while everything around it keeps moving.

The cache is now consulted on genuinely terminal phases, or once the
mission is over. Mid-mission it recomputes, whatever the last message
happened to say.
