# Roomba+ 4.3.0b4

**A beta.** Everything in [4.3.0b3](v4.3.0b3.md), plus the fixes from
the stable release [4.2.16](v4.2.16.md), plus: the mission history now
really reaches back beyond the cloud's recent window on Classic robots.

Needs *Show beta versions* in HACS. Built on **roombapy-prime 0.4.0**, the first stable release of the
0.4 line.

---

## The mission archive reaches further back

With an iRobot account, Roomba+ fills its mission archive once from the
cloud's history. That archive feeds the lifetime figures, the statistics
behind anomaly detection and the room dirt index. It asked for the
history page by page, going backwards, with the parameters the Classic
iRobot app sends (`count`, `before`).

**The cloud ignores both.** Measured on a Roomba 980 and an i7 (thanks
@Thonno):
- asking for 10 missions returned every mission of the recent window
  (33 and 67);
- asking for older ones returned that same window again.

So the archive only ever held the recent window, whatever was asked.

Two other parameters, `maxReports` and `exclusiveStartTimestamp`, do
page on both robots: 10 asked, 10 returned, then 10 older ones with none
repeated, with the same fields. Roomba+ now:
- **fills the first page as before**, with the request its regular
  refresh makes;
- **then pages back** from the oldest stored mission with those two
  parameters, up to the archive's 800 missions. Older missions go behind
  the stored ones; nothing already stored is dropped to make room.

**Existing archives page back once** after the update. Their first load
finished under the old parameters, so they hold only the recent window.
It runs in the background, one page every two seconds.

**Ending conditions:**
- **A mission-counter reset ends it.** Going back in time, mission
  numbers fall. A robot with a previous owner, a factory reset or a
  replacement unit can have older missions whose numbers are not lower
  than today's. Paging stops at the first of those instead of storing
  two missions under one number.
- Only a page size of 10 has been measured. If the cloud refuses 100 a
  page, Roomba+ asks once more with 10.
- If the cloud refuses the request itself, the archive keeps what it
  has and doesn't ask again.
- If the connection fails, it keeps what it fetched and continues from
  there at the next start.
- A page that brings nothing older ends the paging, so a cloud that
  ignores the new parameters too is asked once, not in a loop.

**Map alignment:** when the refresh's records hold no traversal evidence
for the smart map, Roomba+ asks for older missions. That request had the
same problem: it asked for 500 missions before the oldest one and got
the same recent window back. It now uses the paging request as well.

## From 4.2.16

- **A mission's rooms in the order they were cleaned.** The cloud sends
  a mission's events newest first, and several places read them front
  to back: cleaned rooms were listed in reverse, the time figure of the
  room accessibility score stayed empty, and the mission path and the
  archived event timeline ran backwards. All of them sort the events by
  time first now, including missions already archived.
- **The built-in Roomba card that cannot be dismissed** is explained in
  the troubleshooting guide and the README.

## roombapy-prime 0.4.0

b1 to b3 were built on the 0.4.0 betas; b4 is built on the stable
release. Its code is 0.4.0b3's. The paging request above comes from
there: `ClassicRestClient.get_mission_history_page()`.
