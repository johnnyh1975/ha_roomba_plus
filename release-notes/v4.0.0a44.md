# Roomba+ 4.0.0a44

Requires roombapy-prime 0.3.0b15, which comes with the HACS update.

Three field reports from the day a43 shipped, and one of them is a
startup crash caused by a43 itself.

## Every select failed on a mopping Classic robot

The cleaning-mode select for Classic robots — the a43 fix answering
"how do I start mopping" — took the whole select platform down with
it on exactly the robots it was for. Cleaning passes, carpet boost,
pad wetness, all of it, including the select being added.

`PrimeCleaningModeSelect` was imported inside the Prime branch.
Python binds a name imported anywhere in a function as local to the
*whole* function, so on a Classic entry that import never ran and
the append raised `UnboundLocalError`.

It needed a Classic robot that reports `padWetness` to surface at
all: cloud-only households never reach that line, and a vacuum-only
Classic robot never passes the gate. @utkjmitch had one of each on
the same install, diagnosed it exactly, and sent the fix.

A check now walks the setup function and fails if a name is imported
inside one branch and used in another. Two other candidates turned
up and both were sound — each branch imported for itself.

## The device tracker showed nothing during a zone clean

It fills its name cache from `available_rooms()`, which reads
`rooms_metadata` from each map — and that carries rooms, not zones. So a
zone-targeted mission produced a region id matching nothing in the
cache, and the tracker had nothing to show.

Not because the zone was unnamed. It was never in the list being
searched, and would still have been missing if every zone on the map had
a name.

Zones now merge into the same cache from `prime_room_names`, which holds
every region the coordinator has seen. A room wins a name collision,
because a room's name comes from the map's own metadata while a zone's
comes from whatever the last command called it.

## Suggested intervals kept raw ids after the history fix

`rooms_overdue.suggested_interval_days` resolved through the active-map
view, which is filtered on purpose so a room *command* cannot go to the
wrong floor. A suggested interval is not a command — it is a statement
about a room that exists somewhere, and on a four-map household most
rooms are not on whichever map happens to be active.

The same distinction the history fix rested on, one attribute further
along. It now resolves across every map, with the active one winning a
name collision.

## Every select failed on a mopping Classic robot

The cleaning-mode select for Classic robots — the fix answering "how do
I start mopping" — took the whole select platform down with it on
exactly the robots it was for.

`PrimeCleaningModeSelect` was imported inside the Prime branch. Python
binds a name imported anywhere in a function as local to the *whole*
function, so on a Classic entry that import never ran, the name was
local-but-unbound, and the append raised. Cleaning passes, carpet boost,
pad wetness, all of it gone — including the select being added.

It needed a Classic robot that reports `padWetness` to surface at all:
cloud-only households never reach that line, and a vacuum-only Classic
robot never passes the gate.

A check now walks the setup function and fails if a name is imported
inside one branch and used in another. Two other candidates turned up
and both were sound — each branch imported for itself.

## The pad-dry switch failed on every press

"Failed to perform the action switch/turn_on. Update method not
implemented."

The error came from the line *after* the command, not from the command.
`PrimeStatusCoordinator` is push-driven and has no `_async_update_data`,
so asking it to refresh falls through to Home Assistant's default and
raises.

The command had already gone out and the dock had already acted. The
switch reported failure for work that succeeded — the worst shape a
failure can take, because it invites pressing again.

The refresh request is gone. Nothing was needed there: the dock pushes
its state and the switch's subscription writes it. A check now fails the
build if any entity asks this coordinator to refresh.

## The mission status now names the room it is cleaning

`current_room_id` was a number, and nothing beside it said which room
that was. The device tracker resolved the same ids and showed a name, so
the two entities disagreed about the same robot in the same moment.

`current_room` sits alongside the id now. The id stays, because it is
what a cleaning command takes.

This covers zones too — the name source holds rooms and zones together,
and a zone-targeted mission previously had no name to show anywhere.
