# Roomba+ v4.0.0a19

Prime only again. Requires roombapy-prime **v0.2.0b7**.

Two of the three changes here came from field reports rather than from anything found in the code.

## Schedule switches now stay in sync with the app

a18 made these switches exist for the first time. They read their state twice — when created, and
after Home Assistant wrote it — and never again. Schedules come from a REST call rather than the
robot's live stream, so a schedule toggled in the iRobot app stayed wrong until the integration was
reloaded. Not a mission start, not a reconnect: only a reload.

The comment justifying that in the code said "a setting nobody watches change". @chairstacker gave
the case that breaks it, and it is worse than a stale display:

> Switch the automations off in the app before going on holiday. A Home Assistant automation using
> that switch as a **condition** now acts on a value that has been false since the last restart.

A switch entity is machine-readable state, not decoration, so this was a correctness problem and a
silent one. There is now a schedule coordinator on a fifteen-minute cycle. The calendar reads it
too, instead of running a second timer against the same endpoint — one fetch per account, however
many entities are watching.

## The pad wash status said "Unknown (671)"

@chairstacker pulled the dock's clean water tank and nothing changed: `dock.error` stayed 0, the
dock status stayed "Dock ready", and no sensor moved. Triggering a pad wash produced 671 in
`dock.pwState`; refitting the tank put it back to 601, with every other dock field unchanged
throughout. One field carries the whole signal, and only when something asks the dock to wash — tank
presence is not a state this dock reports, it is an answer to an attempt.

671 is not in the decompiled `DockState` enum, whose pad-wash family stops at 669. It is now in a
separate field-observed table, deliberately kept out of the enum so that decompiled values stay
distinguishable from inferred ones.

The same code was already in the mission error table, labelled "Clean water tank empty" from a
single earlier observation. That label is wrong in a way that matters: this time the tank was not
empty but missing, and "empty" sends someone to refill a tank that is not in the dock. Reworded, in
all six translated languages. The entry itself stays, with the doubt written down — 671 is the only
code in that table between 509 and 1010, which suggests it was filed there from an observation whose
field was never recorded, but deleting it would destroy a real sighting if that reading was genuine.

## Live map layers are back (#65, @jouwdan)

Restores the live rendering from #63 that the a16 refactor dropped: cleaned coverage, trajectories,
hazards and the robot marker, with the a17 static-map fit kept intact.

Rendering is now lazy. A live packet marks the map dirty and the PNG is produced in `async_image()`
when Home Assistant actually fetches it, so an idle dashboard costs nothing; state writes are
throttled to one every two seconds so an open dashboard does not refetch per pose packet. Position
and bundle messages use separate dispatcher signals rather than one signal with an overloaded
`None`.

Each of the three layers is checked by a pixel assertion at a coordinate derived from the same fit
transform, so a layer drifting out of the room frame fails a test rather than looking plausible in a
screenshot.

4,704 tests.
