# Roomba+ 4.3.0b1 — one iRobot account for all your robots

**A beta.** It changes how Roomba+ uses your iRobot account: how you set
up several robots, and how they log in to iRobot's cloud. It does not
change what your robots do, which is why it needs testing before it
becomes a release.

Needs *Show beta versions* in HACS. Built on **roombapy-prime 0.4.0b2**.

---

## Setting up several robots

Until now every robot was a setup of its own from scratch: the account
typed in again for each one, one robot picked per run, and on the local
path the HOME button held on every robot. For three robots on one
account that was three full runs.

**Set up the first robot with your iRobot account, and the others are
offered.** Once it is added, every other robot on the account appears in
*Settings → Devices & services* under **Discovered**. One click adds it;
nothing needs to be entered. A Classic robot is looked up on your
network, and only if it cannot be found does the setup ask for its IP.
A robot you do not want can be ignored there, and stays ignored.

**An account already in use is offered, not asked for.** Adding another
robot later shows the account your other robots use, next to *another
account*. Choosing it still logs in once, so that a robot added to the
account since shows up and a password that stopped working says so.

**No HOME button for a robot of a known account.** When Home Assistant
finds a Classic robot on your network, and a robot running here already
uses the account it belongs to, its password comes from that account.
The setup then only asks whether to use the account for the new robot
too, or none, and tries the password on the robot once you answer.
Finding the robot alone logs in nowhere and connects to nothing. If the
robot is on no such account, or refuses that password, the HOME button
step appears as before, and says why. A robot added to the account only
after your other robots last logged in is not in their login yet: use
*Set up with my iRobot account* for it, which logs in fresh.

**The account comes first.** *Set up with my iRobot account* is now the
first and recommended choice: it works for every robot, finds all of
them, and needs no button. Setting up without any cloud account works as
before.

**One question less for Classic robots added from the account.** A
separate step asked whether to keep the account for cloud features,
defaulting to yes. Choosing the account already answered it. Cloud
features can still be turned off in the options.

**The robot list says which robots are already set up**, instead of
leaving them out without a word.

**A robot showing up on the network no longer ends your setup.** When
Home Assistant found an iRobot robot while you were in the middle of
*Add integration* and had not picked a robot yet, your setup was
silently closed. A check meant for truncated robot IDs matched every
setup without one.

## One login per iRobot account, not per robot

Until now every robot logged in to iRobot's cloud on its own. Three
robots on one account ran the full login three times, within a second of
each other on every Home Assistant restart. iRobot limits how many
sessions an account may hold and locks an account after too many
attempts; a restart with several robots was the moment most likely to
hit either.

Now the robots of one account share one login:

- **The first robot to start logs in; the others wait for it and take
  that login.** A restart with three robots makes one login, not three.
- **When the cloud asks for a new login** (its sessions expire after
  about an hour), the Classic robots that notice at the same moment wait
  for one new login together.
- **A failed login answers for the others for half a minute** instead of
  each robot trying again. Against a locked account every attempt
  extends the lock, so this matters most exactly when things go wrong.
- **Adding a robot or entering credentials again** hands the login the
  setup form just made to the robot, instead of logging in again moments
  later. That includes re-entering the *same* password, the usual
  reaction to a locked account. Until now this worked only for Prime
  robots added from the account list.
- **Robots with different passwords do not share.** If one robot still
  has an old password, it fails its own login and asks you for the new
  one, as before.

The last robot of an account to be removed or reloaded drops the login.
Nothing about it is written to disk.

**For Prime robots, only the first login is shared in this beta.** A
Prime robot keeps its own renewal for its live connection; that moves
onto the shared login in roombapy-prime 0.5.0 and Roomba+ 4.3.0b2. A
Prime robot never gets a shared login whose live-connection token has
less than ten minutes left; the account logs in again first.

## Cloud errors in your language

When a cloud login failed, the message was translated, but the reason
in it was not: a German user read a German sentence with an English one
inside, and the English part was the one that said what to do.

roombapy-prime 0.4 names the cause of every cloud error, and Roomba+
now has a text for each cause in all eight languages. What you see on
the integration card and in the setup forms says which it is:

- the login was rejected (check email and password)
- **the account is temporarily locked** (do *not* re-enter your
  password; wait about ten minutes)
- too many active sessions (close the iRobot app)
- this machine cannot check iRobot's certificate (update the system's
  CA certificates; waiting will not fix it)
- iRobot's certificate has expired, or iRobot's cloud has a problem of
  its own (on iRobot's side, usually fixed within hours)
- no connection, a connection that broke off, or no answer in time

**The setup forms no longer blame the robot for a cloud problem.** A
cloud login that could not reach iRobot showed *"Failed to connect to the
robot. Verify it is powered on and reachable."* A cloud login never
touches the robot.

## One password change for all robots of an account

When you change your iRobot password, all robots of the account now fail
together, since they share one login. Until now each of them then asked
for the new password on its own: three robots, three prompts, the same
password typed three times.

Entering it once is enough now. When one robot gets a new password, by
re-authentication or in its options, every other robot with the same
account address and the same old password takes the new password and
restarts, and its own prompt goes away. A robot with a different
password is left alone, because that password may be one that works.
Switching one robot to a different account, or removing its
credentials, is not passed on; that is a choice per robot.

## A cloud login that failed at startup is retried

On a Classic robot, a cloud login that failed when Home Assistant
started (no network yet, iRobot briefly down) left the cloud features
without a login until the next restart: no room names, no room
cleaning. The next refresh was a day away, and it then reported the
missing login as **wrong credentials** and asked you to re-enter a
password that was fine.

Now the next refresh logs in, and it comes **ten minutes** later instead
of a day, until the login succeeds. A failure there is reported as what
it is.

The one-time download of older mission history also waits for a login
now, and it stops when a page brings no mission it has not seen. A 980's
cloud ignores the request for older pages and answers every one with
the same missions; the download asked for that page about two dozen
times, two seconds apart, before it reached its limit. Now it asks
twice. Before, a failed first page marked it done with nothing in it, and
it never ran again.

## Under the hood

- **`cloud_api.py` is gone.** It was Roomba+'s own cloud client for
  Classic robots. Its requests moved into roombapy-prime 0.4 unchanged:
  the same query, the same body bytes, the same signature, tested there
  request by request. Both generations now use one library for the cloud.
- **`_prime_login_bridge.py` is gone**, replaced by
  `cloud_account.py`, which does the same for every robot and every
  setup path, keyed by the account instead of the robot.
- The config flow reads the robots of an account from the login
  response. A discovery for another robot carries its BLID, name, model
  and the account's address, never a password: the password comes from
  the account's entry when the robot is added.
- **The diagnostics download has a `cloud_account` section**: whether
  the entry shares its login, with how many entries, how old the login
  is, how many robots the account has, and the reason of a recent failed
  login that answers for the others. No address, no password, no hash
  of either.
- **Resetting a part with the cloud says why it failed**, in your
  language. The message showed the name of a Python exception class.
- **`cloud_errors.py`** turns an error's reason into a translation key.
  A test holds the texts to the library's list of reasons: a reason
  added upstream without a text fails the build.
- **Removed translation keys:** `invalid_cloud_credentials`,
  `cloud_rate_limited`, `cloud_ssl_certificate_error`, and the unused
  `cloud_auth_failed` and `cloud_unavailable` in the forms;
  `cloud_credentials_invalid`, `cloud_temporarily_unavailable`,
  `prime_login_rejected`, `prime_login_failed`, `prime_cannot_connect`
  and `prime_shadows_unavailable` in the error messages. All replaced by
  one `cloud_<reason>` key per cause. The `prime_classic_analytics`
  setup step and its texts are gone.
- A map picture (UMF) the cloud answers with nothing is now an error
  (no geometry, and a 502 from the mission-map view) instead of an empty
  map. The mission-map view also reports connection errors as 502; they
  were a 500.
- **roombapy-prime 0.4.0b2** is pinned.
