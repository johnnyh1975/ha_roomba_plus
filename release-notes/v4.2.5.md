# Roomba+ 4.2.5

Zones follow the robot too, four maintenance items get a reset button,
and the zone-naming dialog is usable again.

## Zones were still offered from every map

4.2.4 narrowed the **room** list to the map the robot can actually
reach. Zones come from a different source and were missed, so a
two-map robot still saw every zone from every map — and picking one
from the wrong map produced the same refusal as before.

Reported precisely: rooms narrowed correctly with the map selector,
zones did not (@chairstacker).

## Diagnostics can now answer "was the command sent?"

Three reports in a week described a command that produced nothing at
all — no error, no mission, robot on its dock. Every time, the first
thing to establish was whether it had gone out and with what, and every
time nothing could say: the robot records the commands it *receives*,
which is exactly what was in doubt.

Downloads now include the commands Roomba+ sent, with whether each was
published.

And a cloud-connected robot's download catches up with a locally
connected one. It was never missing the data — the robot publishes the
same fields, split across four documents that the download already
contained, just raw. They are now assembled and reported the same way:
last command, map ids and versions, mission state, battery, lifetime
counters, capabilities, and the room and position details added in
earlier releases.

A locally connected robot's download gains two things the cloud one
already had: which kind of connection produced the file, and how long
ago the robot last said anything. A robot that has been silent for
hours looked identical to a healthy one in every other field.

Related: the result of sending a command was being discarded at every
call site. A failure to publish was indistinguishable from success.

## A zone could have a name and no map

Room and zone names reach Home Assistant by two routes. One records
which map each name came from; the other did not, although it was
building that very map at the time.

A zone known only from the second route therefore had a name and no
floor — and a zone with no floor cannot be matched to the map you
selected, nor sent to the robot, which refuses it. One discarded value,
both symptoms.

Both routes record the map now.

## Four maintenance items had no way to be reset

The pad, the wheels, the charging contacts and the bin could all be
marked as done in the code, and nothing could reach it. Each was
advertised as a service that had never been registered, so calling it
returned "service not found" — and there was no button either.

All four now have a button, alongside the filter, brush and battery
ones. The seven services that never existed are gone from the
documentation, and a build check now compares what is documented
against what the services actually accept.

## Naming Smart Map zones

The dialog offered a pre-filled box that showed `20=21=23=` on one
line, while the instructions above it asked for one per line and the
error below called it invalid. The box was single-line and collapsed
the newlines it was filled with.

It is a multi-line box now, and the notice says which robot it means —
with two robots there was no way to tell (@liblit).

## Per-room cleaning options

`room_passes` let you set the pass count per room and nothing else,
though the code underneath has always accepted all four settings per
room. Each room can now carry its own `two_pass`, `cleaning_mode`,
`smart_scrub` and `pad_wetness`; anything omitted falls back to the
call-level field, then to the robot's own setting (@theChef613).

## Rooms and zones take the same options

`clean_room` offered two-pass; `clean_zone` offered smart scrub and pad
wetness. Only cleaning mode was on both — and it was being refused
outright on zones, with an error naming a field the interface had
offered. All four are on both services now.
