# Roomba+ 4.0.0a39

**Upgrade immediately if you are on a38.** It breaks vacuum entity setup
on Home Assistant 2026.7 and later — every robot, every model.

## What a38 did

It declared `self.last_seen_segments = None` in the vacuum entity's
`__init__`, on a code comment stating that `StateVacuumEntity` does not
provide that attribute.

That was true of the Home Assistant pinned in this project's test
environment — 2025.1.4, the newest installable on Python 3.12. It has
not been true of Home Assistant itself for some time: `last_seen_segments`
is a `@final @property` **with no setter**, and assigning to it raises
`property has no setter`.

That exception happens during entity construction, so the whole vacuum
platform fails to set up. Not one robot — all of them.

@ScenicSystemsLLC upgraded a three-robot fleet (two S9+, one Braava jet
m6) and lost all three, reproducing 3/3 every time. Rolling back to
v3.5.1 restored them within minutes.

@utkjmitch then checked the source rather than waiting for a crash and
widened it: the property is `@final` back through **2026.7.4**, and
`grep -c "last_seen_segments.setter"` returns 0 on both 2026.7.4 and
2026.8.1. So there is no Home Assistant version in the wild where that
assignment could have worked — @ScenicSystemsLLC was simply first to
install.

## What a39 does

Removes the declaration, and the method a38 added alongside it. Both
names belong to Home Assistant's vacuum platform. **Reading them is
correct; declaring them is not** — which is what a37 did, and why a37
was fine.

Where mypy against the pinned HA reports them as missing, they are
suppressed rather than declared.

## The general shape, because this will recur

mypy runs against the newest Home Assistant installable on Python 3.12.
The integration targets newer versions. So the type checker will keep
reporting real, newer APIs as missing — `AddConfigEntryEntitiesCallback`
and `StatisticMetaData`'s `mean_type` are the same situation, already
handled.

**"Fixing" such a report by declaring the name locally turns a type
checker complaint into a runtime crash.** That is exactly what happened
here, and it happened inside a release whose whole purpose was fixing
bugs found by that type checker.

Three tests now guard it: nothing may assign to Home Assistant's vacuum
properties, nothing may define them, and the guard itself has to name
something the module actually uses.

## Verified against the versions users run

Not against the pinned one — that is the check a38 skipped:

| | 2025.1.4 (pinned here) | 2026.7.4 | 2026.8.1 |
|---|---|---|---|
| `last_seen_segments` | — | `@final @property` | `@final @property` |
| `async_create_segments_issue` | — | present | present |

Both names are Home Assistant's, and the second is documented for
exactly this case: *"Integrations should call this method when the
vacuum reports different segments than what was previously mapped to
areas."*

So the a37 reads were correct all along. Only the assignment was not.

## Apologies

This was avoidable. The comment a38 relied on was written against one HA
version and read as a general fact, which is the failure mode this
project wrote a convention about the same day.
