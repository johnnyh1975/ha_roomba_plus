# Roomba+ v4.0.0a27

Requires roombapy-prime **v0.2.0b13** — unchanged, no library update needed.

Field reports from a25 and a26, and every one of them found something real.

## The four history sensors filled six hours late

Clean streak, Missions – Last, Last duration and Area cleaned today read `unknown` after every
restart, then presumably filled — which nobody ever saw, because nobody watches a sensor for six
hours. So "always unknown" was the observed behaviour.

@utkjmitch's debug log named it exactly: the first mission-history sync rides the parts coordinator's
update, and setup awaits that coordinator **before** `runtime_data` is assigned further down the same
function. The sync's first run could never succeed — it reached for runtime data that did not exist
yet, and a best-effort `except` filed the AttributeError at DEBUG. The next chance was the six-hourly
interval.

The first sync now runs after setup completes, and the coordinator ride is guarded so a doomed
attempt is skipped rather than logged.

**A sync that never ran should not look like a robot with no history.** Third variant of that shape
in two days, after a command that never left and a subscription that was never acknowledged.

## The schedule calendar was fifteen minutes behind the robot

@chairstacker ran a mission from 18:20 to 18:28 and watched the entity switch **on** at 18:28:23 and
**off** at 18:43:23. Fifteen minutes apart to the second, both edges late.

The phase check added in a25 reads the status coordinator, and this entity only listened to the
schedule coordinator — which runs every fifteen minutes. The logic was right and hung off a source
that could not reach it. It now follows both.

**And an interim dock no longer ends the event.** A robot docks *during* a mission to wash its pad or
to recharge and resume, and the phase alone cannot tell that apart from finishing. His own capture
from two days earlier had the answer in it: `phase=padWash, cycle=clean` mid-mission against
`phase=charge, cycle=none` at the end. A running cycle now keeps the event open whatever the phase
says.

## The previous mission's route no longer sits under the new one

The thin line @chairstacker could only clear by reloading was not our trail — ours had already been
cleared. It is iRobot's own `trajectories` layer from the downloaded bundle, which carries the last
mission until the robot uploads a new one.

That layer is worth keeping: our trail only exists while Home Assistant is watching, so a restart
mid-mission loses it while the bundle has the whole path. It now stands down as soon as we have
points of our own, and fills in when we do not.

## The dock is drawn where the dock is

The bundle records where the dock stood when the map was **built**, and nothing corrects it when the
dock moves. @utkjmitch's map put it on a spot now occupied by a treadmill while the iRobot app showed
it correctly.

A bundle carries thirteen content files and `dockPose` is the only one with a dock in it — so the app
reads the robot, not the map. His own suggestion is the fix: a robot reporting `charge` is standing
on the dock, and its position arrives through the same stream in the same coordinates. The bundle
stays as the fallback, because it is there immediately on a fresh install.

## Schedules can be edited from the calendar

Creating and deleting worked; editing did not, because Home Assistant only shows a save button when
the entity says it supports it. Room selection survives a time change — events are regenerated from
the schedule rather than stored, so the dialog opens on the canonical room labels, and those parse
back to the same rooms.

Editing a single occurrence is refused: a robot schedule has no notion of "this one only".

## Also

  covers all seven types it knows.
