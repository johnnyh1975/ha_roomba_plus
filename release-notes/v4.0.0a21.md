# Roomba+ v4.0.0a21

Requires roombapy-prime **v0.2.0b10**.

Almost everything here came from testers using a20 and telling us what they saw. Four items are
corrections to things a20 claimed and did not do.

## Schedule switches now actually disappear

a20's release notes said a deleted schedule's switch "will disappear". Only the half that adds
switches had been written. @DaRealGuGu reported three switches still sitting there greyed out, well
past the refresh interval, and he was right.

Removal only happens after a refresh that succeeded. A failed one leaves the coordinator's data at
its last good value, so nothing would vanish in practice either way — but tying deletion to a flag
that says "this data is current" is the difference between a rule and a coincidence. Deleting
someone's switches because the cloud hiccuped is the worst thing that file could do.

## The schedule calendar was stuck on "off" for its entire life

Reported as far back as issue #23: the entity said off while the same schedule was plainly visible
in the calendar view.

The entity does not poll — it inherits that from the Classic base class, where entities are driven
by the robot's own push. `async_update()` is the only thing that fills its occurrence cache, and
Home Assistant never called it. The cache stayed empty, so the state was permanently off.

The calendar *view* was never broken, which is why this survived: it fetches directly, with no
cache. And the fix made at the time — checking for an ongoing occurrence, widening the window — was
correct and could not possibly take effect, because it read a cache nobody filled. Two releases of a
repair running on empty input.

It now subscribes to the schedule coordinator, like the switches have since a19.

The Classic calendar had the same "off during a running mission" bug for a different reason, and is
fixed too.

## Schedule switches are named after what they clean

Six switches all read "Schedule – Regular Schedule". The iRobot app names every schedule it creates
that, shows the name nowhere, and offers no field to change it — so the name could never tell them
apart.

They now read like the app's own list: rooms, days and time.

```
Kitchen, Bathroom Sat 15:45
Kitchen, Bathroom +2 Mon-Thu 09:00
```

Rooms alone were not enough either: two of one tester's three schedules clean the same four rooms at
the same time and differ only in which days they run. Weekday abbreviations ship in all eight
languages rather than being hard-coded — `calendar.day_abbr` follows the process locale, not the one
configured in Home Assistant.

Entity ids still come from the schedule id, so a routine renamed in the app cannot rename an entity
out from under an automation.

## The robot and dock markers are legible

@chairstacker and @DaRealGuGu both reported the robot position as "not working". It was being drawn
the whole time — in a colour 90 units away from the trail it sits on, out of a possible 765, while
the dock differs by 245 and both of them could see that immediately.

Fixing the colour was not enough. At radius 7 the marker was fourteen pixels on a 600-pixel render:
about four and a half on the card he screenshotted, where a two-pixel ring is half a pixel. And both
markers were circles within two pixels of each other, so spotting a dot still did not say which one
it was.

The robot is larger now, with a white ring and a longer heading line. The dock is a square with its
own ring — shape says which marker it is, independently of size and colour.

## Also

- **No pad wash or dry entities on a robot with no wash dock.** A robot reporting `dock: {"known":
  false}` was read as "capability unknown, offer them anyway".
- **The error sensor shows the code rather than a Classic label.** There is no error table in the
  iRobot app for either generation, and a field capture had a physically stuck robot reporting "Low
  battery" at 55%.
- **New:** dock clean water tank level, for the docks that report one, and a pad drying switch.
- **A failed first read no longer costs the calendar entity** — found in this release's own bug
  hunt. The exception propagated out of entity setup, so one malformed schedule would have left the
  user with no calendar rather than an empty one.

4,746 tests.
