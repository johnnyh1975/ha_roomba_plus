# 🤖 Classic robots

*Everything that speaks local MQTT.*

## ✨ New

| | |
|---|---|
| **🧽 Mopping from Home Assistant** | Cleaning mode selector — vacuum · mop · both · vacuum-then-mop. `clean_zone` takes a mode too, plus pad wetness and smart scrub for a single run. |
| **📅 Schedules are writable** | Create, edit and delete from HA; changes reach the robot. Previously read-only. |
| **🚫 More blocking sensors** | `input_boolean`, schedules, people, device trackers. A house in vacation mode can block a mission. |
| **🕐 "Last cleaned" per room** | Optional, off by default — a four-map household makes a lot of entities. |
| **🧹 `clean_area` on Combo robots** | Did not work before. |

> **The mopping one has an awkward history.** The send path had accepted a
> cleaning mode for a long time. The selector that sets one lived in the
> Prime-only branch — so there was nowhere to say it. The wire was
> connected at one end.

## 🐛 Fixed

**📅 The calendar could not change a weekday.**
Three releases fixed the handling of a value HA never sent. The events
carried no recurrence rule, so HA showed no recurrence fields at all —
nothing wrong with the processing, no way to state one.

**🗺️ Room history showed raw ids on multi-map households.**
Every record was resolved against the *active* map, so a mission from
another floor kept its ids. Two more places had the same fault:
rooms-overdue counted an unresolved id as permanently overdue, and visit
counts split one room in two. *Nothing is rewritten* — past missions get
their names on the next read.

**🎯 `clean_zone` refused to run on a two-map robot**, even mid-mission,
because it waited for the robot to say which map it was on. A zone
belongs to exactly one map — so the map comes from the zone.

**🏷️ Two map images had the same name** in 7 of 8 languages. Now:
Cleaning path · Coverage heatmap · Live cleaning map · Room map · Raw
live map. A check added while fixing it found a second collision —
Spanish called the dust bin and the water tank the same thing.

**⭐ The favourites diagnostic reported 0** while the cloud reported 6.
Not a favourites bug: the diagnostic read a Prime-only field that is
always empty on Classic. The buttons were fine.

**📐 Area sensors ignored your unit system**, and counts were declared as
measurements.

## 🔬 900-series: the live map, rebuilt

*Only for 900-series — the robots with no saved map, where Roomba+
builds the picture from the position stream.*

> **If your map has looked wrong, this is the section.** It is also the
> newest work here and the part with the least field time.

| Symptom | What was happening |
|---|---|
| **Lines across rooms nobody drove** | A suspicious pose was *discarded*, leaving the previous one as the anchor — so every later real position measured against a stale point. One snapshot in a 106 m² home had **1413 points stranded in a 0.7 × 0.7 m pocket**. |
| **Coverage holes at doorways** | Marks were placed only where poses landed — ~200 mm of unrecorded floor between them on straight runs. A gap in a threshold reads as a **wall** to the room finder. |
| **Room outlines missing entirely** | The canvas fits to the trail, but an outline is drawn *outside* the covered area. It fell off the canvas essentially always — a real room looked identical to no room. |
| **Rooms appearing, then changing** | Detection ran after **one** mission. On a real archive: 7 rooms → 6 after four → 5 once settled. Two were never rooms. |
| **Everything shifted after a pickup** | Set the robot down 2 m away and every later pose is off by the same 2 m — the *gradual* correction dragged points that were still right. |

**Now:**

- ✅ Nothing is discarded — the **line** breaks instead, so a discontinuity is a visible gap
- ✅ The threshold **measures itself** from your robot's message rate, replacing a fixed 500 mm that was below what a robot covers between two updates
- ✅ Coverage follows the **path** between poses, stopping at a break
- ✅ Room outlines are included in the canvas fit
- ✅ Rooms wait for **three completed** missions
- ✅ Coverage from before a pickup is matched against known area — or left out when the match is not clear

### ⚠️ What this can and cannot give you

A room is built from **where the robot drove**:

- 🪑 Furniture leaves holes
- 📏 Edges stop ~one robot radius short of the wall
- 🚪 Boundaries fall at narrow points in the coverage, not necessarily at doorways

**More missions settle the room *count*. They do not change the *shape*** —
the furniture is in the same place every time. Wall-accurate outlines
would need obstacle data these robots do not report.

# ☁️ Prime robots

*Cloud-only robots on iRobot's newer protocol.*

Support began in **a0** with battery level unconfirmed and a warning that
this was a genuine alpha. **Forty-four releases later**, a dozen testers
run it daily.

## ✅ Confirmed working

| | |
|---|---|
| 🔑 **Setup & control** | Sign in with your iRobot account. Start · stop · pause · resume · dock · locate. Classic robots on the same account are found too. |
| 🎯 **Room & zone cleaning** | Including vacuum · mop · both per run. |
| 🗺️ **Live map** | iRobot's own rendered map, plus a rooms map with floor plan, furniture and live trail. Interactive room selection. |
| 📅 **Schedules** | As an HA calendar — create, edit, delete, with recurrence. |
| ⭐ **Favourites** | As buttons, appearing and disappearing as you change them in the app. |
| ✂️ **Map editing** | Rename rooms, split and merge them. |
| 🔧 **Maintenance & settings** | To-do list with the dock's real part names. Evacuate · pad wash · pad dry. Suction, carpet boost, pad wetness, child lock. |
| 🕐 **Room-level history** | Cleaning history, rooms overdue, per-room "last cleaned", `roomba_plus_room_completed` event. |
| 🌙 **Do Not Disturb & blocked reasons** | No Classic robot reports these. |

> **Region cleaning, and why we call it confirmed.** A single-room command
> on a Combo 105 produced a 27-minute run covering **234 sq ft** — against
> two prior whole-house runs at exactly **644**. An acknowledgement proves
> delivery; the area proves scope.

## 🟡 Not yet confirmed on hardware

*These work as far as anyone can tell — nobody has watched a robot
respond.*

- 🌙 **Do Not Disturb actually taking effect.** One tester's mission ran
  inside a quiet window. That observation predates several corrections to
  the values being sent, so it may have been a bad write rather than a
  robot ignoring a good one. Not repeated since.
- 🏠 **Whole-house cleaning through the region command path.** Reading
  iRobot's firmware narrowed it without settling it — and a wrong guess
  cleans the whole house, so it stays untested rather than becoming
  "probably fine".
- ⬆️ **Uploading a modified map** back to the robot.
- 💧 **The pad-wash upper range on some docks.** Values are offered that
  at least one dock does not appear to accept.

## ⛔ What Classic has and Prime does not

| | |
|---|---|
| 🔌 **Working without internet** | Structural, not a gap to close — Prime robots have no local protocol at all. Connection down = robot unreachable. |
| 📊 **Dirt ↔ sensor correlation** | Grew out of the Classic health-tracking path, not carried across. |

Everything else — room cleaning, schedules, maintenance, presence-aware
scheduling, mission maps, room rhythms — is on both.

# 🔍 Found by looking, not by breaking

A block of this beta came from field reports in its final week, and most
of it had been wrong since it was written. Recorded as its own section
because the pattern matters more than the individual fixes.

## 🗺️ The coverage heatmap was upside down

Since it was written. Every other map measures downward from the top of
the image; that one measured upward from the bottom of the grid.

Nobody noticed because the tile has **no landmark** — no dock icon, no
room outlines, nothing to be upside down *relative to*. @pk-1966 marked
four known places on his coverage and room maps and it fell out at once.

Correcting it exposed a second fault underneath: the bounding box is
measured centre-to-centre, so a row of cells at one edge had always been
missing. Invisible for the same reason.

## 🧩 Five bugs with one shape

Every one was Prime code reading a source that either does not exist on
a Prime robot, or exists and carries only part of the answer:

- 📭 **The per-room sensors created nothing.** A tester ticked the
  option, ran a mission, reloaded, and got not one entity.
- 🏷️ **The room name in `roomba_plus_room_completed` was always empty**
  — so "Kitchen finished" arrived without the kitchen.
- 🔢 **The device tracker showed a raw region id during a zone clean**,
  while the names sat in the diagnostics download the whole time.
- 🚫 **Zones could not be mapped to a Home Assistant area**, because
  they were never in the list the mapping dialog shows.
- ⬜ **The cleaning map stayed blank on robots that report no pose.**
  **@mdarocha** built the fallback that fills it — the last mission's
  cloud coverage, rendered when the pose renderer has nothing. It was
  then gated on the robot's declared `cap.pose`, which is exactly the
  field that lies on lewis firmware, so it stood aside on the robots
  needing it most. Covers an i3+ that never claims the capability and
  an i7 that claims it and never sends a pose.

None was carelessness at the time. A better source appeared later and
the places already reading the older one were never revisited. Four of
the five produced no error and no complaint.

**`scripts/check_prime_sources.py` now fails the build on that shape.**
It found one of the five itself.

## 🔀 Zones, everywhere they were missing

Saved clean zones are **drawn on the rooms map** — outlined rather than
filled, because a zone sits inside a room and a fill would hide it.
They are **offered as areas** in the mapping dialog. They **resolve to
names** in the device tracker and mission status.

The names were readable all along. Three releases of the diagnostic tool
reported "no zone names found" after a search that had not run.

## 🗣️ The status sensor speaks your language

For as long as it existed it showed English to everyone: Classic
translated in code, one language hard-wired; Prime reported the robot's
raw firmware words, which have no language at all.

Both now report translation keys, and the same ones. **Twenty sensors**
gained state translations in eight languages — `job_initiator`,
`clean_base_status`, `readiness` and the phase sensor among them, with
thanks to **@mdarocha**, who found twelve I had missed.

Two states are new because nothing expressed them before:

| | |
|---|---|
| ⚡ **Charging mid-mission** | A robot topping up is not finished. As plain "Charging" an automation reacting to it fires mid-clean. |
| 🔇 **No contact** | Nothing received for over an hour. @utkjmitch's robot went silent at 36% battery and nine days later every entity still showed its final value, indistinguishable from live readings. |

⚠️ **This changes the sensor's value.** Automations match `charging`
rather than `charge` or `Charging`. A break, taken deliberately in alpha
rather than after a stable release.

## 🧴 Consumables from the cloud

**@mdarocha** again: the parts counters iRobot's own app shows now
replace the install-time "assume everything is fresh" guess, with resets
written back so the app and Home Assistant agree about a part you just
changed.

**Side brush and dirt disposal bag** were visible in the iRobot app and
absent here. They now get the same treatment as filter and main brush —
wear rate and days until due, four new entities.

The obvious way to add two consumables is to copy the filter branch
twice. He replaced the branching with a table instead, so a mop device
turning its main-brush counter into a pad counter is data rather than a
conditional in three files. The next consumable is a table entry.

⚠️ Classic robots only. Prime robots get remaining counts straight from
iRobot for eleven parts — a better source than anything derived from
runtime. What they do not get is the interpretation: "89 pad washes
left" rather than "twelve days at your rate".

He found it by noticing his filter and brushes both read *exactly*
fourteen hours consumed — a counting start, not a measurement.

## 🏷️ Entity names that disagreed with themselves

`strings.json` and `translations/en.json` gave **different names for
eight entities**. English users see one file; a developer reads the
other.

Found by **@mdarocha** while settling a naming question in his own
contribution — he assumed two entities disagreed with each other, and
found one file disagreeing with another instead. A check now fails the
build on it.

## ⏱️ Per-region timestamps that stayed and worked

Turning on "Separate sensor per room and zone" created one timestamp
entity per room and zone — and they vanished on the next reload, marked
*"no longer being provided by the roomba_plus integration"*. Before
that they all read Unknown, including the zone a mission had just
finished.

Two faults. Region names are filled during a **map build**, so a sensor
platform listening to the status coordinator heard plenty and never
with names present: the entities appeared only when a map happened to
be built first. And the timestamp lookup keyed on a map id the Prime
sensors do not carry, so it never matched.

Both @chairstacker, who reported them with screenshots showing exactly
when each entity was created and when it went stale.

The sensors are also renamed: **"Last cleaned – Kitchen"** rather than
"Kitchen – last cleaned", which sorts with the `Schedule –` and
`Favourite –` entities instead of scattering through the list. His
suggestion.

## 🤐 A command the robot accepts and ignores

A robot can take a command into `lastCommand`, report `notReady: 0` and
`error: 0`, and simply not act on it. **@Young9898** documented three
routes to that state on one i3+ in a single day:

- the readiness sensor reading **Cliff** — a false drop-off on a dark
  patterned rug, which swallows every motion command until the robot is
  physically moved, and survives a reboot
- a **room clean sent away from the dock** — six of six launched from
  the dock, none of two from mid-floor, with a plain start working from
  the same spot a minute later
- a **stale map version**, already guarded separately

Enumerating causes does not scale: the first was diagnosed and written
down, and the other two are indistinguishable from it without a capture.
So the *symptom* is watched instead — if no mission opens within twenty
seconds of a room clean, Home Assistant logs a warning with the
readiness value and what it usually means.

His three reports arrived at that recommendation from three directions.

## 🏠 Room names on a local-only install

Zone names saved through the integration live in its own options and
need no cloud. `available_rooms()` read them — after an early return
that fired when no cloud coordinator existed.

So an install without cloud credentials got nothing.

The comment four lines below that guard says a first version of this
method *"lost every user-named room on installs without cloud
credentials"* and that six tests caught it. It came back as a guard
clause a few lines higher, and nothing caught it the second time —
every test builds a coordinator.

Found because **@Young9898** reported that local-only users have no way
to get region ids and proposed discovering them by launching real
missions one candidate at a time. The ids were already there.

## 🤫 Commands the robot accepts and ignores

A robot can take a command, report `notReady: 0` and `error: 0`, and
simply not act on it. **@Young9898** — writing his own client, so with
no integration code in the path — documented three routes to that state
on one i3+ in a single day:

- the readiness sensor reading **Cliff**, after a false drop-off on a
  dark patterned rug. Every motion command is swallowed until the robot
  is physically moved; it survives a reboot.
- a **room clean sent away from the dock**. @mdarocha explains why:
  cameraless i-series use the dock as their localisation reference, so
  without it the robot cannot navigate to a region at all. The official
  app behaves the same way.
- a **stale map version**, already guarded separately.

Enumerating causes does not scale. So the *symptom* is watched: no
mission within twenty seconds of a room clean logs a warning with the
readiness value and what it usually means.

## 🏷️ Error 1010 is a docking failure

Not "Clear path", which was an unconfirmed guess. **@utkjmitch's** robot
finished a mission, drove home, aborted the final approach two inches
short of a powered, working dock, and raised 1010 — hand-placed on the
same dock, it charged at once.

The same code appeared when his dock was unpowered ten days earlier and
was read as an obstruction for the whole time. Corrected in all eight
languages.

His robot's own abort history is now an attribute on the error sensor:
`bbpause.pauses` is a rolling ten-entry list nothing read, and his
carried **four docking failures in ten runs** while he experienced each
as a one-off.

## 🧭 The device tracker stopped guessing

Two reports, one root: states derived from what *should* follow rather
than from what the robot reports.

- It said **"Cleaning" for nine days** about a robot that had stopped
  transmitting at 36% battery.
- It said **"Docked"** about a robot flashing red two inches short of
  its dock — `stop` is a mission-end phase, and a failed docking
  reports exactly that.

An error is now reported as an error, and silence as silence.

## 🏠 Room names on a local-only install

Zone names saved through the integration live in its own options and
need no cloud. `available_rooms()` read them — after an early return
that fired when no cloud coordinator existed. So an install without
cloud credentials got nothing.

The comment four lines below that guard says a first version *"lost
every user-named room on installs without cloud credentials"* and that
six tests caught it. It came back as a guard clause a few lines higher,
and nothing caught it the second time — every test builds a
coordinator.

A second reader had the same shape: `PrimeRoomCleaning.available_rooms()`
filtered on metadata names alone, so a robot whose rooms are named in
the version endpoint got *"no named rooms yet — finish a mapping run and
name the rooms"*, which @utkjmitch had done. Both fixed, and the message
no longer asserts a cause it has not checked.

**@Young9898** found the first by reasoning from the architecture,
without running the integration at all.

## 🔒 Diagnostics no longer leak the robot's id

Every credential-shaped field was redacted and the blid still appeared
in clear text inside `map_id`, which is `<blid>-<epoch>` — a secret
hiding as part of a composite value, under a key that does not sound
sensitive. @utkjmitch had stopped attaching downloads because of it.

# 🧪 Why beta, and not 4.0.0

The Prime work has field time behind it. **The rebuilt 900-series pose
pipeline does not** — its calibration was checked against one robot's
stored data and synthetic cases, not a broad sample.

**If your map trail breaks up during ordinary cleaning, please report
it.** The threshold is meant to trigger only on genuine discontinuities.

And the section above is the other reason. Five bugs of one shape
surfaced in the final week of alpha, four of them silent — they produced
no error and nobody had complained. They were found by going looking,
which means the honest read is that looking harder would probably find
more.

A build guard now catches that particular shape. It cannot catch the
next one, and the state translations, the zone drawing and the cloud
consumables in this release have no field time behind them at all.

**Automations matching the status sensor's old value will stop
matching.** That is the one thing here worth checking before you update,
and the reason it is happening now rather than after 4.0.0.
