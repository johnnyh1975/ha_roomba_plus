# Roomba+ 4.3.4

**A run started at the robot is recorded as the whole home, the live
path of an i7+ keeps going after the robot falls silent for a minute
and stays on the rooms map when the map is turned in the iRobot app,
iRobot's error texts from the current app with roombapy-prime 0.6.0,

## A start at the robot took the last command's rooms

@Hardy-196's robot cleaned for 44 minutes after a start from its own
CLEAN button. The mission was recorded, and shown while it ran, as his
zone "Couch": Roomba+ takes a mission's rooms from the robot's last
command, and that still held the zone command Roomba+ had sent before.
A button start names no rooms; the mission says who started it
(`initiator: manual`).

- **A mission started at the robot takes no rooms from the last
  command.** One rule for every place that reads them: the mission
  record, the planned order and destination on the vacuum, room
  tracking and its time estimate. Starts from Home Assistant, the
  iRobot app and schedules read them as before.
- **A mission without rooms replaces the last plan** (Classic). The
  previous mission's rooms stayed the plan whenever its end had been
  missed.
- **A mission says when it was the whole home.** `mission_scope` on the
  vacuum while it runs and `scope` on the last mission summary and in
  the history: `rooms` or `whole_home`. A run with no rooms read as
  missing data before.

## Skipping the current room (#178), to try

`skip` is in the robot firmware's own command list, and the iRobot app
offers it; no robot has been seen to take it from Home Assistant yet.
`vacuum.send_command` with `command: skip` now sends it, on Classic over
the local connection and on Prime as a simple command, and keeps the
mission's state when it was sent and a minute later in the diagnostics
(`field_evidence.skip_attempts`). A button follows once it is confirmed.

## Collecting what the next question needs

- **Which command a starting mission found.** Whether a robot reports
  the running mission before its new last command decides how far that
  command can be trusted at a start. Each start now keeps the command
  it found (command, initiator, time, how many regions, how long before
  the start it was sent) and the next one the robot reported, under
  `field_evidence.mission_start_commands`. No room ids, no positions.
- **Every raw command is in the sent commands.** `vacuum.send_command`
  left no trace in the diagnostics.

## The live path stopped halfway through a mission

@pk-1966 watched a single-room mission of his i7+ (lewis 22.52.10): the
path stopped being drawn eight minutes in, at about 58 %, and the log
said the robot "does not answer position requests". It does. It had
answered every request until then, about one every 1.4 seconds; then
three requests went unanswered, and a minute later it answered all
three at once, 61 to 69 seconds late.

roombapy counts three unanswered requests as a robot that does not
implement position requests, and Roomba+ stopped asking for the rest of
the mission. The coverage map was right after the cloud sync; only the
live path was missing.

- **A robot that has answered before is asked again after a pause**:
  30 seconds, then 60, then every 2 minutes, up to ten times a mission.
  Asking every second through a stall would only queue requests the
  robot answers late. A robot that has never answered (an i3 on
  daredevil) is still left alone until its next mission.
- **The next mission asks again, even on the same connection.**
  roombapy keeps its "does not answer" until the connection drops and
  refused every later request without sending it, so a give-up carried
  over into the next mission, and every one after it, until a reconnect.
  Roomba+ clears it before each stream it starts.

The request rate is unchanged. The late answers to all three requests
point to a robot that was busy for a minute rather than one that was
asked too often; the pause keeps a stall from piling requests up.

## A map turned in the iRobot app turned the live path with it

@frnchfrgg checked 4.3.3 on his i-series (lewis): the rooms map and the
coverage map agree, and *Map rotation* turns both. The live path did
not: it came out in the orientation he had saved in the iRobot app. He
changed the orientation in the app, saved it, started a new mission, and
the path turned with it. So with a map turned in the app the path never
met the other two pictures, and *Map rotation* turned it a second time.

The robot answers position requests in the map as the app turned it;
the rooms map and the coverage stay in the map's own frame. 4.3.3's
notes put his 4.3.2 observation down to a coincidence. It was not one.

- **The path is turned back by the app's turn** before it is drawn. The
  cloud map's header names both angles, the map as the robot made it
  and as the user turned it; the difference is the turn. With the map
  left as mapped it is zero, and the path is drawn as in 4.3.3.
- **Read once per mission**, at its first position. A turn saved in the
  app during a mission reaches the robot at its next one, and the path
  drawn so far does not swing round.
- Nothing is stored from requested positions, so a mission drawn under
  an earlier turn leaves nothing behind in the wrong orientation.

The direction comes from his one turn, a quarter counter-clockwise in
the app with the header angle a quarter smaller. The diagnostics show
the turn applied (`position_chain` → `requested_path_turn_deg`).

## Error texts from the current iRobot app

Roomba+ showed iRobot's own title and explanation for an error code from
a copy of the table taken from the Prime app 3.0.0. It now takes them
from roombapy-prime 0.6.0, which carries the app 3.2.0 texts: the same
112 codes in the same eight languages, 173 texts reworded, most of them
clearer (Portuguese and Dutch especially).

Where 3.2.0 made a text worse, roombapy-prime gives its own:

- **234 (mop not in place)** says what to do again: attach the mop to
  mop; vacuuming works without it. 3.2.0 only said a "sweeping task" was
  possible.
- **4003/4004** say the dock's software is updating in all eight
  languages. 3.2.0 changed this in English only.
- **18/1010** in English start with "Place the robot on its dock to
  charge" again.
- French no longer writes codes like numbers ("(1 008)").

## Smaller changes from roombapy-prime 0.6.0

- **"Started by: Google"** for a mission a Google routine started. The
  library knows the value now; until 4.3.3 such a mission showed
  "None", as if the robot had said nothing about who started it.
- **A dock at wash level 4** (deep hot water wash, new in app 3.2.0)
  offers the same pad-wash heat levels as level 3, as the app does. The
  app's new "deep heat" value and new "smart" wash frequency appear on
  no screen of the app and are not offered here either.
- **Five more Prime models are recognised** (SKUs starting Q4, Q5, F2,
  W3, Z2). They already took the Prime path; setting one up no longer
  logs a request to report an unknown model.

## Under the hood

- `cloud_coordinator.umf_user_turn_rad()`: `user_orientation_rad` less
  `robot_orientation_rad` from the active map's header, in (-π, π], 0.0
  without both. `RoombaMapImage._handle_live_position()` turns the
  requested position and heading by it about the map's origin, read
  once per mission (`_live_position_turn()`). Diagnostics:
  `position_chain.requested_path_turn_deg`.
- `const.mission_command_regions()` and `ROBOT_SIDE_INITIATORS`
  (`manual`, `dockBtn`); used by `_capture_zone_names()`, the mission
  plan, `_get_planned_room_order()`, the vacuum's live destination and
  the pass-mode reason. `const.mission_scope()`, `MISSION_SCOPE_ROOMS`,
  `MISSION_SCOPE_WHOLE_HOME`; record field `scope`.
- `RoombaData.mission_start_commands`, `RoombaData.skip_attempts`;
  `callbacks._note_mission_start_command()`, `_note_next_command()`;
  `IRobotVacuum._async_send_skip()`.
- `LivePositionStream` remembers whether the robot has answered
  (`_has_answered`). From such a robot `RrtpUnsupportedError` is a
  stall: status `stalled`, a pause from `STALL_RETRY_DELAYS_S` via
  `async_call_later`, at most `MAX_STALLS_PER_MISSION` (10) per mission.
  The pause is cancelled at the end of the mission, when the option is
  switched off, and on unload.
- `_forget_library_verdict()` clears roombapy 2.0.2's
  `_position_unsupported` before each stream. It is a private attribute
  of the pinned version and is left alone where it does not exist.
- Diagnostics, `position_chain.live_position`: `has_answered`,
  `stalls_this_mission`, `waiting_to_ask_again`.
- **roombapy-prime 0.6.0** in `manifest.json`, the workflows and
  `quality_scale.yaml`. `vendor_errors.py` and its test file are gone;
  `const.get_localized_error_entry()` reads
  `roombapy_prime.vendor_errors.vendor_error()`. The library repairs
  broken placeholders on the way out, as the local copy did.
- `select_prime.VENDOR_VALUES_NOT_OFFERED` names the vendor values the
  pickers leave out on purpose (`HeatType` 3, `ReturnByMode` 103), with
  the reason; `check_vendor_value_tables.py` and the tests read it and
  fail on a stale entry. `_PAD_WASH_HEAT_LEVELS_BY_CAP` gains level 4.
- `JOB_INITIATOR_LABELS["google"]`, with the state in `strings.json` and
  all eight translations.
