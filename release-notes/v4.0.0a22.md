# Roomba+ v4.0.0a22

Requires roombapy-prime **v0.2.0b10** (unchanged from a21).

**This one is for Classic owners.** It fixes a wrong refusal that has been in place since v2.9.0,
found by analysing iRobot's own Classic app rather than by anyone reporting it.

## "The robot is updating its Smart Map" was shown for eight unrelated states

`cleanMissionStatus.notReady` was treated as a bitmask, with bit 64 meaning "Smart Map updating".
It is not a bitmask. The app decodes it as a scalar index into a readiness enum, with an offset:

```java
mReadyState = jsonInt <= 10 ? values()[jsonInt] : values()[jsonInt - 3]
```

Indexing an enum by the value would be meaningless if it were a mask.

The 64 was inferred rather than read, and the inference was close: wire value 67 decodes to
`DownloadingMap`, which really does mean the map is being updated. But `67 & 64` is true, and so
is every value from 64 to 71:

| Wire | What it actually means |
|---|---|
| 64 | Fleet disabled |
| 65 | Subscription expired |
| 66 | Dead navigation board |
| 68 | Off dock |
| 69 | Tank leaking |
| 70, 71 | Fluid level sensor broken |

So a user with an expired subscription was told to wait for a map update — a wrong reason they
could do nothing about, which is exactly what that error message set out to avoid. Five call sites were affected: two service guards, the repair-issue callback, the zone-clean button
and the map-saving binary sensor.

**Five call sites, not three.** Two of them did not use the shared constant at all — one carried a
bare `& 64`, the other a local copy under a different name — so a search for the constant's name
found the call sites and not the duplicated values. Both blocked real actions: the zone-clean button
refused, and the "map saving" binary sensor turned on.

All five now compare for equality with 67. A `decode_not_ready()` helper converts a wire value to
the readiness index the way the app does, for anything that needs the state rather than this one
case.

**Wire 11, 12 and 13 collide** with 8, 9 and 10 under that offset, and the app cannot tell them
apart either. They decode to the colliding index rather than to an error, because that is what the
robot's own app would show. Nobody has observed one; a diagnostics capture carrying one would be
worth knowing about.

## Also

Nothing else changed. Everything in a21 stands.

**A test encoded the bug exhaustively.** It asserted `sensor.is_on == bool(value & 64)` across 256
values, so 128 of them claimed the map was saving. The test agreed with the implementation and
neither had ever been checked against the robot's own app.

## The readiness sensor was showing states the robot never reported

Same root cause, one layer up, and it had **no test coverage at all** — which is why nothing
objected.

`NOT_READY_LABELS` had nine entries and **six were wrong** against the vendor table:

| Value | It showed | The robot means |
|---|---|---|
| 2 | Uneven ground | Wheel drop both |
| 16 | Bumped unexpectedly | Bin full |
| 31 | Fill tank | Schedule no clock |
| 39 | Pending | Charge timeout |
| 48 | Path blocked | Safety fault hardware |
| 68 | Updating map | Off dock |

Only "Ready" and "Low battery" held up.

**And entry 68 is where the bitmask story started.** Someone recorded "Updating map" at 68, `68 & 64`
is true, and a bit test looked like it worked. The state that actually means the map is updating is
**67**.

Below that table sat a bit-by-bit decoder that assembled labels like "Updating map, Pending task"
out of the same premise.

Both are gone. The sensor now decodes the value the way the app does and names the state from the
full 73-entry table — `Wheel drop both` rather than an invented phrase. Less fluent, and traceable
to a source, which the old labels were not. An unlisted value keeps its number instead of being
decomposed into plausible-sounding parts.

## Three error labels corrected

Checked against the vendor's own 173-code table; of 28 divergences, most were spelling or dropped
placeholders. Three said something else:

- **68** read "Updating map". Both the enum name (`CAMERA_HARDWARE_FAILURE`) and the app's text
  ("Camera issue") say otherwise, and they agree with each other. A user was told to wait while the
  robot reported a hardware fault.
- **216** read "Charging base bag full". It is the robot's own bin — sending someone to replace a
  bag when the bin needs emptying.
- **2** read "Main brushes stuck". That text is real, but it is the SKU override the app applies for
  one model prefix; the default is "Debris extractors stuck". The special case was being shown to
  every robot.

The remaining divergences are left alone. Where the vendor is vaguer than we are, being more
specific is a service rather than an error — and the table has stood in front of users for years.

## Two corrections to this project's own reasoning

Neither changes behaviour; both change what the code claims.

**The Prime error sensor's justification was incomplete.** It said APK analysis found no error-code
table for either generation. True of the app, wrong as a conclusion — the table lives in the
service. `GET /v2/help/{lang}/{country}/{sku}` returns a full Prime catalogue without
authentication: 43 error entries, 21 charging, 15 start-refuse.

The decision to show the raw code was still right, and there is now better evidence for it than the
single field capture it rested on. Of 16 codes present in both the i7 and the Combo 405 catalogue,
**all 16 point to different articles** — while two Classic models share 4 of 21. iRobot itself
treats these as separate namespaces.

**There are three different 671s, not two.** A comment here already corrected "671 does not exist in
the APK" to "two numbering spaces". It is three: the dock state we observe in `dock.pwState`, a
connection error `C671` in the app's raw resources, and a genuine Prime error code with its own help
article. Every round that got 671 wrong got it wrong by asking "same number?" instead of "same
field?".

## Field confirmations from a20

Neither needs a change; both close a question that was open.

**The live map works.** First confirmation since PR #65 went in, from a padless vacuum mission with
the Rooms Map open (@utkjmitch, Y351020): coverage and the robot marker drawing in behind the robot,
and the counters agreeing — 139 position messages, 173 points, 46 renders, **zero decode failures**.

Worth knowing for anyone else checking: a browser can hold a cached frame and make the card look
minutes stale while the image entity updates sub-second. A refresh clears it.

**`detectedPad` senses the carrier plate, not the cloth.** Established by the one experiment that
could establish it — the same robot reading `noPad` in one capture and `padPlate` in the next, with
nothing about a mop pad changed, only the bare plastic plate clicked back in during a rescue.

So the sensor is right and its name promises more than the field delivers. Nothing in this
integration gates mop behaviour on it, which is now a documented requirement rather than an
accident: the field cannot say whether a cloth is fitted, only whether the plate is.

## Combo robots keep their filter sensors

`is_mop()` answers "can this robot mop" and was being used to ask "does it have no brushes". On a
Braava those are the same question, which is why thirteen brush and filter gates were written as
`not is_mop(state)` and nothing objected.

On a **Combo** they are not the same: it mops *and* vacuums, so it was losing its filter wear and
filter-due sensors to a question about mopping.

A new `is_braava()` decides on the SKU prefix rather than a capability flag. Both were weighed:
`cap.binFullDetect` is absent on a Braava and present on every other platform in iRobot's own
sample data, but it can also be absent because a robot's firmware simply does not report it — and
that would strip the brush sensors off a working i7. A SKU cannot go missing on a robot that has
one, and when it does, the fallback is the old behaviour.

**No robot anyone owns changes behaviour.** Braava, i-series, s9 and 900-series all read exactly as
before; only a Classic Combo, which no field tester has, gains anything.

**One limitation stays, deliberately.** The maintenance store has a single slot used for a brush or
a pad depending on the robot, so `brush_last_replaced` and `pad_last_replaced` remain either/or. A
Combo getting both would see one number twice, which is worse than one unambiguous sensor. Fixing
it needs a second store slot.

**And one pre-existing oddity is now pinned rather than fixed:** `filter_remaining_hours` and
`filter_last_replaced` carry no gate at all, so a Braava gets them despite having no filter. A
different question from this one, and it deserves its own decision.

## Schedule switches from before this release are removed now

a21 said a deleted schedule's switch would disappear. It did — but only if the deletion happened
while Home Assistant was running.

The removal compared against a set of ids **the current session had added**. After a restart that
set begins empty, is filled with whatever exists now, and the difference is empty by construction.
So an entity whose schedule vanished while HA was down, or before the upgrade that added the
removal, could never be reached. @DaRealGuGu had four of them still sitting there on a21.

It now reads the entity registry instead, which is where those orphans actually live. Only switches
carrying this robot's schedule prefix are touched — a second robot in the same entry keeps its own,
and no other switch is a candidate.

That is the second correction to this claim in two releases, and the first one was written the way
it was because it only ever got tested against deletions that happened live.

## The live-map counters were counting arrival, not survival

A capture showed 2267 position messages and 5553 points, and no robot marker on the map (@DaRealGuGu,
a21). The obvious reading is that the data arrived and the drawing failed. It is not the only one.

`position_points` counts `len(message.updates)` — what the robot sent. Every sample after that can
still be dropped: one without a `point`, or a point without x/y, is skipped silently. **So 5553
points counted proves nothing about whether a single one reached the list the trail and the marker
are drawn from.** If none did, what remains on screen is the trajectories layer from the downloaded
bundle, which looks very much like a trail and is not one.

Three counters now sit where that decision is made — `trail_points_added`,
`trail_skipped_no_point`, `trail_skipped_no_xy` — and they add up to what arrived, so a shortfall
has exactly one place to hide. Diagnostics also carry `trail_points` and `trail_last_point`, which
cover the third possibility: a marker drawn outside the map's own bounds.

This is the same mistake as several others in this release, one layer further out. A counter that
increments where data arrives cannot tell you anything about where it goes.
