# Roomba+ v4.2.11

## Config entries on schema versions 4 to 10 could not be migrated

**If your Roomba+ stopped loading at some point and you never worked out
why, this may have been it.** An entry on one of those versions — from
the v2.1.x series — matched no migration step, never advanced, and Home
Assistant refuses to load an entry it cannot bring up to date. Nothing
in the log named the cause.

Seven per-entity migration steps were collapsed into a single version
jump some releases ago. The jump's condition was correct; it was nested
one level too deep, inside the branch for version 3 alone. An entry on 3
worked. Everything from 4 to 10 fell through.

Nothing is needed from you — the next start migrates the entry and it
loads.

Found by replacing a test that searched the migration source for the
condition's text with one that runs the chain from every version. The
old test was green throughout: the string was there, in a branch those
versions never entered.

## Config entries on schema version 20 or older could not be migrated

The step that brings a config entry from schema 20 to 21 checked a
variable for `None` that it had set to an empty string. None of the
checks ever held, so every entity that needed no change was renamed to
an empty ID, which Home Assistant rejects. The migration stopped and the
integration did not load.

This affects anyone upgrading from a release old enough to be on schema
20 or earlier — the same kind of fault as the one above. The
two renames that step exists for (`_battery` → `_battery_level`,
`_map` → `_cleaning_map`) now also run, as they always should have. The
new migration tests run against Home Assistant's real entity registry;
the old ones used a stand-in that accepted the empty ID.

## Fifteen entities report *Unknown* rather than *Unavailable*

*Unavailable* means Home Assistant cannot reach the device. *Unknown*
means it is fine and has no value right now — which is what a docked
robot that has never errored, or a fresh install with no mission
history, actually is.

This covers mission start and elapsed time (reported by **@naveso**),
the last-mission sensors, the error sensors, problem zone, consecutive
mission anomalies, estimated battery end-of-life, lifetime completion
rate, and the three maintenance timestamps. Tools that list broken
entities — Orphan Entity Cleaner among them — stop flagging these.

**Battery cycle count** and **Battery age** now disappear entirely on
robots that never reported the underlying data, rather than existing
permanently unavailable.

**If an automation tests these sensors for `unavailable`, update it.**
`has_value()` and numeric comparisons keep working unchanged.

## Live state goes *Unavailable* when the robot cannot be reached

**@mdarocha:** the robot ran its battery flat and dropped off the network.
The Connected sensor noticed within a minute — and the vacuum went on
reading *cleaning*, *ready*, 99 % through its mission at 1 % battery, for
three and a half hours, until the robot came back.

No entity had ever tied its availability to the connection; Home
Assistant's default of "always available" applied to all of them. Now,
once the local connection has been down for a minute, the entities that
describe the robot's current state become *Unavailable*: vacuum, phase,
readiness, battery, signal, position, mission progress, the active
mission's times, and the bin and mop status sensors. When the robot
reconnects they come back at once.

Settings the robot reports — edge cleaning, child lock, eco charging,
carpet boost, cleaning mode and the other settings switches and selects —
go *Unavailable* with it, instead of showing a value the robot is no
longer confirming. History, counters and the last mission keep their
values. **Connected** and **MQTT stale** stay available — they report
the outage.

**Prime robots**, which have no local connection, do the same when
iRobot's cloud stops delivering their state.

**Buttons that send the robot a command** — clean zone, repeat last
mission, favourites, locate and the rest — go *Unavailable* as well,
rather than accepting a press nothing will receive. The reset buttons,
which only record something in Home Assistant, stay available.

**If an automation reacts to the vacuum's state, it can now see
`unavailable`** whenever the robot is out of reach.

## "Finished cleaning" every hour on an idle Prime robot

**@1lyra:** the Activity log showed *finished cleaning* once an hour while
the robot sat on its dock.

The hourly Prime history sync decides which missions are new by the ids
already stored. It collected those ids through a date query — and that
query skips any record without a start time. Prime records written before
the start time fell back to the end time have none, so their ids were
never counted as known, and every sync rebuilt them as new missions. The
store recognised the duplicate and dropped it, but reported nothing back,
so the sync counted it as added anyway: it saved, re-ran the statistics
backfill and announced a completed mission.

For an older such record the effect was worse than noise — the duplicate
check only compares against the last five records, so the mission was
stored a second time and counted twice in statistics.

The sync now takes known ids from every stored record, and counts and
announces only what was actually stored. Records already stored twice
are removed at the next start, and the statistics — rebuilt from the
records at every start — lose the double count with them.

## Deleting the device of the robot you are still using

Home Assistant offers **Delete** on every device of an integration that
supports removing devices, not only on devices without entities. Roomba+
answered yes to all of them, including the robot the entry is set up
for, which cut its entities loose until the next reload.

The configured robot's device is now refused. Any other device of the
entry — a replaced robot, a device left over from an older release —
can still be deleted.

## Maintenance resets reported success for a robot they could not find

`reset_filter`, `reset_brush` and the other reset actions logged a
warning and carried on when given an entity that is not a Roomba+ robot,
so the action reported success and nothing was reset. The cleaning
actions have always refused such a call; the reset actions now do the
same.

**If an automation calls a reset action with a wrong entity, it now
fails with a message instead of passing silently.**

## Buttons that did nothing now say why

A press that could not do anything used to end without a word: no zone
chosen, the robot updating its map, no previous mission to repeat, no
learned room yet, a favourite without commands, a part iRobot's cloud
does not list or would not confirm. The button was pressed, nothing
happened, and nothing said why. Each of these now shows a message, in
your language, saying what is missing.

## *Clean zone* on robots with more than one map

On robots whose firmware does not report its maps locally — the lewis
firmware of the i-series — the button looked up the map's version from
the robot's last command. When that command had been on another map,
there was no version to find, and the button silently did nothing.

The version was never sent: including it is what caused error 224 in
the past, and leaving it out is what roomba_rest980 does as well. The
check guarded nothing, so it is gone. The check that stops a zone clean
while the robot is rebuilding its map stays.

## A maintenance reset shows at once

After a reset — by button or action — the remaining hours, the
replacement date and the due status updated only when the robot next
sent a message. The reset path re-wrote each sensor's *old* value with a
new timestamp, or refreshed only the button itself. Every entity of the
robot now redraws from the new data straight away.

## Side brush and Clean Base bag reset buttons on local robots

These existed only when iRobot's cloud reported the part, and Classic
robots never receive that data — a fully working cloud connection still
returns no consumable list for them. So a locally operated robot had no
way to reset those counters at all, and the maintenance sensor stayed
overdue for good after a replacement.

They now appear for any robot that has the parts. A Braava still gets no
side-brush button; a robot without a Clean Base still gets no bag
button. Pressing one records the replacement locally and then reports it
to iRobot if there is a connection — the order the filter and main-brush
buttons have always used, so a cloud outage no longer costs you the
reset.

## `clean_sequence` used an API Home Assistant is removing

It relied on `async_track_state_change`, which Home Assistant scheduled
for removal and which writes a warning to your log every time it is
used. It now uses the replacement. Behaviour is unchanged: the second
robot starts once the first has docked, once, with the delay you set.

## Error messages in your language

Every error Roomba+ can show — 123 of them — now has a translation in
all eight languages; 62 had been English only. Eight messages named a
placeholder, such as the entity concerned, without the code supplying
it, so the text came out broken; they now say which robot or entity is
meant.

The notice about obstacles the robot detected on the cloud map carried
the text of the zone-naming notice by mistake, in every language: it
asked you to type zone names into a notice that has no field for them.
It now says what it means — the cloud has seen obstacles, a few
cleaning runs will confirm them, and a keep-out zone in the iRobot app
is the way to avoid one for good.

## Every field in setup and options explains itself

Twenty-six fields in the setup and options forms had no description
below them; now all do, in all eight languages. Two option lists — what
happens when a start is blocked, and how presence scheduling decides —
were English in every language; they are now translated.

## Duration sensors look like durations

Seventeen sensors that measure time — remaining filter and brush hours,
days until a part is due, mission and recharge times, total cleaning
time, uptime — now carry Home Assistant's duration device class. **They
are displayed as durations, and you can pick the unit** in the entity
settings. Stored values and history are unchanged.

## Missions that got stuck and gave up counted as completed

When a robot gets stuck, Roomba+ reads iRobot's mission record to decide
whether it carried on afterwards — *stuck and resumed*, which counts as a
completed mission — or gave up. It counted every room finished in the
mission: also the rooms finished **before** the robot got stuck, and the
room it gave up in, which the firmware closes when the mission ends. A
robot that cleaned two rooms and gave up in the third was recorded as
having resumed, and the completion rate rose with it.

Now only what happened after the stuck counts: a pass the robot finished,
or its drive home. Missions already stored keep their result.

## Long-term statistics after a history import

Importing past missions into Home Assistant's statistics wrote each
mission's own value where a running total belongs. Graphs showed
negative changes, and two missions in the same hour overwrote each
other. The import now writes running totals, one entry per hour, in
order.

## A room missing from the room history

**@Thonno:** a mission cleaned four rooms, the iRobot app showed all four,
and Roomba+ recorded three. The Kitchen — the first room of the mission —
kept its date from two days earlier.

On a Classic robot with a cloud account, room history is built from
iRobot's own mission record, whose room events carry a `status`. Roomba+
counted a room only when that status said the pass had *finished*. The
iRobot app, it turns out, does not look at the status at all: decompiling
the app (7.18.0) showed the value is read and never compared, and a room
with any room event is shown as cleaned. A room the robot cleaned but did
not finish — cut short by a recharge, a time limit or the end of the
mission — was in the app and missing here.

Room history now counts a room whenever the robot cleaned floor in it. It
stays one step stricter than the app on purpose: a room event with no
cleaned floor does not count, so a room the robot skipped cannot slip in.

**Everything that decides when a mission has ended, and every learned
figure, still counts only finished passes.** These had shared the same
rule, and loosening it there would let a room still in progress close a
mission after its first room, or let half a pass shrink a learned room
size. The two questions are now separate, and a test pins which part of
the code asks which.

**If you stop a mission part-way through a room,** that room's *last
cleaned* time now moves to that mission.

The diagnostic also shows the newest mission's room events — status,
reason, pass and area for each region — with the regions counted as
cleaned and those whose pass finished listed side by side.

## Room coverage for rooms cleaned in a single pass

Room coverage — how much of each room the last mission covered — was
reported only for rooms the robot went over twice. The firmware writes the
cumulative covered area only from the second pass on; a room cleaned once,
which is the usual case, carries only the area of that one pass, and
coverage skipped it. It now uses that figure.

The same misreading made the per-room dirt index divide by the room's size
after one pass and by the covered area after two, so a room's figure moved
with its pass count. It now always uses the room's size.

## Smaller fixes

- An implausible timestamp from the robot or the cloud no longer breaks
  the update it arrives in; five places could raise on one.
- Entering an invalid zone name in the options closed the step without
  saving and without saying why; it now shows the error.
- Removing or reloading the integration left some entities subscribed to
  robot messages; every subscription is now released.
- Actions are registered once when Home Assistant starts, and a call
  aimed at a robot whose entry is not loaded says so.
- A file check that ran inside Home Assistant's event loop on every map
  fetch now runs in the background.
- A mission whose last room the firmware closed at mission end with
  status 5 is now confirmed from the cloud record straight away, rather
  than after the 90-second cap. Status 6 was already accepted.

## The mission callback, restructured — no change in behaviour

This is the code that decides when a mission starts, which room the
robot is in, and when a mission has really ended. It had grown into one
1,230-line function whose state lived in eighteen hidden variables that
any branch could change. That is where most of the "fixed it in one
place, missed its twin" bugs of the past weeks came from.

Its state is now one named object, and its logic five named steps:
recognising a mission start, detecting the end of a drive, advancing the
room display, moving to the next room when a drive ends, and confirming
the end of the mission. The function that remains is half the size.

**One real inconsistency surfaced.** The end-of-mission check and its
own log line computed the same decision separately, and disagreed about
a streak with no recorded start time — the log read it as held for 0 s,
the decision as held since the computer booted. They agreed in practice
only because another part of the callback always sets that start time.
They now share one computation, and a test pins the rule they rely on.
So when a log says a mission was not yet closed, and why, that is what
the code actually decided.

**How this was checked without a robot:** a real three-room mission from
the field log — dock drive, two room changes, the drive home, three
refused end signals at the dock, then completion — replayed through the
code before and after the change. Identical room changes, identical
refusal times to the millisecond, identical end. It is now a permanent
test, with its expectations taken from the field log rather than from
the code under test.

## Measured against Home Assistant's quality scale

This release measures Roomba+ against every rule of Home Assistant's
integration quality scale, rule by rule and against the code rather than
the claims. Doing that found real faults, most of them invisible until
something went wrong: the schema 20 migration, deleting the live robot's
device, maintenance resets reporting success, broken and untranslated
error messages, the misplaced obstacle notice and the statistics import
above all came out of it.

`quality_scale.yaml` now states, for all 52 rules, where each is met; it
had claimed several that were not.

## Under the hood

- **Background work is owned by the config entry.** Forty-two places
  scheduled tasks on Home Assistant itself and kept running after a
  reload, including statistics backfills writing to stores that were
  being closed. Twenty-one used a bridge that swallowed exceptions
  entirely — repair checks after every mission among them
- **The four stores whose contents cannot be rebuilt** now record a
  payload version, so a future format change is refused cleanly instead
  of misread. Existing files are read as the current format
- **The REST endpoints send `X-Roomba-Plus-Api-Version`**, so the
  Lovelace card can eventually check what it is talking to
- **Shared read paths** for the coverage baseline, the mean mission
  duration and the MQTT silence reference, each of which had been
  reimplemented in two or three places
- **Guard tests for the rules that can drift** — translations and their
  placeholders, icons, device classes, form descriptions — so they cannot
  quietly break again
- **Four tests changed shared entity classes** for the rest of the test
  run, so later tests could pass or fail depending on order. Fixed, with
  a guard against the pattern
- **A coverage gate in CI**: every module must stay above 95 % line
  coverage, counted from `coverage.xml` rather than the rounded report
- **Removed:** the unused `CloudRawSensor` class, a duplicate loop in the
  device tracker, thirteen translations for sensors merged into others
  long ago, the room-type research log (the research is complete), four
  unused service-name constants and seven unused imports, on which the
  lint job had been failing. Icons set in code moved to `icons.json`

8,270 tests pass; `mypy --strict` clean across 84 source files. Every
module has test coverage above 95 %, counted exactly; the config flow is
