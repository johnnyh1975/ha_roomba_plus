# Roomba+ v4.0.0a13

Room cleaning now goes through one path for both robot generations, and a multi-floor bug that
could clean the wrong room is fixed.

## Room ids now carry their map

Room ids are assigned per map and start low, so two floors almost certainly both have a room "1".
Cleaning sent the id against whichever map the robot happened to be on — so picking a downstairs
room while the robot sat upstairs cleaned the upstairs room instead. Silently, because the id was
perfectly valid there too.

Ids are now qualified with their map, so the map comes *with* the room rather than being inferred
from where the robot is standing. Asking for rooms on two different maps in one call is refused
rather than half-executed.

Two testers have multi-floor accounts, so this was reachable rather than theoretical. It was found
by feeding deliberately inconsistent data — both halves of the code were individually correct.

Related: if the robot reports being on a map that is not in its own map list (carried to another
floor, or a map deleted in the app while Home Assistant was running), that report is now ignored
rather than trusted.

## One path for both generations

`clean_room`, HA's Clean Area segment list and segment cleaning all go through the same backend now,
for Classic and Prime alike. `vacuum.py` holds no cleaning logic at all.

Moved rather than rewritten, which mattered: an earlier attempt copied the Classic code and lost the
cross-map conflict rules, the map-updating readiness check, cloud enrichment of stored zone data and
a distinct error message. Existing tests caught all four, plus a missing guard and two entity
attributes that a mechanical rename had silently left behind.

## The map is stored less often

Persisting the map on every frame meant about 26 writes per mission — roughly 17 MB, and 6 GB a
year on a daily schedule, on hardware that is commonly an SD card. Only the last frame is ever read
back. Writes are now coalesced, so a burst of frames produces one.

## Fixed

- **Uninstalling now deletes the stored map.** A new store had been added without a matching removal
  entry, so removing the integration left behind a file containing a picture of the user's home.
- **`push_freshness` no longer claims a fault where there is none.** It used to read "the stream is
  not delivering"; shadow updates arrive on change, and a robot parked on a full battery changes
  little, so zero messages after a restart is expected. That wording sent its own author hunting a
  connection bug on a robot that simply had nothing to report.
- **Diagnostics now report whether the ROBOT is connected to iRobot's cloud**, and whether the login
  carries a token expiry. An offline robot and a broken push stream look identical from the outside
  — shadow reads keep working either way — and they need opposite responses.
