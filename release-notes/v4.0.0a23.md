# Roomba+ v4.0.0a23

Requires roombapy-prime **v0.2.0b11**.

The robot marker is fixed, and it was never a rendering problem.

## The trail was empty on every robot, always

`detectedPad`, contrast, marker size, draw order — three releases went into making a marker visible
that was never being drawn, because the list it is drawn from never received a single point.

Two lines did it:

```python
x_m, y_m = getattr(point, "x", None), getattr(point, "y", None)
if x_m is None or y_m is None:
    continue
```

`PositionSample.point` is a plain `(x, y)` tuple. There is no `.x`, so every sample was skipped —
while the counter beside it dutifully recorded them arriving. That is @DaRealGuGu's capture
explained: 2267 messages, 5553 points, no marker. What he was looking at was the trajectories layer
from the downloaded bundle, which looks like a trail and is not one.

**The defensiveness is what hid it.** An exception would have been found in a day; a silent
`continue` written against a shape nobody had checked survived every release. A test written in a22
used the same wrong shape and passed.

Paired with b11, which fixes the other half: the keep-alive slept before its first ping, so on some
accounts nothing was published at all.

## Choose which map is shown

Accounts with more than one map could only ever reach one of them — the image renders the map the
robot reports standing on and falls back to the first (issue #45, @chairstacker: "Whole House" with
seven rooms, "Master_Bathroom" with one).

A new **Map** select offers the map names, with "Follow the robot" as the default. A user who never
touches it sees exactly what they saw before.

A select rather than one image entity per map, because the person who would live with it asked for
that: entity-per-map lets two dashboards show different floors, and gives no way to keep a
rarely-used map off a dashboard at all.

**A prerequisite came out of building it.** The check deciding when to re-read the map compared
`p2maps[0]` while rendering a different one — so on a two-map account, a change to the map on screen
went unnoticed and a change to the other one forced a pointless refresh. It also compares the map
**id** now: moving between floors changes which map is rendered without either version moving.

## Dock buttons appear only when the dock can act

They had no availability rule at all — pressable whenever the capability existed. @chairstacker
pressed Wash Pad with a tank removed, the robot complained out loud and the dock reported 671; the
app would not have offered that button.

The rules are now the app's own: wash at pad-wash state 601, start drying at 701 or 703, stop drying
at 702, empty bin at 301, 355 or 305. Everything is disabled during a mission or a dock error.

**Return to base was skipping the guard entirely** — it called the command directly rather than
going through the shared path, so it was the one control that still fired mid-cycle.

**Unknown means available.** A robot that does not report a sub-state keeps its button; taking
function away because a field is missing is the worse mistake.

## Errors say how serious they are

The Prime error sensor shows a raw number deliberately — iRobot gives Prime and Classic different
help articles for the same code, so no label of ours would be sourced. A severity is not a label:
it is iRobot's own classification, and it answers what a bare number cannot.

171 codes now carry `severity` and `partially_operable`. Camera faults, battery failures and expired
subscriptions are the urgent bucket; 671 is in the workaround bucket, matching the dock's own
"switched to vacuum only".

## Also

- **Three pad values were missing** — including one that made a Braava jet m6 show "Unknown" for a
  fitted wet pad, because iRobot spells the same value two ways across platforms. Found by running
  the capability gates against iRobot's own sample robot states, now kept as test fixtures: seven
  platforms covering hardware nobody in the group owns.
- **The schedule services contributed in #49 (@utkjmitch) have tests**, aimed at the places where
  being wrong is expensive: the lock discipline, the sole-occupant delete decision, and never
  writing a container list built from a read that failed.
