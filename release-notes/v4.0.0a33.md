# Roomba+ 4.0.0a33

Requires **roombapy-prime 0.3.0b4**, pinned automatically.

Six new controls, a phase display that showed wire values instead of words,
and a capability gate that was fetched and thrown away.

## Your combo robot has been showing you `padWash`

Six mission phases had no label, so the sensor fell through to the raw wire
string. A combo robot spends real time in three of them at the end of *every*
mop mission:

```
padWash  → Washing pad          hmUsrChrg → Sent home to charge
padDry   → Drying pad           mapupd    → Updating map
refill   → Refilling tank       chgerr    → Base unplugged
```

No crash, no failing test, and it looked deliberate — which is why it survived
this long. Four cycle labels were missing too (`dockupg`, `tidy`, `manual`,
`monitor`).

## Six new settings controls

All from iRobot's own value sets, not from the per-SKU picker lists:

| Control | Values |
|---|---|
| Mop dry duration | 2–6 hours |
| Mop wash frequency | after each room · by time · by area · Standard · Medium · High |
| Mop wash area interval | 6 · 8 · 10 · 15 · 20 |
| Mop wash time interval | 10 · 15 · 20 · 25 |
| Heated mop water | no heat · default · high |
| Auto-empty frequency | depends on your dock |

**That distinction cost real work and it matters.** The per-SKU lists return
what one product mode's picker shows, and a robot can sit outside them.
@chairstacker's robot reports an auto-empty frequency and a mop wash frequency
that appear in *neither* list — and both are correct. A control built from the
narrow list could not have shown his own settings, and his first tap would have
changed one he never chose to change.

His Mop Wash Frequency screen in the iRobot app shows nothing selected at all,
because his value is in a range the new app UI dropped. This control can
display a state the vendor's own app cannot.

**Two controls adapt to the hardware.** Auto-empty frequency offers three
options on one dock and nine on another, from `cap.autoevac`. Heated mop water
offers two levels or three, from `dock.cap.pw`. A dock that supports neither
gets no control rather than a control with no options.

**And presence decides, not hardware.** @utkjmitch's robot has an auto-empty
dock *and* reports the capability, but has no frequency setting — and the
iRobot app offers him none either. The settings key list tracks what is
user-configurable on the model, not what is installed. No capability flag can
answer that, so the key list is read directly.

## Pad drying could not be switched off, and now can

App 3.0.0 greys out every Dock Control once a dock task starts. Tap one and it
answers "Dock task in progress. Try again later" — so a drying cycle cannot be
stopped from the app once begun.

The robot disagrees with its own app: stopping works, confirmed on hardware.
That block is client-side.

This integration keeps the stop button available for exactly the state where
drying is running, which is the moment the app refuses. Reported by
@chairstacker, who asked for the difference to be kept, and it is now guarded
by tests so a later "align with the app" pass cannot quietly remove it.

## A setting was offered for a dock that cannot do it

`padDryAllowed` had no capability gate at all. The vendor's own table puts pad
drying under `dock.cap.pd`, a *dock* property — and every switch description
could only name a *robot* capability. The dock capability was already being
fetched at the call site and discarded.

A robot on a base without pad drying was offered the setting anyway.

## Favourites, third attempt

Not announced as fixed. Comparing the Classic and Prime paths properly turned
up three differences, any one of which alone empties the list; two are
addressed in 0.3.0b4, and the third is left alone deliberately until the data
says whether it applies.

What changed here: when favourites are dropped, it now says so. "7 of 7 were
not offered as buttons" is a next step; silence was a shrug, and silence is why
two reasonable fixes could neither be confirmed nor ruled out.

## Also in this release

- **Consumable parts named by the app 3.0.0 vocabulary** (`main_brush`, `bag`,
  `sensor` …) as well as by number. A server switching would have produced
  "Replace main_brush" in the maintenance list.
- **`padWashesUsed`** — iRobot spells this count type two ways and only one was
  handled, so a robot using the other showed a bare number.
- **The region type in a schedule docstring** said `"furniture"`, propagated
  from a library value that was wrong. Nothing read it, so it misled readers
  rather than code.
- **`CYCLE_LABELS` was read by nothing.** The orphan guard checks private
  *functions*; this was a public *constant*, and it went straight through. The
  guard now covers both — and caught a second one the same day.
- **A third argument that `allowed_modes` is not the operating-mode bitmask.**
  Fault 287 says vacuuming is impossible and reads 2, which is the vacuuming
  bit. The two are exactly swapped against that reading.

## Upgrading

HACS will pull the pinned library automatically. If you install manually,
upgrade both.

Note for anyone checking: **zero pip lines in the journal at boot does not mean
the install was skipped.** Home Assistant handles the git-URL change silently.
`pip show roombapy-prime` inside the container is the check that answers it
(thanks @utkjmitch).
