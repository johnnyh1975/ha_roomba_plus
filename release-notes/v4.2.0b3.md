# Roomba+ 4.2.0b3

Everything in b1 and b2 still applies — see those notes for the async
rewrite and what is worth testing. This adds the fixes from a day of
field reports.

## Every room was also offered as a zone

The fix that also went into 4.1.3, and the one behind two reports that
looked unrelated.

Room ids have carried their map since 4.1.0 — `<map>/<room>` — but the
check that stops a room being repeated in the zone list compared those
against bare region ids. `MAP-A/11` never equals `11`, so every room was
emitted a second time under a zone id. Reproduced from @theChef163's
diagnostics: 21 segments where 11 were meant.

The selector keys by name and collapsed each pair, so it looked like a
missing zone. The area-mapping dialog keys by id and showed both, so it
looked like mixed lists. One line, two symptoms.

## A bin evacuation could open a phantom mission

Sending a robot home while it is already home runs an evacuation, and
during it `phase` alternates `charge`/`run` while `cycle` stays `evac` —
with the `run` messages carrying the *previous* mission's id, possibly
days old. Roomba+ decided a mission had started from `phase` alone.

`cycle` decides now. Established by a controlled test rather than
inferred: one `dock` command to a robot at 100% on its dock, nothing
sent before or after, every packet captured (@AlakazipLabs).

**Related:** `vacuum.return_to_base` on a docked robot empties the bin,
because that is what a `dock` command means when the robot is already
home. Not suppressed — deciding the robot is docked would risk
swallowing a real recall — but now documented.

## Classic robots offer every map's rooms too

Home Assistant's area mapping showed only one map's rooms on a Classic
robot — whichever the cloud happened to list as active. A room on
another floor could not be mapped to an area at all, and a mapping made
while one map was active silently stopped working when that changed:
the clean command dropped the unrecognised prefix without a word.

`clean_rooms()` has resolved the map per region since 4.1.0 — "every
requested region carries its own map" — and only this path was left
behind. It now offers rooms from every map, each id carrying its own,
and sends a stored id to the map it names rather than discarding it.

Rooms from two floors in one command are refused, with the message this
project already had for that. And the self-healing that repairs ids
after a map retrain now checks against the segment's own map, which is
where it was quietly undoing the fix one step further down.

## Which floor the robot is on

A robot reports its map only while it knows where it is. Parked on its
dock it reports nothing, which is exactly when somebody presses a
button.

Roomba+ now remembers the last map the robot reported and says whether
an answer is the robot speaking or the last thing it said. A dock does
not move: the floor it last cleaned is where it still is, unless a
person carried it — and that person knows they did.

The room/zone selector exposes this as attributes, so a dashboard can
show which floor a room is on **before** the button is pressed.
Cleaning a room on another map is warned about in the log, naming both
maps, and never refused: refusing would block the carried-upstairs case,
which is the only reason anyone does it.

That warning exists because @chairstacker targeted a room on his
secondary map and got three minutes of wandering and an unexplained
error 69, with nothing in the log connecting the two.

## The client was reading the certificate store on the event loop

Home Assistant caught it on a live install:

> Detected blocking call to load_default_certs inside the event loop by
> custom integration 'roomba_plus'

Building the robot client also builds a TLS context, and that reads the
system trust store from disk. The b1 migration took the construction out
of the executor with a comment saying the constructor does no I/O. It
does. The context is cached, so the cost was paid once per start — once,
on the loop.

Found in a log a tester sent for something else. The same log showed
eleven and a half hours of connection with no reconnect and no error,
which is the more useful half of it.

## A counter was named after something nobody has seen

`robot_lifted` in the mission API came from the robot's pick-up counter.
@AlakazipLabs retracted his own earlier claim that the counter witnesses
a lift: eight of ten increments had no wheel-drop reading, six of those
fell inside a dock-contact window, and it did not move when he placed
the robot on its dock by hand.

The number stays — it correlates with missions that went wrong — and now
also appears as `pick_events`, named for what was measured.
`robot_lifted` is unchanged for anything already reading it.

## Which settings this robot actually accepts

A wire census of every preference key, one write at a time
(@AlakazipLabs, i3): five land as single writes, one works only as a
pair, and three are dropped in silence — the write returns, nothing
echoes, the switch snaps back and no error appears anywhere.

Every switch Roomba+ builds is in the first group. The count is now in
the code, and a guard fails the build if any of the three dropped keys
is ever sent alone.

## Two things in the log

**Diagnostics always said "no rooms map entity"**, whether one existed
or not — the lookup used a different id shape from the one the entity
registers under. Two people sent files carrying that note while their
map was on screen and working.

**A deprecated Home Assistant call** was naming this integration in
everyone's log, with a deadline of 2027.8. The replacement does not
exist in HA 2025.5, the minimum supported here, so the call is chosen at
runtime.

## Still what this beta is for

No part of the async rewrite has run against a real robot beyond one
900-series reporting sensors, start and stop correctly over eleven
hours. The failure to watch for remains **a command that silently does
nothing**.
