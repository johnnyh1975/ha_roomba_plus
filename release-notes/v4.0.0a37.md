# Roomba+ 4.0.0a37

Requires **roombapy-prime 0.3.0b7** — upgrade both, and tag b7 first.

Six fixes, and every one came from a field report.

## Favourite buttons showed every robot's favourites

`GET /v1/user/favorites` is **account-level**, and nothing filtered by robot. A
two-robot household saw both robots' favourites listed under each of them.

@scenicsystemsllc's severity analysis is the part worth keeping: pressing a
mislabelled button commands the robot it is displayed under — correctly, over
that robot's own connection — but with a payload built from a **different
robot's map**. Usually a no-op or an error. In the worst case a region id is
coincidentally valid on the receiving robot's map too, and it cleans somewhere
nobody asked for.

Each favourite says which robot it is for, so the filter is a direct match
rather than the region-id heuristic the report suggested. A favourite that
names no robot is kept and shown everywhere.

**Pressing one now works too** — that half is fixed in b7.

## Mission sensors did not refresh across back-to-back missions

Also @scenicsystemsllc, flagged honestly as a hypothesis. Their value comes
from the mission store while their refresh was triggered by an MQTT delta, and
mission-end processing is debounced — so the delta that triggers a recompute
can arrive before the record exists. With a gap the next delta cleans it up;
back to back, the next delta belongs to the next mission.

Eleven sensors now refresh when the store gains a record, so the refresh
trigger and the value source finally agree.

## Zone names were lost when a mission included a recharge

Also @scenicsystemsllc. Cloud and local records were matched on **end**
timestamps within 120 seconds. A robot that runs its battery down docks,
charges and resumes ends its mission an hour or more after either side first
called it over — and widening the window would start matching neighbouring
missions.

Matched on **start** time now. A recharge moves the end, never the start.

## The robot and its trail appeared on the wrong map

@chairstacker. Zones, the robot marker and the trail all come from the live map
bundle; a36 bound the zones to the map being drawn and left the other two
reading it unchecked. Selecting a different floor plan drew the run over a
second map's rooms.

Same rule for all three now, with the same fail-open contract: an unknown map
id counts as matching, because a single-map household must not lose its live
position to fix a multi-map one.

## A control was hidden when its value was unusual

Promised in issue #46 and not delivered until now: a setting whose value is not
in this robot's known list made the entity **unavailable** — reproducing
exactly the "not set" the iRobot app shows, and looking like our bug rather
than theirs.

@DaRealGuGu's 515 holds a pad wash interval from another series' value set.
Neither his app nor our control could render it. The raw value is shown and
offered now.

## Pad washing allowed

The sixth control from issue #46, withheld on a reading of the older iRobot app
that suggested it could only be written as part of a bundle. **App 3.0.0
inverted that**: it writes these keys individually, and this one is among them.

## Also

- **A guard for the two hand-written strings each control carries.** A wrong
  `wire_key` produces a write the robot ignores; a wrong `model_attr` makes the
  control permanently unavailable. Neither raises, and both have happened here.
- **Phase sets consolidated.** The "is it cleaning" set existed as three
  identical literals in three files, and only one carried the reasoning —
  including why `evac` deliberately differs from the vendor's own rule table. A
  copy without the reasoning is the one that gets "corrected" later.

## Upgrading

Nothing changes an entity id or an action's arguments.

If you have more than one Prime robot, expect **fewer** favourite buttons per
robot — the ones that disappear belonged to your other robot.
