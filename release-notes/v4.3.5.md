# Roomba+ 4.3.5

**A skip, pause or resume no longer wipes a room mission's plan, the
entry is set up again after a late cloud answer instead of being left
half unloaded, and the diagnostics no longer report a map turn or a
missing cloud where there is none.**

---

## A skip wiped the mission's plan

A tester tried `skip` (4.3.4, #178) on an S9+ during a `clean_room`
mission to two rooms, Foyer then Bathroom. Right after it, the vacuum's
`planned_room_order` and `mission_destination` went to null and stayed
there, while the robot kept cleaning. While a mission runs, Roomba+
reads its rooms from the robot's last command, and after a skip that is
`skip`, which names no rooms. A pause or a resume becomes the last
command in the same way.

- **The command that started the mission is kept**, and a pause,
  resume or skip after it is passed over when the mission's rooms are
  read: the planned order and destination on the vacuum,
  `mission_scope`, the rooms recorded with the mission, room tracking
  and the end-of-mission check. Any other command, a new start
  included, is read as before.
- After a restart of Home Assistant in the middle of a mission, the
  start is not known; the rooms then come from the last command as
  before.

**Skip itself did nothing on that S9+.** The robot recorded the
command (`last_command: skip` in the diagnostics) and stayed in the
first room. That is one robot; `skip` stays available to try, and
`field_evidence.skip_attempts` still records each attempt.

## The reload after a late cloud failed with KeyError

4.3.3 sets the entry up again once the cloud first answers after a
failed start. On the maintainer's 980 the start failed (iRobot's
discovery answered HTTP 429), the login retry ten minutes later
succeeded, and Home Assistant logged "Error unloading entry Roomba for
roomba_plus" with `KeyError: 1`: the entry was left half unloaded
instead of set up again, until the next restart.

- **The listener that triggers the reload is removed once.** It removed
  itself when the cloud answered, and the reload's unload removed it a
  second time, which Home Assistant's coordinator does not allow.
- **The warning at a failed start says what happens next**: the login
  is retried every 10 minutes and the entry is set up again then. It
  said "up to 24h", and to reload by hand.

## Diagnostics

- **`position_chain.requested_path_turn_deg` is `None` without a cloud
  map.** A robot with no Smart Map, such as a 980, showed `0.0`, which
  reads as a map the app has not turned.
- **`favourites.source` tells a cloud that has not answered yet from a
  missing one.** After a failed first fetch it said there was no cloud
  coordinator; it now says the cloud has not answered yet and points to
  `cloud.last_exception`.

## Under the hood

- `const.IN_MISSION_COMMANDS` (`pause`, `resume`, `skip`) and
  `const.mission_command(last_command, held)`. `mission_command_regions()`
  and `mission_scope()` take the held command; every caller passes it,
  which a test checks. `RoombaData.mission_command` is set by the
  mission callback (`_hold_mission_command()`) from every `lastCommand`
  that is not one of those three. Diagnostics:
  `field_evidence.mission_command` (command, initiator, time, region
  count).
- `_reload_once_the_cloud_answers()`: one `_remove_once()` for both the
  listener itself and the entry's unload.
- Diagnostics: `requested_path_turn_deg` is read only when the umf has
  `poses.orientation_rad`; `_favourites_diagnostics()` separates a
  coordinator without data from no coordinator.

## Tested

- The full suite passes on Home Assistant 2025 and 2026; ruff, the
  typing baseline and the per-module coverage floors pass.
- Every new test was checked against the code without its fix and failed
  there.
