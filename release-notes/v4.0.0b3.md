# Roomba+ 4.0.0b3

Requires roombapy-prime 0.3.1, unchanged from b2.

Three findings from the two days after b2, all from reports.

---

# 🏠 `current_room` says how it knows

**@ScenicSystemsLLC** reported it disagreeing with where the robot
physically was — twice, once late in a mission and once early — then
read the source and found the mechanism himself: the value comes from
elapsed mission time against per-room estimates and never checks a
position.

The obvious fix is a position-based resolver. His diagnostics say it
would produce nothing on his hardware: `cap.pose: 2`, `position: null`,
`point_count: 0` after months of missions.

So there is a new attribute, `current_room_source`, reading `estimate`
or `mission_timer`. The sensor still gives you a room — it is right
most of the time — but it no longer asserts one without saying where it
came from.

**`cap.pose` does not lie — it was being misread.** The lewis firmware
sets it to a **compile-time constant**, so it says nothing about
whether a robot publishes a position. Seven robots showed a perfect
split — 1 reports, 2 does not — which reads like causation and is a
correlation with model generation.

`reports_local_pose()` now answers the actual question by checking for
an arriving position. `has_pose()` stays for what it does correctly:
distinguishing a 600-series, which works because the constant differs by
generation.

One sensor was gated wrongly by it. **Navigation quality** filtered on
`cap.pose` and reads `mssnNavStats` — and an R980040 reports the
capability while carrying no `mssnNavStats` at all, 55 state keys with
that one absent. The sensor existed and could never have a value. It
gates on its own field now.

**And it affected more than one firmware family.** It was filed
as a lewis quirk after an i7 reported the capability and never sent a
position; his S9+ runs **soho** and does the same. Anything needing an
actual position checks for one now, and `has_pose()` says in its own
docstring that it is a claim rather than a fact.

Two call sites that use it as a stand-in for "not a 600-series" are
commented as such. They work; they were not saying what they meant.

# 🗂️ Zones in the room list templates can read

The `rooms` attribute on the *Rooms overdue* sensor was built from the
cloud coordinator's `regions` property, which holds **rooms**. Clean
zones live in a separate property that nothing was reading, so no zone
ever appeared — and on a Prime robot, which has no cloud coordinator at
all, the list came back empty.

Found by **@ibernstone** asking how to enumerate zones in a `for_each`.
The names match what `clean_room` and `clean_zone` expect, so the list
feeds straight back into a repeat.

# 🏷️ Zones reach the device tracker's name cache

**@chairstacker**: rooms resolved to their names, zones stayed as
`Room 100`.

The cache merges two sources — `available_rooms()` for rooms, and the
flat `prime_room_names` for zones — and that merge was already correct.
The **refetch gate** was not. It fired only while the cache was empty.

Rooms arrive first, from the map's own metadata. Zones arrive later,
once a map build has filled `prime_room_names`. So the first room to
land closed the gate, and no zone was ever picked up.

It now refetches while either source could still add something.

# 📊 Navigation quality gates on the field it reads

It filtered on `cap.pose` and reads `mssnNavStats`. An R980040 reports
the capability and carries no `mssnNavStats` at all — 55 state keys with
that one absent — so the sensor existed and could never have a value.

Part of the same correction as `reports_local_pose()` above: `cap.pose`
is a compile-time constant on lewis firmware and says nothing about what
a robot reports.

# 🔁 A resumed mission is no longer filed as abandoned

**@ScenicSystemsLLC**'s Braava got stuck, was freed by hand 16 minutes
later, then cleaned four more rooms and drove home — 168 minutes, 524
sqft, a genuine dock finish. It was recorded `stuck_and_abandoned`.

He found the asymmetry: the stuck event is detected as a before/after
snapshot, the recovery as a live phase transition. Tracing it further,
the transition was not the problem either. The timestamp it sets is
rewritten on **every** re-entry into an active phase after a stuck, so
on a long mission the last one wins — and the classifier then measures
"time since the robot resumed" against what is really "time since the
last phase change". His final room ran under five minutes, and that was
all the clock was measuring.

His own suggestion is what shipped: decide retrospectively from the
mission record. Rooms completed after the stuck, or a real `dest: dock`
finish, answer the question directly — elapsed time was only ever a
proxy for both.

Falls back to the old test when there is no cloud record, which is
wrong in one direction but better than refusing to classify.

# 🔋 A flat battery no longer counts as getting stuck

**@AlakazipLabs** walked an i3 down to 6%, sent `dock`, and watched it
accept, set off, and give up thirteen seconds later with `error 46`
(Low battery). The robot's own `nStuck` counter went 111 → 112.

So a robot that repeatedly runs itself flat scored identically to one
that repeatedly gets trapped — in the problem-zone sensor and in every
mission result derived from that counter.

`error 46` separates them and arrives in the same message. Deliberately
narrow: only that code, and only where the stuck delta would otherwise
have decided the result.

Found as a side note in an experiment about something else entirely.

# 🔧 Housekeeping

None of this changes behaviour; it changes what the build catches.

**The integration now runs against Home Assistant 2026.8 as well.** A
second CI job tests on Python 3.14 with an HA release about eighteen
months newer than the pinned one. Seven differences turned up, all in
test code — the largest being that `pytest-homeassistant-custom-component`
ships async fixtures that need `asyncio_mode = "auto"` to resolve.

The pinned version is unchanged: 2025.1.4 is the newest release that
installs on Python 3.12.

**One real fix came out of it.** Statistics metadata passed a bare `0`
where newer HA declares an enum — it now resolves the enum at runtime
and falls back, so it is correct on both.

**Dependabot only proposes what this project chooses.** It was opening
PRs for all 133 pins in the frozen requirements file, most of which are
Home Assistant's transitive tree. Bumping those independently is not
noise, it is wrong.

**CodeQL scans what ships.** There is more test code here than
integration code, so most of every scan was fixtures — which
legitimately contain sample credentials and broad excepts.

**And all eleven build guards now actually run.** Nine were only *read*
by their tests. One had drifted: three of its entries named tables that
were renamed when their values became translation slugs, so it had been
exiting non-zero without anyone knowing.
