# Roomba+ v4.0.0a20

Prime only. Requires roombapy-prime **v0.2.0b8**.

Everything here came from field reports or from APK analysis — nothing was found by reading our own
code.

## Schedule switches appear and disappear with the schedules

a19 kept the *state* of schedule switches in sync with the iRobot app. @DaRealGuGu's four-row test
matrix showed what that left out: entities were still built exactly once, at setup.

> Create a schedule in the app → no switch until a reload.
> Delete one → the switch goes unavailable, and then stays there forever.

The entity list now follows the schedule list on every refresh.

Matched by `schedule_id`, never by content — the order of `start.day` is not stable between two
reads of the same unchanged schedule (`[4,3,1,2]`, then `[1,2,4,3]`, then `[3,1,2,4]` across his
captures), so a content comparison would report a change every fifteen minutes.

His diagnostics also settled where the staleness lived: the file he took at the moment Home
Assistant was showing the old value already contained the new one. The read path was never the
problem.

## New: dock clean water tank level

Some docks report it, some never do. One capture has `tankLvl: 100` with dock firmware 24; the
other never sends the key at all with firmware 20 — not even while a pad wash was failing for want
of water.

Two things differ between those docks at once, so the field cannot say which governs, and the APK
cannot settle it either: `pd`/`pw`/`pwo` are not literals, the mapping is filled at runtime, and the
capability enum behind it is purely categorical with no notion of a level 2 or 3.

So the sensor is gated on the value being present rather than on a capability flag. A dock that
stays silent produces no entity, instead of one reading "unknown" forever — the lesson from the
vacuum-only Max 705 that got a pad-wash sensor it could never populate.

Grey water gets no sensor: the field appears in no capture from either dock, and its role could not
be established in the app either.

## New: pad drying switch

One of the seven AutoWash settings is now a switch, and the other six deliberately are not.

Of 37 setting-write commands in the app, exactly one covers this area: `SetPadDryAllowCommand`.
Everything else travels through a bundled write whose contents are not statically readable. A
control that writes one field of a bundle alone may be accepted and do nothing — `schedHold` already
behaves exactly that way on these robots.

`padDryAllowed` has its own command, so it is written the way the app writes it. The rest wait for a
field capture showing whether one slider moves one field or several.

## Pad wash status 671

The label is confirmed as the best available. 671 appears nowhere in the app's dock-state table,
whose pad-wash family stops at 669, and there is no newer table. The app carries "Unknown dock state
%d" for exactly this case — so the official app would show less than this integration does.

## No dock entities for a robot with no dock

@utkjmitch's Y351020 sits on a plain charge dock and reports `dock: {"known": false}` with no
capability object at all. A missing capability object was read as "the shadow has not arrived, fail
open" — right when the shadow really is incomplete, wrong here. `known: false` is the robot stating
there is no such dock.

It produced pad wash and pad dry sensors plus the wash and dry buttons on a robot that can do
neither. Same family as the a17 Max 705 fix, different trigger: there the capability object was
present and the key absent, here the object never arrives.

A dock key that is absent entirely still fails open — that is a genuine gap. Only an explicit
`known: false` suppresses.

## The error sensor reports the code, not a guess

It used to render Classic's error labels, on the stated assumption that "the codes are the same
product-wide catalogue, only the transport differs". That was an assumption written as a fact.

APK analysis found no error-code table in the app at all — for either generation. And a field
capture contradicts the label outright: error 46 with `phase: "stuck"` on a robot physically
confirmed stuck, at 55% battery, which the Classic table calls "Low battery".

So the sensor now shows `Error 46`. The Classic reading stays available as an attribute named
`classic_label_unconfirmed`, because it is probably right more often than not — it just must not be
asserted, and an automation should not be built on it by accident.

Same reasoning already applied to consumable parts 202 and 212: a wrong label gets believed, a
number invites a question.

An unmapped code now reads `Error 9999` rather than "None", which used to say "no error" for a robot
that had one.

## Mop wetness, documented not implemented

The capture that blocked a wetness control for weeks is explained. `padPlate` has its own
enumeration, offset by one from the other two pad categories, so the "impossible" 3 was `Invalid`
under `disposable` — meaning no disposable pad is fitted. Nothing was out of range.

Still no control: which of the three fields to write depends on which pad is fitted, and writing the
wrong one applies the wrong scale to the wrong field, silently.
