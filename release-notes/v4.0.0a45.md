# Roomba+ 4.0.0a45

Requires roombapy-prime 0.3.0b16, which comes with the HACS update.

Diagnostics only. Nothing about how the integration behaves changes — but
a diagnostics download now answers questions it previously could not.

## Navigation telemetry was never exported

Firmware analysis of the i-series documents twelve fields in
`mssnNavStats`, validated against a real Braava m6 dump:

- `kdp`, `sfkdp` — kidnapped detection
- `l_drift`, `h_drift` — pose confidence
- `gLmk`, `lmk` — landmark density
- `mpSt` — map state
- `reLc` — relocalisations
- `mTrk`, `plnErr`, and map-change counters

This integration reads **one** of them.

Among the rest is a kidnap signal that the live-map rebuild went looking
for and concluded did not exist on Classic robots. It does. Nobody had
looked here — and the same applies to pose confidence, which an open
design note describes as needed and unavailable.

The whole object is now in the diagnostics download, verbatim rather than
key by key. The 980 is a different platform from the i-series, and
choosing which keys to export would decide the question this exists to
answer.

**It only fills during a mission.** On the dock most of it reads zero, so
a download taken afterwards shows nothing even on a robot that supports
every field. It has to be pulled while the robot is cleaning.

## The dock model was determinable and not determined

The i-series OTA carries dock firmware for 14 hardware/variant
combinations named `dock_hw{N}_var{M}`, and the `dock.hwRev` and
`dock.varID` fields map straight onto N and M.

Neither was read anywhere. The download now carries both, plus part
number and firmware version.

This bears on several open reports: which docks can evacuate, which have
a fresh-water tank, and why `empty-now` does nothing on one tester's
install.

## If you are sending a diagnostics download

Pull it **during a mission**, not after. That is the difference between a
file that answers these questions and a file full of zeros.

## The coverage heatmap was upside down

Since it was written. Every other map in the integration measures
downward from the top of the image; the heatmap measured upward from the
bottom of the grid.

Nobody noticed because the tile has no landmark — no dock icon, no room
outlines, nothing to be upside down *relative to*. @pk-1966 marked four
known places on his coverage and room maps, and it fell out at once: y
matched `1 − y` on all four while x kept its order.

Correcting it exposed a second fault underneath. The bounding box is
measured centre-to-centre, so the outermost cell's own width was never
accounted for — **a row of cells has always been missing**, previously
off the bottom. Invisible for the same reason.

## The pad-dry switch could never be on

It read the dock's general `state` field looking for a value that only
ever appears in `pd_state`. The dock reports three status fields in
separate numeric bands, and pad drying lives in the third.

So the switch turned on, Home Assistant showed it on until the next
state write, and then it read the wrong field and reported off —
behaving as a momentary button, with nothing to turn off.
@chairstacker.

## A Prime robot topping up mid-mission read as Docked

`charge` maps to docked, but a robot returning to top up is not
finished: its cycle is still `clean`. The activity timeline showed
Cleaning, Docked for about seventy seconds, then Cleaning again — three
times over one morning, looking like the mission ended and restarted.

Worse than cosmetic: an automation reacting to "docked" fires
mid-clean. The Classic path has had this rule for a long time; only the
Prime branch checked the cycle in one direction and not the other.

## A missed message could lose a whole mission

The mission-history sync fired only when a `charge` transition was
actually observed. Miss that one message — a quiet push stream, a
reconnect, a short run — and the mission never synced: no sensor
update, no activity entry, nothing, until a reload or the six-hour
interval. @chairstacker had a zone mission ignored completely while the
connection sensor read Connected.

`nMssn` counts missions and only goes up, so a change now triggers the
same sync whatever was observed in between.

## Zone cleans are named

A timeline event carries three place fields: `room` and `travel`, both
keyed `region_id`, and `zone`, keyed `zone_id`. Only the first two were
read, so a zone-targeted mission resolved no room at all — and the
device tracker fell through to its "somewhere, cleaning" label while
the diagnostics download carried every zone name.

The lookup was never the problem. There was no id to look up.

## Entity names could disagree with themselves

`strings.json` and `translations/en.json` gave different names for eight
entities. English users see the second; a developer reads the first.

Found by @mdarocha while settling a naming question in his own
contribution — he assumed two entities disagreed with each other, and
found one file disagreeing with another instead. A check now fails the
build on it.

## Also

- **Consumable counters from iRobot's cloud**, replacing the
  install-time assumption for anyone migrating from the official app,
  with resets written back so the two agree. @mdarocha.
- **The cleaning map on robots that report no pose** now falls back to
  the last mission's cloud coverage instead of serving blank. Covers an
  i3+ that never declares the capability and an i7 that declares it and
  never sends one.
- **Two timezone-dependent tests** that only failed off UTC.
