# Roomba+ v4.0.0a15

**Fixes a regression in v4.0.0a14: the vacuum entity could be missing.** Reported by @arielgr.

## What happened

v4.0.0a14 added a helper parameter to the room-cleaning backend, with a fallback that read
`config_entry.hass`. `ConfigEntry` has no `hass` attribute, so that access raises.

The factory is called from `supported_features` — a property Home Assistant evaluates while
registering the entity. An exception there means the entity is never added. For V4/Prime robots that
removed the vacuum entity entirely: the one that shows the robot and starts a clean.

Two more places had the same access. One was the constructor of the new Prime room map, which would
never have appeared either.

## Why the tests did not catch it

Every test passes a `MagicMock` as the config entry, and a MagicMock answers any attribute access
with another MagicMock. All 4,577 tests were green against code that raises on the first real
`ConfigEntry` it meets.

That is not a gap in one test — it is a property of mocking. Two guards were added:

- No module may read `hass` off a config entry.
- **Every** attribute this integration reads off a config entry must be declared on `ConfigEntry`.
  The second one checks the general form rather than the single case, because `hass` would have
  stayed green with five more like it.

## Also in this release

**Seven migration steps removed.** Versions 3 through 9 renamed entity_ids from German to English
slugs after an early release shipped translated `translation_key` values. Each was built from the
entity registry of a single installation — 400 hardcoded entity_ids, all carrying one robot's
prefix — and on any other installation they matched nothing.

Entries still on those versions now jump to version 10 and receive every later migration, which are
the generic ones that apply anywhere. 669 lines, 31% of the migration function.

That every test stayed green after removing them is its own finding: none of the seven had one.

4,582 tests passing.
