# Roomba+ 4.1.1

Three fixes for the room and zone selector that 4.1.0 introduced. All
three were reported by @chairstacker within hours of the release, with
screenshots.

## The selector was always unavailable

`select.{robot}_select_room_or_zone` appeared and never worked. It loaded
its list in `async_update()`, and these entities do not poll — Home
Assistant never called it, so the list stayed empty and the entity
reported itself unavailable. The companion button had nothing to act on
and did nothing.

It loads when the entity is added now, which is what the map selector
beside it already did.

## Cleaning a zone sent the robot to a room

Assigning a Roomba **zone** to a Home Assistant area produced a robot
that left the dock, localised, then declared the mission complete and
returned — @chairstacker's, with the bin emptied on arrival each time.

The segment decoder stripped the `zid_` prefix before handing the id on.
The command builder uses exactly that prefix to choose between a zone and
a room, so a zone arrived looking like a room and went out with an id no
room has. Rooms were unaffected: their prefix is meant to be stripped.

## The zone list came out in a random order

The rooms half of the area-mapping dialog is alphabetical; the zones half
was sorted by internal region id. Both are sorted by name now.

## Room names on other maps

Two more things surfaced the same evening, both downstream of what 4.1.0
made possible for the first time.

**`current_room` showed "Room ID 18" instead of "Hallway"**
(@ScenicSystemsLLC). He ran a favourite that cleaned a room on a map the
robot was not currently using — the button worked, the robot went to the
right room, and the sensor displayed a raw id. Nobody could have hit this
before 4.1.0, because a cross-map mission could not be started.

He traced it himself: the mission-progress sensors read
`cloud_coordinator.regions`, which returns the ACTIVE map only. 4.1.0
lifted that restriction for `clean_room` and left the other readers
alone. There turned out to be **eight** of them, each building the same
lookup by hand. All eight now call one function, and a guard fails the
build if a ninth appears.

**Zones on other maps had no name at all** (@chairstacker). The
all-maps source read a map's `regions` and ignored its `zones` — the two
sit side by side in the same document. That is why the area-mapping
dialog listed rooms from every map and zones only from the one being
drawn, and why a room could appear under Rooms and not under Zones.

Roomba+ also now reads the map VERSION document, which is where iRobot
keeps region names for rooms **and** zones. roombapy-prime found that
endpoint months ago — it took four rounds with @chairstacker — and
nothing had ever called it.

That last part is **additive on purpose**: whether the document carries
zones is still unconfirmed on any robot, so it fills gaps rather than
replacing what works. If it returns nothing, the list is exactly what it
was. If it returns your zones, the gap below closes with it.

---

## Still open

**Whether every zone now appears.** Three sources feed the list, and the
widest of them — the map version document — has never been seen carrying
zones on a real robot. If a zone of yours is still missing after this
release, that is worth saying: it would settle a question the library
itself has open, and @chairstacker's robot is the one it was chased down
on.
