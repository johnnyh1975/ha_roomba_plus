# Roomba+ v4.0.0a7

A field-feedback release: every change here came from something a tester actually reported and
looked at, mostly chairstacker's detailed run through v4.0.0a6.

> 4,184 tests passing · `roombapy-prime` pin updated to v0.1.11a22

## 🐛 Fixed

- **"Cleaning" shown all the way back to the dock instead of "Returning".** The mission-event
  stream alone cannot express "heading home" — the same `travel` event fires both for
  room-to-room travel mid-mission and for the final trip back, so a finished mission still
  reported CLEANING until `evac` arrived, by which point the robot was already at the dock. Prime
  now derives its activity from `cleanMissionStatus.phase` (confirmed live for Prime), reusing
  Classic's long-proven phase mapping — which draws exactly the distinction the event stream
  can't: `hmPostMsn` (mission done, heading home → Returning) vs. `hmMidMsn` (heading home to
  recharge, mission continues → Cleaning).

- **The mop tank and bin sensors displayed "Home"/"Away".** They carried
  `device_class: presence` — the device class meant for people and device trackers. Removing it
  gives a plain on/off. Applied to all five physical-component presence sensors (bin and tank,
  Classic and Prime alike), since the same wrong label affected every one of them. Safe for
  existing automations: a binary sensor's state is always `on`/`off` regardless of device class;
  only the frontend label changes.

- **Live map diagnostics.** The map stayed blank while data was arriving and failing to decode
  106 times an hour, with a log message that said only "failed to decode" — nothing about what
  actually arrived. Now checks the HTTP status (never checked before) and logs status,
  content-type, byte length and the first 32 bytes as hex. Ruled out along the way: an expired
  download URL, since error-page bodies fail at a different parse offset than the real failures do.

## ✨ Added

- **Error sensor for Prime robots.** `cleanMissionStatus.error` is confirmed live but was never
  surfaced. Reuses Classic's error catalogue and its hard-won stale-error suppression — the
  firmware does not reset the error to 0 when docking after a failure, so a naive sensor would
  show a long-finished error indefinitely while charging. Also exposes `not_ready` and
  `cond_not_ready` as attributes: a readiness-based start refusal leaves `error` at 0 and puts
  the actual reasons there.

- **Error code 671 (clean water tank empty)**, in all six translated languages. Field-reported by
  chairstacker from a single observation, and documented as such rather than as vendor
  documentation.

## 🧪 Test-suite robustness

- **Four date-dependent tests were time bombs**, passing only while the real calendar happened to
  sit close to their hardcoded fixture dates. One had already broken CI; the other three were
  found by re-running the suite under a frozen future clock rather than by reading the code. All
  now pin their own reference date explicitly.

## 📖 Clarified, not changed

- **The mission counters are not off by one.** Total counts up when a mission STARTS, the three
  outcome counters only when it ENDS — so mid-mission the total is legitimately one higher, and
  the sum matches exactly at rest. This is the robot's own counter behaviour, faithfully reported.
  Our own documentation implied the sum was an invariant; that has been corrected.

- **System uptime measures time since the device's registration**, not continuous power-on time.
  chairstacker's own back-calculation landing on the robot's "birthday" confirmed this — worth
  knowing before reading anything else into the number.
