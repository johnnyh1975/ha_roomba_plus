# Roomba+ v4.0.0a29

Requires roombapy-prime **v0.2.0b15**.

Three things users asked for, and one change to how this integration reports its own failures.

## A maintenance list for Prime robots

Classic has had one for a while, built from a single number — lifetime running hours — and thresholds
of ours, guessed from iRobot's published intervals.

A Prime robot reports each part individually, with how much it has used and how much is left, **in
whatever unit that part is counted in**: hours for a filter, missions for a brush, evacuations for a
bag, pad washes for a pad.

So this list has no thresholds of its own and cannot be wrong about one. It is read-only: the robot
decides when a part is fresh again, and it only learns that from a reset performed on the robot or in
the iRobot app. Ticking an item off here would record a claim the robot does not share.

A part that reports no remaining count is shown as not due. That is the safer direction — a list that
nags about a part nobody can act on gets ignored wholesale, and with it the items that mattered.

## Choosing vacuum, mop, or both

@arielgr asked for this: the iRobot app offers the choice when starting a clean, and this integration
had a suction control and nothing for the mode. The values had been confirmed for weeks; nobody had
asked.

**The select reflects the robot's own last start.** Begin a mop-only clean from the iRobot app and
Home Assistant shows mop, because that is what the machine did. A choice of yours is the fallback for
when nothing has been started yet.

The obvious source would have been wrong. `cleanMissionStatus.operatingMode` uses a different
vocabulary from the commands — "vacuum and mop" arrives as one number, "vacuum then mop" as another,
and **a pad wash arrives as the same number as "vacuum and mop"**. Reading it would make the select
jump to a cleaning mode while the dock cleaned a pad. It reads the last command instead, and ignores
anything that is not a `start`: `drypad` and `washpad` carry regions and a mode too, and neither is a
cleaning choice.

`clean_room` also takes a `cleaning_mode` for a single run. That field was described in
`services.yaml` and never read — the service accepted it and threw it away, using the select
regardless. It now outranks the select, as its own description always promised.

## Suction on the vacuum card

Also from @arielgr, and the more useful half. Home Assistant renders a speed control on the vacuum
card when the entity says it supports one. **Two Classic classes said so; the Prime path did not** —
so the generation with the richest settings was missing the one control Home Assistant can actually
put there.

Light, Standard, Deep, named as the iRobot app names them. The card and the existing selector write
the same field, so they cannot disagree.

## Failures that always happen now say so

Six faults in four days shared one shape: a name or signature disagreeing across a boundary, an
`except` filing the result at DEBUG, and a symptom reading as "there is nothing here" rather than
"something failed". Not one was found by us — each took a user reporting a missing feature.

**The `except` was never the mistake.** Swallowing a transient failure is right; a warning per hiccup
is how warnings become noise. What it could not distinguish is a code path that has *never*
succeeded, and that is a defect rather than a hiccup.

Twenty-one call sites now record both outcomes. A path that fails twice having never worked says so
once, at WARNING, and appears in a diagnostics download under `never_succeeded` — empty on a healthy
install.

**Thirteen sites were deliberately left out**, each with its reason in the code: a fresh install has
no stored map, a room estimate is legitimately absent in Auto mode, a watcher ending is the normal
shape of a disconnect. A warning that fires during normal operation teaches people to ignore
warnings, and would take the real ones with it.

## The schedule calendar was empty

`async_get_events` — the method that fills the calendar **view** — unpacked the occurrence tuple into
four fixed names. That tuple grew twice in a28: a schedule id so events could carry a `uid`, and an
operating mode beside it.

So it raised `ValueError` on every call, and an exception there produces an **empty calendar** rather
than a visible error. @chairstacker's entity was present, enabled, listed in the integration — and
had nothing in it. Adding an event worked and still showed nothing, because the write succeeded and
only the display could not render it.

The `event` property was widened at the time and this was not, which is why the state moved and the
view did not. **Every test stayed green throughout, because none of them called this method.** Four
now do.

## A Combo lost its room cleaning

`CLEAN_AREA` is withheld from Braavas, which target rooms through pad wetness rather than region
segments. The check asked the wrong question:

```python
and not is_mop(self.vacuum_state)
```

`is_mop()` answers *can it mop* — it looks for `detectedPad`. A Combo has a pad **and** brushes
**and** stable region ids, so it was excluded as though it were a Braava. Home Assistant then
filtered the entity out of its own service picker, which is what @connormxy saw.

His diagnostics showed the cloud coordinator holding twelve regions the whole time. He uninstalled
three integrations looking for a cause that was one word in ours: `is_braava()` reads the sku, and a
`c755020` is not an `m`.

**The fourteenth site of this same confusion**, and the first that cost somebody a feature.
`is_mop`'s own docstring already said which to use for anything about vacuum hardware.

## Favourite buttons appeared for nobody

Fixed in b16: the favourites parser read a key the model itself does not write, so every favourite
was dropped for having no id. The buttons had been built for weeks and could never be created.
