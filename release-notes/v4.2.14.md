# Roomba+ 4.2.14

## Room cleaning no longer sends the robot's own map version

Since 4.2.13, every room clean failed on some robots with *Smart Map
localization failed* (error 224): a j7+ (@FJSoninC) and two S9+ with
three maps between them (@ScenicSystemsLLC). App favourites for the same
rooms kept working.

**Why.** iRobot's cloud keeps several versions of each map. On these
robots, the version the robot saves at the end of a mission becomes the
*active* one, marked as made by the robot. 4.2.13 started sending the
active version, because on the robot in #183 the active version was one
a user had made and the other candidate was an edit that never became
active. On robots whose active version is their own, that choice is
wrong: the robot cannot localise against it. In every report, the app
and the favourites used a different field, the map's committed user
version.

A room command now gets its map version in this order:

1. the newest version the iRobot app stored for that map in a favourite
   or a schedule. The app runs its own favourites on it, and it was
   right in all three reports
2. the cloud's version of the map:
   - the active version, unless the robot made it
   - otherwise the committed user version
   - otherwise the last version a user made
   - the robot-made active version only if none of these exist
3. the version the robot last accepted for that map
4. the robot's own map list

This applies to **Clean room**, **Clean area**, **Send command** with
regions and **Repeat last mission**.

**A version that just failed is passed over.** A favourite or schedule
can predate a map edit. If the robot's last command for a map ended in
error 224, the next room clean for that map uses the next source that
gives a different version. One failed attempt is enough to try
something else. The failed version is only sent again when every source
gives it.

A debug log line now names which source a room command's version came
from.

## The recorded rooms follow the cloud

4.2.13 corrected the rooms a mission cleaned once the cloud's room
events arrived, but only where the rooms are derived from those events.
The stored list of cleaned rooms kept what room tracking saw during the
mission, and the **REST export** and **diagnostics** showed that list.

In @FJSoninC's closed-door test, the tracker moved on to the bathroom
behind the closed door, and the cloud said only the office was cleaned.
Room history showed the office; the stored list kept both.

The stored list is now replaced with the cloud's rooms once they arrive,
under two conditions:

- **Every room has a name.** If a map is not loaded yet, the list keeps
  the tracked rooms until the next cloud refresh.
- **The names come from the mission's own map.** On a robot with several
  maps, a room number means a different room on each map. A mission
  whose map has since been deleted, or whose room was split, keeps the
  tracked rooms.

A mission whose room events list no cleaned room at all also keeps the
tracked rooms.

## Cloud data shows up without waiting for the robot

When the cloud refresh merged room events or results into a mission, the
sensors showed the new values only after the robot's next status
message. A docked robot sends few, so **Room cleaning history** and
**Last mission summary** kept the old value for a long time
(@FJSoninC).

They now update as soon as the merge is done.

## Missing missions are recovered on a fresh install too

4.2.13 records the cloud's missions that have no local record, but only
those that ended after the oldest local one. That left two gaps:

- on an install that had not recorded any mission yet, nothing was
  recovered
- missions lost right after installing stayed lost once a later one was
  recorded, because they were older than it (@FJSoninC)

Missions are now recovered back to when the robot's integration entry
was created in Home Assistant, or to the oldest local record if that is
older. Older missions are still not imported, so the first refresh does
not pull in the robot's whole cloud history.

For entries created before Home Assistant began recording creation dates,
it reports the time of that upgrade instead, and a removed and re-added
robot starts again. Both only shorten the window.

## Under the hood

- The cloud's map picture (UMF) is fetched for the same version a room
  command gets from the cloud. On robots whose active version is their
  own, that is the user version again, as before 4.2.13
- The rule that reads a mission's cleaned rooms from the cloud's room
  events is one function now, shared by room history and the stored list
- New signal `roomba_plus_mission_store_changed_<blid>`, sent after a
  cloud merge changed the mission records; every Roomba+ entity of that
  robot re-renders on it
- **CI takes about a quarter of the time** (locally, 2 CPUs: the
  coverage run 212 s -> 58 s):
  - dependencies are installed with uv instead of pip, with identical
    package versions
  - the suite runs on every CPU of the runner (`pytest -n auto`)
  - coverage is measured in the HA 2026.8 / Python 3.14 job only, where
    branch coverage costs about 10 % instead of doubling the run; the
    per-module 95 % gate moved with it
  - the guard tests parse each source once, with a check at the end of
    the run that no test changed a shared tree
  - collection on HA 2025.5 no longer re-checks every fixture before
    each test (10 s instead of 25 s)
