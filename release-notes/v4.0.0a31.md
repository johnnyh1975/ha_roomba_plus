# Roomba+ v4.0.0a31

Requires roombapy-prime **v0.3.0b1**.

Three faults reported by testers on a30, two features that were built and then found unreachable,
and error messages that now come from iRobot rather than from us.

## Editing a schedule no longer collapses the series

@DaRealGuGu edited the **Monday** occurrence of a Mon/Tue/Wed schedule and it became Monday-only.
Home Assistant hands us one occurrence; the day list was being rebuilt from whichever day he had
clicked.

Same principle as the frequency fix in a30, one layer down: **an edit that says nothing about
recurrence must not change it — and the day list is recurrence.** Only an explicit rule replaces it
now.

His a30 report also confirmed the two fixes above it: recurrence survives a time change, and a
one-off schedule stays where it belongs instead of moving with the calendar view.

## `clean_area` on a Combo, finally

@connormxy's Combo 105 still had no room cleaning on a30. His diagnostics said why and it was
misread: `withheld_features` came back **empty**, meaning our own check considered the feature
offered. It was. **Nothing asked it.**

`is_mop()` is true for anything with a pad, so every Combo was being built as a `BraavaJet` — a
class that deliberately excludes `CLEAN_AREA`, correctly, because a Braava has no regions to clean.
The class was chosen by the wrong question.

The same `is_mop`/`is_braava` substitution was corrected inside that class weeks ago for him. It was
the right condition in a place his robot never reached.

## The maintenance list stopped nagging about a clean pad

Two of @DaRealGuGu's parts count the same 90 pad washes: the pad has 210 washes of life left, the
wash counter reads zero *since the last one*. **On a replacement part zero means used up; on a
maintenance part it means just done.** His app and light ring were right; the list was wrong.

## Error messages, part names and units now match the app

This integration wrote its own 126 error labels. A comparison against iRobot's own app found that
**two** of them matched — and the differences are not cosmetic: "Charging error" where iRobot says
"Charging Issue: contacts need to be cleaned". The second tells you what to do; the first tells you
something is wrong, which the stopped robot already said.

112 codes with the vendor's title and explanation, in all eight languages, falling back to ours for
the 75 codes iRobot does not document — @connormxy's error 236 is in neither.

Part names follow ("Maintenance – High-Efficiency Filter", keeping our grouping and taking iRobot's
word), and so do the units: `evacs` reads "Dust Collection Left" in the app, not "evacuations". A
list saying one thing beside an app saying another reads as two different measurements.

## Presence scheduling and demand cleaning work on Prime

Six options — the enable switch, the mode, the person entities, two delays — were offered in the
dialog, stored, and read by **nobody** on a Prime robot. A user could switch presence scheduling on,
configure it fully, and nothing would happen. No error, no message. They did not merely not get the
feature; **they believed they had it.**

Classic pauses schedules with `schedHold`. A Prime robot accepts that write, reads it back changed,
and runs anyway — the field has no consumer in iRobot's Prime app at all. Prime disables the
schedules instead, which is what the app itself does. Only schedules *we* switched off get switched
back on.

Demand cleaning goes the other way: **Prime has the better source.** Classic infers dirt from mission
records and a weekday baseline; a Prime robot reports a value per room and the threshold to judge it
by. So instead of starting a whole clean, it starts the dirtiest room.

## Zones, unfinished rooms, and a to-do list you have to ask for

- **Zones no longer need a running mission.** @chairstacker ticked clean, keep-out and no-mop zones,
  reloaded twice and saw nothing — correct, because the data came only from the live map bundle,
  which arrives while the robot is driving. Zones barely change and nobody checks their keep-out
  areas mid-clean.
- **Rooms the last run left undone** now appear on the mission sensor with the mission that skipped
  them. @chairstacker reported a mission that failed on a blocked door and left no trace anywhere;
  the answer was in the payload the whole time.
- **`phase` and `readiness`** — the most basic state sensor there is, and Prime did not have it.
  With it, the device triggers work: "when the robot starts cleaning" simply did not appear in the
  automation editor before, because there was nothing to attach to.
- **The maintenance list is opt-in on both generations.** Classic users who use it will need to
  switch it back on.

## Prime mission history imported nothing at all

@utkjmitch's robot had 46 missions on the endpoint and imported **zero**, on every release since the
feature was added.

`get_mission_history()` returns the raw response by design; nothing called the parser. So the sync
iterated plain dictionaries and asked them for attributes — `getattr(dict, "mission_id", None)` is
`None` on every entry, so every entry converted to nothing and every one was dropped. **Silently,
because dropping records without an id is the correct handling of a malformed record.** The data was
not malformed; it was unparsed.

This is the third life of that call site: a wrong `days` argument, then a missing robot id, now a
missing parse. Each fix moved the failure one layer deeper.

## A robot that says it is cleaning and is not

Also his: a mission that ended in an error left the cloud document stuck at `phase: "run"` for **61
hours**. Two daily schedules were silently skipped, the vacuum showed "cleaning" for two and a half
days, and **every remote command was swallowed** — start, stop, dock and find, each confirmed
delivered, none with any effect. iRobot's own app was equally fooled and could not end its own
phantom mission. Only a power cycle cleared it.

Nothing here can unfreeze that, and nothing can: the fix is to power cycle the robot, now written up
in **[Troubleshooting](docs/TROUBLESHOOTING.md)**. What this release does is stop repeating the lie —
`phase` reads **`stale`** when the battery is rising while the document claims the robot is running.
Charging and cleaning are mutually exclusive, and the robot supplies both numbers. The test was his
suggestion.

## The maintenance list, on his dockless robot

- **Part names were translation keys.** The list read "Replace prime_part_dirt_bag" — Home Assistant
  does not translate to-do summaries, and the readable name was loaded for the sensors all along.
  Unknown ids still show their number, which is ugly and honest.
- **A dust bag on a robot with no dock.** The cloud reports the part regardless of the hardware.
  Parts are now hidden when the robot explicitly denies the capability (`dock.cap.evac == 0`), and
  only then: silence is not a denial, and a maintenance item wrongly hidden is worse than one
  wrongly shown.

## Calendar summaries said `Zone 10` for rooms the map named correctly

Two name sources, one read. The map bundle knows names the schedule coordinator does not, and on his
four-map account the same rooms appeared correctly on the map and as zone numbers in the calendar.
The bundle now fills the gaps behind the coordinator rather than over it.

## What iRobot's own app corrected, where nothing was failing

The vendor's Prime app was rewritten in 3.0.0 and now ships its data layer as readable definitions
rather than compiled constants. Comparing this integration against it found faults that no amount of
field testing would have surfaced, **because nothing was throwing an error**:

- **Demand cleaning would never have fired.** The per-room dirtiness reader expected a level of
  nesting that appears nowhere in iRobot's model — so on a real response it found nothing, which
  reads exactly like "no room needs cleaning". Every test passed, because the fixtures were written
  to match the invented shape.
- **The `phase` sensor was missing five values** and had guessed two. A value outside the declared
  list makes Home Assistant take the entity offline, so a robot returning to charge mid-mission
  (`hmUsrChrg`) would have knocked the sensor out entirely.
- **`mission_last_cleaned` is an object, not a number.** A caller reading "which mission last cleaned
  this room" got a data structure where an integer was promised.
- **Four of iRobot's own error messages are broken** — a placeholder run into the next word in
  Spanish and Polish, and one English message using a different placeholder entirely. Repaired on
  display, so the stored catalogue stays a faithful copy.
- **Per-room preferences** (`smart_clean_prefs`) are now carried: the server's record of "always mop
  the kitchen", which explains why a room can clean differently from the robot's global settings.
- **Diagnostics report the robot's own capability flags** — all 35 of them, across the three shadows
  they live in. When somebody asks why a feature is not offered, the answer is now one line in a
  diagnostics download rather than a code reading.

## Also

- **A room clean with no known map is refused** rather than sent. @Echovictor37 found that such a
  command returns a PUBACK **and cleans the whole house** — so asking for the kitchen would have got
  every room, with a success in the log.
- **Room naming reads three sources**, not just schedules: a robot whose owner never built a
  schedule *with rooms* had nothing to name, though it knows its rooms perfectly well.
- **An empty naming step says which of two things happened** instead of reporting itself finished.
- **`CONF_CLEAN_DELAY_MIN`** was offered, stored and read by nothing. Now wired.
- **Backups include a Prime robot's cloud state.** "It is already in the cloud" is not a reason to
  skip it.

5,255 tests.
