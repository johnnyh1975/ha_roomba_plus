# Roomba+ 4.0.0a36

Requires **roombapy-prime 0.3.0b6** — unchanged from a35, no library upgrade
needed.

Two things: a favourite-button fix that a35 got half right, and making a
question answerable that has been open since a29 without anybody being able to
answer it.

## Deleting a favourite in the app removes its button

a35 made favourite buttons appear and disappear with the list. **Only the
appearing half worked**, and @chairstacker found the asymmetry within a day:

> Creating a favorite in the app makes it show up in HA within a reasonable
> amount of time. Deleting it in the app has not yet removed it.

He put it down to the six-hour refresh, and I had told him that was the
mechanism. Both wrong. Adding compares against the wanted list and never
touches a prefix; removing scans the entity registry **by** prefix — and the
prefix was built from the bare BLID while the ids are
`roomba_plus_{blid}_favorite_…`. It matched nothing. No button would ever have
been removed, after any amount of waiting.

Two places built the same string separately, and nothing tied them together. A
test now constructs an id the way production does and matches it against the
prefix removal uses, rather than asserting a literal.

## Per-room preferences are in the diagnostics now

The Rooms Map has carried a `room_preferences` attribute since a29 — the
settings each room already has in the iRobot app:

```
profile · suction_level · two_pass · carpet_boost · scrub
```

It is read per room from `operating_mode_defaults`, under the mode that room
last ran in rather than any other, and an absent key stays absent rather than
becoming a zero.

**Nobody has ever confirmed it works.** The version plan has carried it as
unverified since it was built, and it stayed that way for a reason worth
naming: the only way to check was to open an entity's attributes and look. That
is a worse thing to ask a tester for than something already in a download they
send anyway.

So it is in the Prime diagnostics block now, read from the entity rather than
recomputed — a recomputation could succeed where the entity fails and hide
exactly the gap this exists to find.

**And when it is empty, the block says which of two reasons applies**: the
robot reported no `operating_mode_defaults` at all, or no room carried a
`last_operating_mode` to read them under. Those need different follow-ups.

This is the same fix as the favourites block in a34 — that one sat in the
Classic code path while the question was about Prime. Put the instrument where
the question is.

## Documented

`AUTOMATIONS.md` now shows how to use it: cleaning a room **the way it is set
up** rather than overriding it. *"Clean the kitchen the way I configured it"*
instead of *"clean the kitchen on deep because the automation says so"*.

If your `room_preferences` comes back empty, that is worth a report.

## The mop tank sensor is documented as unreliable

@chairstacker also settled a question that has been open through two different
gating rules:

> I cannot identify any sensor/entity that indicates a water level for the
> robot [...] And does the 405 have a fill port on the robot body? Nope

So on his Combo the pad is wetted at the dock and there is no onboard tank —
while the robot reports `tankPresent: true`, constantly, and unmoved by pulling
either dock tank.

That disproves the rule this sensor has used since he first reported it. The
original gate was `cap.scrub`; it was replaced with "does the robot report the
field at all", on the reasoning that the robot itself would say. **It does not.**

**The sensor stays**, because nothing distinguishes a robot with a tank from
one without — there is no capability flag, and `cap.ppWetLvl` describes pad
wetness the *dock* applies. Removing it everywhere on one robot's evidence
would take a working reading away from any robot where the field is real, and
nobody has observed one either way.

It is documented as unreliable in the feature reference now rather than quietly
trusted, with the observation that would settle it: **a robot where the value
goes `off` when you pull the tank.** If yours does that, it works and the
caveat does not apply to you — and that is worth reporting, because nobody has
seen it.

## Also

- **The pad-wash interval list carries a note about the app's presets.**
  @ratpic83's AutoWash screen offers three area presets — 5, 10 and 15 m² —
  against the five values the vendor's own enum declares. There is no 5 in
  `ReturnByArea`, so the app is almost certainly displaying 6 rounded, and only
  10 and 15 line up cleanly on both sides.

  The list stays at five. 8 and 20 are the vendor's own values and unreachable
  from their own UI; narrowing to match one screenshot from one product mode
  would remove two settings the robot accepts.

## The mop wash frequency labels were wrong, and the values matter

@chairstacker's screenshots of the iRobot app gave the three upper values their
actual meanings, and they are **cumulative** — each adds a trigger to the one
below:

```
Standard  100  before and after cleaning routines
Medium    101  ALSO during refills
High      102  ALSO in between rooms
```

The old labels read as single moments — "At mission end", "On refill", "On
refill or new room". The first was simply wrong; it happens twice. They now
read **"Before and after routines" · "Also during refills" · "Also between
rooms"**.

**And a warning worth having.** On @chairstacker's 405 with a `pw: 1` dock,
every value in that upper range makes mopping unusable: the robot enters the
room, spins, announces a mid-session pad wash, returns to the dock, washes,
comes back, and repeats. Vacuum-only runs are unaffected. `By area interval`
works.

It is not the refill trigger — he disproved that by setting Standard, which
involves no refill, and getting the same loop. The three share one thing:
**they all wash "before a routine"**, and if the robot counts resuming after a
dock visit as starting one, that fires again on every return.

The three values are **not withheld**, because nothing yet distinguishes his
robot from one where they work — @ratpic83's 405 with a `pw: 3` dock is offered
an entirely different picker by the same app version. If your robot keeps
returning to the dock while mopping, check this select first.

## HACS: the stable v3.5.1 is currently unreachable

Not an a36 change, and it will affect anyone trying to install the stable
version: **HACS reads only the 30 most recent releases in a single API call**,
and there are now 37 v4 pre-releases on top of v3.5.1.

With betas off HACS finds nothing eligible and offers `main`, which 404s. With
betas on you get a v4 alpha rather than v3. Install v3.5.1 manually from the
release assets until a fresh v3 release restores it to the window.

Found by @pk-1966, mechanism read from HACS's own source.

## Known cosmetic leftover from a35

If a35 stopped creating an entity for you — most likely
`switch.*_prime_vac_high`, whose key your robot does not report — the entity
may still be listed and permanently `unavailable`.

That is Home Assistant's own registry row for an entity that vanished, not the
integration recreating it. Its state carries `restored: true`. **Deleting it
from the entity list is safe** and it will not come back.

Reported by @ratpic83, who checked before filing it as a regression: *"the fix
works; the leftover is cosmetic and deletable. Worth knowing in case a35 gets a
'the switch is still there' report."*

Not cleaned up automatically. Removing registry rows on the strength of a key
being absent risks deleting a working entity when a shadow is merely slow to
arrive, and a one-off cosmetic row after an upgrade is not worth that.

## Upgrading

Nothing changes an entity, an attribute or an action.

**If a favourite button is stuck showing "Not provided"**, it will go on its
own once this is installed — no reload needed, though a reload is faster than
waiting for the refresh cycle.
