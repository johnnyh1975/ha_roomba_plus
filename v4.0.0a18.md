# Roomba+ v4.0.0a18

**A schedule feature that shipped without ever creating a single entity.** If you have a Prime robot
with cleaning schedules, this release is the first one in which the switches actually appear.

Requires roombapy-prime **v0.2.0b6**.

## Schedule switches never existed

`SchedulesList.schedules` holds raw dictionaries. The code read `.schedule_id` and `.options` off
them as attributes, which returns None on a dictionary — so the setup loop skipped every schedule
and created nothing. On every account, for the entire life of the feature.

Nothing raised. The feature was simply absent, and its own tests were green: they declared a
`_Schedule` dataclass with those names as attributes, recording a shape no server has ever sent.

Three paths were broken by that one cause. Reading created no entities; the state read the enabled
flag as False; and the write path would have handed dictionaries to `update_schedules()`, which
calls `.to_json()` on each element — an `AttributeError` mid-write, had it ever got that far.

## The diagnostics probe added to answer this could not run either

It read `data.household_id`; the field is `prime_household_id`, and the same file reads it correctly
a few lines further down. The probe returned nothing unconditionally, on every install. Underneath
that sat the same dictionary-versus-attribute mistake.

It now reports two counts — what the server sent, and what this project read — and says so when they
disagree. A count is a conclusion; the recurring problem here has been that a zero could mean "no
schedules" or "could not read them", and nothing distinguished the two. Schedule names, room ids and
the household id are deliberately still absent: this file is generated and attached, not reviewed
line by line before it is shared.

## Four more found in this release's own bug hunt

- **A schedule deleted in the app left a working-looking switch behind.** A read that failed and a
  read that found nothing returned the same value, so the state was kept in both cases. The switch
  went on reporting "on" indefinitely and did nothing when pressed. Deleted now goes unavailable; a
  cloud hiccup still keeps the last known state, which is the difference that needed telling apart.
- **A write could have been built on a list that was never read.** `update_schedules()` replaces the
  whole list, so writing one assembled from a failed read deletes schedules.
- **Toggling two schedules at once silently reverted one of them.** Read-modify-write of the whole
  container, twice in parallel: the second write reverted the first while Home Assistant showed both
  as changed. `switch.turn_off` against a group does exactly this. Read and write are now serialised
  per container.
- **The schedule switch belonged to no device.** It was the only Prime entity in the integration not
  built on `IRobotEntity`, so it carried no device info at all — the switches would have appeared
  outside the robot's page, and with two robots their schedules would have been
  indistinguishable.

## Prime device pages were missing model, serial and firmware

`IRobotEntity` takes the config entry, and for a Prime entity that is the only source of those
fields — there is no local robot state to read them from. A fix for this was made and then applied
to some entities and not others.

Ten classes never got it: the three Prime buttons, the settings select, the settings switch, the
rooms image, and — through shared code paths used by both robot generations — the vacuum entity
itself, ten sensors, the mission-progress sensor and the device tracker.

Device identifiers are unchanged, so nothing moves between devices; the metadata simply arrives.

## The check that would have caught all of this

`test_prime_platform_coverage.py` already ran every platform's setup and asserted entities came out.
It passed throughout, because it used `MagicMock` — where `getattr(m, "anything")` returns a truthy
mock, so reading attributes off what is really a dictionary looks like it works.

Three additions:

- every platform is now also run against **real library data**, parsed by the same code the
  integration uses (`tests/prime_fixtures.py`)
- every `Prime*` entity class that exists in the source must be built by some platform. A class that
  is never instantiated is absent from every comparison of one run against another, which is exactly
  how the schedule switch stayed invisible
- every entity a Prime setup produces must carry complete device info

The first two were verified by reintroducing the original bug: they fail.

4,696 tests.
